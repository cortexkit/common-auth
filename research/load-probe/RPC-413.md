# Oversized RPC request: early response and late test-body rejection

## Finding and scope

## Instrumentation and measurement boundaries

`rpc-413-trace.mjs` is an optional test-only preload. It observes the existing Node-compatible HTTP Server/IncomingMessage/ServerResponse methods, response finish, and server socket end/destroy/peer-FIN/close. The data observer is attached **after** the server's synchronous request callback: `readBody()` removes data listeners when entering discard mode, so an earlier listener would silently disappear. No src seam was needed. It records the original fetch promise and the separate response.json promise without replacing their return values. Rejection observers added by instrumentation can affect unhandled-promise diagnostics; they are not used as evidence that the original test could not leak.

Clocks use performance.now(), in milliseconds. The table below subtracts each request's fetch-start clock; numbers are min–max over runs, not a synthetic single execution. The request has declared length **1,048,588 bytes**. Counters measure bytes delivered to JavaScript request data listeners, not kernel receive buffers or client upload progress. No byte or body-end event occurred for the oversized request in any final measured run: bytes discarded were **0 at 413 write and 0 at close**; first/last-byte clocks and drain completion are **not observed**, not inferred to be complete.

Observer controls (`RPC_413_TRACE_ALL=1`) on each runtime also traced the ordinary follow-up POST: the observer recorded **2 bytes and body end** before the 200 reply. Thus the zero-byte result is not an inert counter. Both controls passed the actual declared-length test and its three assertions.

## Why the between-tests error survives body tracking

`TestLifetime.observe()` already attaches a rejection handler to the tracked body, and drain joins that body before resource cleanup. There is no detached `.then()`/`.finally()` chain in the original post helper: it awaits fetch and then JSON sequentially. However, **body ownership is not cancellation, and observing a rejected body does not stop Bun's runner from reporting the late body rejection after its own test deadline**.

`test/fixtures/rpc-abort.fixture.ts` demonstrates this with shortened, new control budgets (50 ms runner, 100 ms client), without changing existing budgets:

- With withheld headers, fetch rejects with TimeoutError; JSON is never entered.
- With headers plus incomplete JSON, fetch resolves; response.json() rejects with TimeoutError.
- In both cases the raw async body rethrows that error, the already-observed tracked promise returned to Bun rejects, and Bun prints **Unhandled error between tests** alongside the original named timeout.
- The control's process unhandledRejection identity listener never runs. This is a runner late-body diagnostic, not evidence that an unobserved application promise escaped the registry.
- A caught-error exploration that let the body fulfill retained the named timeout and removed the between-tests diagnostic. This was diagnostic only: production tests do not swallow arbitrary request errors.

Representative old-signal output, on both Bun versions:

```text
CONTROL fetch rejection TimeoutError: The operation timed out.
CONTROL tracked body rejection observed TimeoutError: The operation timed out.
# Unhandled error between tests
TimeoutError: The operation timed out.
(fail) a request outlives the runner deadline
  ^ this test timed out after 50ms.
0 pass, 1 fail, 1 error
```

The partial-JSON control prints `CONTROL headers`, then `CONTROL json rejection TimeoutError`, with the same runner diagnostic. Thus it would be unsound to assign the historical unmarked TimeoutError uniquely to fetch. In the controls the originating promise and its propagation to the runner body are explicitly known; in the historical run they are not.

## Requested test-only changes, not a 413 fix

After the evidence was reported, the reviewer requested future-failure clocks and lifetime cancellation, rather than a speculative server drain change or transport replacement:

1. `test/rpc/request-phase-clock.ts` keeps cheap in-memory clocks for the original 413 test. It captures server 413 write/finish; byte totals and first/last delivered-byte times; body end/abort; server local end/destroy versus client peer-FIN; socket close; client headers; fetch settlement; and JSON settlement. Teardown stop is marked separately so its close is not misdiagnosed as an early-response close. Null first/last timestamps mean no byte was observed. It emits **one JSON diagnostic only when the body did not successfully finish its assertions**, including lifetime cancellation, and restores its spies in cleanup. No per-chunk logging is retained in the ordinary suite.
2. `TestLifetime.signal` is aborted at the beginning of drain, before waiting for bodies. The request-errors helper combines `AbortSignal.timeout(5_000)` with the lifetime signal via AbortSignal.any. The other in-fence fetch timeout in `rpc-server.test.ts` combines its existing 15,000 ms signal in the same way; that budget is unchanged.
3. **Adding a signal alone was insufficient**: a controlled run still printed a between-tests **AbortError** instead of TimeoutError. The tracked body therefore consumes **only the exact lifetime cancellation reason while drain is active**. A timer abort, assertion failure, or any unrelated rejection remains rejected and visible. This is necessary to prevent Bun from treating teardown's expected cancellation as a second failure. It does not convert the runner timeout into a pass.

New-signal output on both runtimes, for fetch and JSON controls:

```text
CONTROL fetch rejection AbortError: The operation was aborted.
CONTROL tracked body fulfilled
(fail) a request outlives the runner deadline
  ^ this test timed out after 50ms.
0 pass, 1 fail
```

`request-cancellation.test.ts` asserts the old and new real-runner outcomes for both phases, plus abort-before-join ordering, unrelated-error preservation, and timer-error preservation. The child timeout remains a failure under its own name; no between-tests error is accepted in the new-signal branch. The child fixture is not discovered by the full suite.

The out-of-fence `test/opencode2/e2e/placement.e2e.test.ts` also uses AbortSignal.timeout. It is deliberately unchanged, by reviewer decision: it runs only in its dedicated real-host CI job (skipped in normal runs), its 1 s fetch is a retrying health poll rather than the single request involved here, and no leak has been observed there. Research host scripts and the library's cachekeep signal are also outside this test-only change.

This cancellation addresses a continuing fetch/JSON await when drain begins. A timer rejection already propagated before drain begins remains a genuine rejection; it is not hidden by name-matching TimeoutError or blanket error suppression. It is not a claim that every race between equal deadlines is eliminated.
