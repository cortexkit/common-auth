# Adoption inventory

This revision is publish-ready, not published, and does not adopt the library into any plugin. A later adoption into the openai-auth plugin must use a published npm range for `@cortexkit/common-auth` as a build-time devDependency, bundle/inline it, and verify its absence from the consumer's node_modules. No git, file or link dependency is permitted.

Only **moves** machinery and its covering tests are removed/replaced. A partial-file move does not authorize deleting policy in the same file. Origins in [sources.md](sources.md) are historical provenance labels, not required files or runtime imports; both inventories remain usable without the supplied reference tree.

## Adoption inputs: public exports and parameters

### ./setup

`@cortexkit/common-auth/setup` is a Node-compatible ESM subpath, not a plugin
bin. Each plugin's later adoption supplies its own Node bin and calls
`await runSetup(plugin, process.argv.slice(3))` after dispatching `setup`.
No prompt-library dependency is required.
The `/setup` subpath requires the `@cortexkit/claustrum-client` peer (the package's
supported floor is `>=0.6.2`), including for local sign-in and dry runs. Its
Claustrum imports are static so plugin bundlers keep the setup code in the entry
bundle rather than emit lazy chunks that a running host could lose when `dist`
is rebuilt. The three adopting auth plugins already depend on this peer.
The peer remains optional in package-wide metadata for consumers of subpaths
that do not use Claustrum; `/setup` consumers must install it.

The minimal `SetupPlugin` contract is:

```ts
import type { SetupPlugin } from '@cortexkit/common-auth/setup'

const plugin: SetupPlugin = {
  packages: { opencode: '@cortexkit/opencode-example-auth', pi: '@cortexkit/pi-example-auth' },
  version: '1.2.3', // The plugin's concrete published version, not a range.
  displayName: 'Example Auth',
  slashCommand: '/example',
  vault: {
    connectionFile, // Resolve provider-specific environment overrides in the plugin.
    hosts: {
      opencode: { name: 'example-auth-opencode', paths: { stateDir, host: 'opencode' } },
      pi: { name: 'example-auth-pi', paths: { stateDir, host: 'pi', override: piTokenPath, cwd } },
    },
  },
  signInLocal: async (host, context) => { /* provider login and local-custody checks */ },
  beforeRegister: async (host, mode, context) => { /* optional provider activation and custody checks */ },
  migrate: async (host, context) => { /* provider-specific migration */ },
}
```

`vault.hosts[host].paths` is exactly the input to `/claustrum`'s
`hostEnrollmentPaths`, with separate host identities and enrollment files.
Setup proves availability by finding `ck` on PATH and handshaking the supplied
connection file within two seconds. Connect uses the existing enrollment manager,
prints the `ck auth enroll approve` command, and polls for up to five minutes;
pending requests survive for a later rerun. Enrollment does not grant a
provider's account permissions or switch its serving store: provider-specific
grants, Pi auth-slot consent, migration-path overlap checks and exclusive
vault-mode policy remain in the callbacks. `signInLocal` must reject non-local
custody before initiating login, as the existing plugins do. Callbacks are never
called during a dry run.

Since 0.17.0 each callback also receives a `SetupCallbackContext`:
`{ opencodeGeneration: '1' | '2' | 'both', mode: 'local' | 'claustrum', hosts }`:
the generation being registered after `--opencode` or the interactive choice,
and every host this run sets up, so the first `beforeSignIn` can check
conditions across all of them before any host changes. It also carries `piAgentDir`, Pi's agent folder resolved the way Pi does
(`PI_CODING_AGENT_DIR` with `~` expanded, else `~/.pi/agent`): Pi's own
`auth.json` is there, so plugins use it instead of their own path settings.
OpenCode 2 does not read OpenCode 1's login file, so a plugin signs in the way
the registered generation expects. Callbacks written for 0.16.0 that ignore the
argument keep working.

Cancelling any setup question (Escape or Ctrl-C) stops setup with no change;
at the vault question that is distinct from an explicit "No", which chooses
local sign-in.

A dry run changes nothing, so it previews running hosts with
`previewRunningHosts`: on Windows that skips the PowerShell query for Node and
Bun command lines, because PowerShell writes a startup cache into the user's
profile, and only reports how many Node or Bun programs are running. A real
run does the full inspection.

The process fence names a host from the program a process runs, or the script
a Node or Bun runtime was started with (skipping runtime options and their
values, and `bun run`); other arguments never count. `ps` prints arguments
unquoted, so on macOS and Linux a program or script path containing spaces is
not recognized. npm and Bun install OpenCode and Pi under paths without spaces;
Windows reads quoted command lines and has no such limit.

The optional `beforeSignIn(host, context)` runs on a real run for each host
after the host, mode and generation are chosen and before the vault ceremony
or `signInLocal`, while nothing has changed yet. Rejecting stops setup for that
host with no enrollment, authority change or registration; use it for consent
(for example before moving an existing Pi login aside) or other preconditions.
A dry run prints it instead of calling it. Provider category grants belong in
`beforeRegister(host, 'claustrum', context)`: the shared vault Connect runs
only the enrollment ceremony.

The shared flow detects and reports hosts and offers a toggle multiselect with
found hosts preselected. A real run refuses while OpenCode, LiteCode or Pi is
running; a dry run only reports the running processes. In a real run, setup then
chooses vault or local sign-in, runs `beforeRegister(host, mode)`, registers,
migrates, and prints a next step. The process check runs again between side
effects and before atomic config publication. Failed/malformed process inspection refuses on
a real run; a dry run only reports active hosts or inspection failure and proceeds
with its no-mutation plan. Windows uses `tasklist /FO CSV /NH` and accepts its idle
PID 0 row, with PowerShell CIM command-line inspection for other Node/Bun processes
so npm Pi/OpenCode entry scripts are recognized as hosts. The exported
`listSetupProcesses` returns the unfiltered snapshot (including the current
process) for inspection tests; callers must not print its command-line arguments.
process diagnostics retain only recognized executable names, not arguments.

Flags: `--yes`, `--dry-run`, `--claustrum`, `--no-claustrum`, `--login`,
`--opencode=1|2|both`, `--host=opencode|pi`, and `--enroll-only`.
`--host` is repeatable (not a comma list): `--host=opencode --host=pi` selects
both, with duplicates ignored. It bypasses the host picker and selects only
requested hosts, in OpenCode/Pi order. Unknown or unavailable hosts refuse with
the fixed message `Requested setup host is unknown or unavailable. Use
--host=opencode or --host=pi with a detected host.` A Pi folder without its CLI
is unavailable. `--host` works with `--yes`, `--opencode=1|2|both`, and
`--dry-run`; a dry run's final summary names the selection. Without `--host`,
interactive selection is unchanged and `--yes` selects all found hosts.
`--yes` does **not** implicitly authorize vault enrollment.
`--login` chooses local sign-in and conflicts with
`--claustrum`; the two Claustrum flags also conflict. Without a TTY, `--yes` is
required. A Pi agent folder counts as installed but registration still requires
its CLI on PATH. Dry runs print exact shared config paths and contents,
enrollment paths, the Pi install command, and which opaque plugin callbacks
would run. Temporary, isolated version-probe profiles are removed; the user's
profile and callback-owned files are not changed.

`--enroll-only` implies vault mode and requires an available Claustrum vault,
with or without `--claustrum`. It conflicts with `--login` and
`--no-claustrum`, refusing with `--enroll-only and --login cannot be used
together.` or `--enroll-only and --no-claustrum cannot be used together.`
It still runs `beforeSignIn` preconditions, proposes enrollment and waits for
approval, writing the selected hosts' enrollment state and token files. It
does not plan or validate registration config, call `beforeRegister` (vault
activation/category grants), register either plugin, or call `migrate`.
The final report says that no host config or plugin registration was written
and tells the user to register the plugin themselves and enable vault access
as required by the plugin. A dry run reports just enrollment and preconditions,
without any writes. Failure outcomes from `setupEnrollment` are unchanged.
The existing process fence still applies, including enrollment-only runs:
this flag does not yet allow setup while another OpenCode or Pi is running.

OpenCode uses `OPENCODE_CONFIG_DIR`, else `XDG_CONFIG_HOME/opencode`, else
`~/.config/opencode` on **all** OSes. A config folder alone, an AFT Desktop
marker, or `opencode` or `opencode2` on PATH proves installation, independently of
the version probe's success. Windows PATH lookup prefers `.exe`, `.cmd`, `.bat`
to npm's extensionless POSIX shim, and version/install batch launches use fixed
arguments through `cmd.exe /d /s /c`. Shell-expanding launcher paths or arguments refuse.
Pi honors `PI_CODING_AGENT_DIR`, including `~` and `file://` overrides.

Generation inference never starts OpenCode: it reads npm launcher targets and
owning package metadata, shared targets and the `opencode2` name. An unclassified
CLI, config-only or Desktop-only installation infers v2 from an existing plural
`plugins` key; otherwise it defaults to v1. Conflicting v1/v2 evidence prompts
interactively and refuses with `--yes` unless the generation flag is supplied.
The flag overrides inference everywhere. An end-to-end test against OpenCode
2.0.22 uses a package whose root exports the OpenCode 1 plugin, with a `./server`
entry for OpenCode 2. Registered only under `plugin`, the package's server entry
loads and fires a model hook in OpenCode 2. Consequently `both` uses the single
compatible `plugin` registration plus TUI config, not two config roots.

V1 writes `plugin` in OpenCode and TUI config; v2 writes `plugins` in OpenCode
config only. Existing `.jsonc` is preferred to `.json`; absent files get a
minimal schema config. JSONC edits preserve unrelated comments and whitespace,
replace any version of the package, preserve tuple/object options, remove
duplicates and remove the package's entry from the alternate key. Other
plugins' entries are never removed. Setup's ordinary-config writer stages and
atomically replaces each config so readers never see a partially written file.
Existing POSIX file modes are preserved; Windows configs inherit the parent
folder's ACL without a protected DACL. Sharing-related Windows rename failures
retry for about two seconds, rechecking that OpenCode/Pi are stopped before each attempt.
Actual enrollment and credential secrets still use their private writers; setup
does not weaken their permissions. Pi is
registered by its resolved `pi install npm:<package>@<version>` command.
On install failure, the `./setup` subpath exports `SetupCommandError` with
`step`, `exitCode`, `signal`, and a `stderrTail` capped at 4 KiB of UTF-8 and
scrubbed by the shared credential redactor; its user-facing message is unchanged
except for the vault lines below.
Common-auth writes no diagnostic file, so a plugin chooses whether and where to
retain the error details.

Since 0.19.0, when a vault-mode setup fails after enrollment began for any
host, setup says which hosts are connected to the vault, because an approved
host stays enrolled when a later step fails. It prints one line per selected
host to the setup terminal, in setup order: `OpenCode: connected to the vault`,
`Pi: not connected` or `Pi: unknown, check with ck auth status`. It then
rethrows the original thrown value untouched: the same value, never read,
rewritten, wrapped or stringified, so a getter, a proxy, a thrown string or an
error classified by its exact message behaves exactly as without setup in
between. When the thrown value is an object, `setupEnrollment(error)` returns
the same outcomes as `{ host, outcome }` entries (`SetupHostEnrollment`, with
`outcome` `'enrolled' | 'not-enrolled' | 'unknown'`), kept beside the value
rather than on it; for a thrown primitive, or when there are none, it returns
`undefined`, and the printed lines are the only report. A failure while
working out or printing the report is ignored, so it never replaces the
original failure. The record belongs to the copy of the module that ran
`runSetup`, so a plugin that bundles common-auth must import `setupEnrollment`
from the same bundle as `runSetup`.
The outcomes are what setup recorded while it ran: `enrolled` once approval
landed and the token was written, `not-enrolled` for a host setup never asked
or whose enrollment the vault refused, could not be reached for, or never
approved before setup stopped waiting. Only a host whose enrollment was in
flight when setup failed is checked afterwards, by reading its enrollment files
once with `enrollmentAuthority`: `vault` reads as connected, `local` as not
connected, and an unreadable result stays `unknown`. A host is never re-probed
otherwise, so a host setup did not reach reads `not connected` even if an
earlier run enrolled it. A failure before any enrollment began, a local-mode
failure, a cancelled vault question and a successful setup are unchanged: no
lines and no record.

`runSetup` returns `{ hosts, dryRun, mode, detection }` and throws on refusal;
the bin owns exit codes. Optional `SetupIO` provides the existing menu terminal,
environment, platform/home/cwd and injectable filesystem, command runner,
process fence, enrollment connection and polling delay for tests. The subpath
also exports detection, registration and fence helpers and their types; it
does not depend on a Bun runtime, OpenTUI or a provider plugin.

All ten subpaths are ESM, with `dist/<subpath>/index.js` and adjacent `index.d.ts` targets. Since 0.1.1, `/fs` also exports the try-once lock underneath `withLock`, `acquireRefreshFileLock({name, ttlMs, path, renew?, renewIntervalMs?, onStep?})`, which returns a `{release, assertOwned}` handle or `null` when the lock is held, and `isLostMarkerRaceError`. It is for callers that hold a lock across several steps or poll rather than wait; openai-auth's refresh leases use it to retain exclusive ownership across a provider request and its token write-back. The adopting plugin supplies its file paths, directory prefixes, registry key, preferences key, logger channels and schema/merge policy.

### ./rpc

(0.9.4) The `applyDeadlineMs` timer no longer keeps the process alive on its own: once `stop()` has closed the connections, an `apply` handler that never settles does not hold the process open until its deadline. The deadline still answers a live request as before; the handler itself is still not cancelled.

(0.9.3) `./rpc/client` exports only the client side (`createRpcClient`, `discoverPortFile`, `DEFAULT_RPC_TIMEOUT_MS` and their types) and loads only the client and port-file modules, so a sidebar process can talk to its server without loading the server, its notification queue or the server registry. The same functions stay exported from `./rpc`.

(0.9.2) RPC discovery files containing server tokens are published by renaming unpredictable, exclusively created staging files with descriptor-enforced 0600 permissions; an existing staging name rejects the write without publishing or removing that existing file.

Default pending parsing (0.9.1) rejects present cursors that are not non-negative safe integers and present sessions that are not strings with 400 `invalid params`, while preserving absent cursors as 0, empty-string sessions, and the existing `requireSession` check; plugins can instead supply `parsePending` over the raw parsed JSON value, including non-object bodies and throw `RpcRequestError` for their own 4xx wire response (other parser errors return 400 `invalid params`).
Exactly one of synchronous `drain` or `drainAsync` is required (0.9.1), with `RpcServerAsyncOptions` describing the async alternative without changing `RpcServerOptions['drain']`; async failures log at warn and return 500 `drain failed` without exposing the exception message.
Server `stop()` (0.9.1) closes the listener and destroys tracked sockets, so unfinished requests cannot delay shutdown. The port file is removed only if its port and token still identify this server so a successor's registration is not deleted.

Server `stop()` also closes peers that sent incomplete headers: it calls `closeAllConnections` before `close()`, because Bun's `close()` disables `closeAllConnections` and such peers may not have reached the tracked connection set.

Runtime exports:
- `pushNotification(scope, payload, sessionId?)`, `drainNotifications(scope, lastReceivedId?, sessionId?)`, `isTuiConnected(scope, sessionId)`, `resetNotificationsForTest(scope)`, `isSessionId(value)`, `RpcSessionRequiredError`. Scope is `{ rpcRoot, directoryPrefix, registrationSessionId, requireSession? }`; payload is `{ command, text, knobs }`; wire sessionId remains optional unless the scope is strict.
- **Strict sessions (library decision: opt-in).** By default a drain with no session returns every session's notifications and a push with no session reaches every session; openai-auth drains from one process-wide TUI scope and relies on that, so making strict the default would change its behaviour. A plugin that needs per-session isolation (anthropic-auth's native drain rejects a missing session) sets `requireSession: true` on the scope and `requireSession: true` on `startRpcServer`. The strict scope then throws `RpcSessionRequiredError` on a push or drain whose session is absent or empty, a drain returns only that session's notifications (the strict queue holds no session-less ones), and the strict queue is separate from the same scope without the flag. The server answers a `pending-notifications` call whose `sessionId` is absent, empty or not a string with 400 `{error: 'session required'}` and never calls `drain`. A plugin must not alias a mandatory-session drain to the lenient default.
- **Sessionless drain (added in 0.8.0, opt-in).** `NotificationScope.sessionlessDrain` is `'all'` (default, the behaviour above, which openai-auth relies on) or `'broadcast-only'`. In `'broadcast-only'` a drain with no session returns only broadcasts (notifications pushed without a session), never a session's targeted ones, and `isTuiConnected(scope, undefined)` is true while any drain on the queue, with or without a session, happened less than 3000 ms ago (live at +2999 ms, dead at +3000 ms). `isTuiConnected` now takes `string | undefined`; the argument stays required, and a default scope still answers false without a session. **Acknowledged broadcasts follow antigravity-auth:** after a sessionless ack in `'broadcast-only'` the acknowledged broadcasts are dropped from the queue, so a later session drain no longer sees them (`['session-b']`, not `['broadcast','session-b']`); targeted notifications are never consumed by a sessionless ack. The default mode keeps every notification on a sessionless ack. The option applies to each call made with the scope and does not split the queue, unlike `requireSession`.
- A handler that throws is answered 500 `{error: 'internal error'}`; the exception text goes only to the plugin's log channel (`rpc request failed`), since it can quote a request or a credential. **Since 0.8.0** a handler (`apply` or `drain`) can throw the exported `RpcRequestError(status, message)` (status must be an integer 400..499, otherwise the constructor throws `RangeError`) to answer that status with `{error: message}`; its message is sent on the wire, so the plugin writes it for the client. Anything else, including an error with a `status` field, still answers 500.
- **Request boundary fixes (0.8.0, default).** A body that is not JSON answers 400 `{error: 'invalid json'}` (was 500 plus a warn). A body over the 1 MB cap answers 413 `{error: 'body too large'}` with `connection: close`, with streamed overflow read and discarded so the uploader can finish; a declared `content-length` over the cap is refused before reading and its socket is half-closed once the 413 response finishes, while discarding incoming data. For declared oversize, the server destroys the refused connection when its request body ends or after a fixed two-second linger bound (matching the default request-delivery timeout), and clears the timer on close. This stops Bun 1.3.14 fetch reuse of refused connections while delivering complete 413 JSON to measured slow declared-length uploaders; streaming overflow retains its existing discard behavior to avoid the EPIPE observed with immediate destroy on Bun 1.4.2. An early response can still cancel a Bun node:http uploader's write side; callers must consume the response even when subsequent writes are rejected. The sidebar raw-socket client already opens a new socket per call and is unchanged. Routing uses the URL pathname, so `/rpc/pending-notifications?probe=1` and `/health?x=1` reach their method (was 404). openai-auth's client already turns any non-2xx answer or a connection error into its fallback, so its behaviour is unchanged.
- **`applyDeadlineMs` (0.8.0, opt-in).** When set, an `apply` handler still running at the deadline is answered 504 `{error: 'handler deadline exceeded'}` at about that time; the handler is not cancelled and its later result or failure is discarded. Unset (the default), only the socket inactivity timeout `timeoutMs` (90 s) bounds a handler, by destroying the socket. The 90 s and 2 s defaults are unchanged; antigravity-auth's own deadline is 120 s, which it passes explicitly.
- **Port files (0.8.0, default).** An entry is usable only if its body PID equals the PID in its file name (`port-<pid>.json`), is a positive safe integer, its port is an integer in 1..65535, and its token is a non-empty string. Unusable entries are ignored by discovery and removed by the sweep, as malformed ones already were. A PID that is not a positive safe integer is never probed with `process.kill` (0 and negatives address process groups). A failed write removes its temp file (it holds the server token), and a server whose port-file write fails at start closes its listener and leaves no temp file. `writePortFile` always writes a well-formed entry, so openai-auth's files are unaffected.
- **Exact PID (0.8.0, opt-in).** `discoverPortFile(dir, expectedPid, { exactPid: true })` returns the expected PID's live entry or null, never another live entry; with no expected PID it returns null. `createRpcClient(dir, expectedPid, onSelected, { exactPid: true })` uses it on every call, so no request ever goes to another server: a call with no matching server returns its fallback without opening a socket. Without the option both still fall back to the newest live entry.
- **Cached selection (0.11.4).** A client reuses the server it validated, per resolved directory, expected PID and `exactPid`, while that server's port file is unchanged (same path, inode, modification time and token); it does not rescan the directory on every call. A connection refused before any request was sent, or a 401, 403, 404 or 410 answer, drops the cache, rediscovers, and resends once in the same call, and only to a different server. A 5xx answer (including the 504 an apply past its deadline returns, whose handler may still be running) and any failure after the connection opened are never resent. `exactPid` still refuses rather than falling back. Additive surface in 0.11.4: `portFileIdentity(dir, entry)` from `./rpc` (the identity the cache compares), and the `discover` option on `RpcClientOptions`, a test seam that replaces `discoverPortFile` and is not meant for plugins. `./rpc/client` exports are unchanged.
- **`onSelected` is a report, not a gate (0.8.0).** It counts as reported only after it returns: an observer that throws rejects that call before any request is sent and is called again on the next call. Once one call of it has returned, later calls do not consult it. A plugin that must never reach another server uses `exactPid`, not a throwing observer.
- **Direct loopback RPC.** The RPC client connects to `127.0.0.1` via `node:net`, so no runtime HTTP proxy configuration can receive its bearer token (including Bun 1.3.14 and Node's `NODE_USE_ENV_PROXY`). Each call writes one HTTP/1.0 JSON POST with `Connection: close`. It completes and destroys the socket once exactly Content-Length bytes arrive (rejecting any overrun already received), or reads to EOF if there is no length. The raw-socket server probe in `test/rpc/client-proxy.test.ts` asserts an unchunked JSON reply and EOF on Bun 1.3.14, Bun 1.4.2 and Node 24; Bun 1.3.14 can keep a delayed HTTP/1.0 apply reply open even after sending its complete length-delimited body, so completion must not depend on EOF. The client rejects non-2xx, invalid JSON, Content-Length underruns or overruns, any Transfer-Encoding, socket errors, headers over 16 KiB and bodies over 8 MiB with the existing fallback. The total deadline covering connect, request and the full response (not an idle timeout) remains 2 seconds by default, with a per-apply override; sockets are destroyed after completion and never pooled.
- `createManagedRpcStateDirPredicate(directoryPrefix)`, `isManagedRpcStateDir(name, directoryPrefix)`, `getRpcDir(rpcRoot, directoryPrefix, projectDirectory)` (pure layout helper, not the host resolver).
- `writePortFile(dir, { port, token, pid }, { secureDir?, beforeWrite? }?)`, `sweepRpcState(root, activeDir, isManagedDir, log?)`, `discoverPortFile(dir, expectedPid?, { exactPid? }?)`.
- `DEFAULT_RPC_TIMEOUT_MS`, `createRpcClient(dir, expectedPid?, onSelected?, { exactPid? }?)`; client methods `pending(lastReceivedId, sessionId?, timeoutMs?)` (the per-call timeout added in 0.9.0), `apply(request, timeoutMs?)`; both use a total deadline over connect, request and the full reply, default `DEFAULT_RPC_TIMEOUT_MS`. The deadline starts after port-file discovery, which it does not bound, and it is an ordinary timer: if the event loop is blocked past the deadline, the timeout runs when the loop resumes. Measured on the 0.9.0 package with a 250 ms deadline (Bun 1.3.14, Bun 1.4.2, Node 24.16): calls settled in 250-256 ms with discovery taking 0.1-2.3 ms; with the event loop blocked for 600 ms they settled in 701-704 ms.
- `startRpcServer({ dir, isManagedDir, drain, apply, log?, secureDir?, sweepRoot?, timeoutMs?, receiptTimeoutMs?, requireSession?, applyDeadlineMs? })`; handle `{ port, token, stop() }`. Injected apply receives opaque command/arguments/sessionId; the plugin keeps its command handlers. `RpcRequestError(status, message)`.
- `adoptRpcServer(registryKey, rpcDir, create)` returns `{ server, release() }`. Registry key is required, with no plugin default.

Type exports: `RpcLogChannel`, `ApplyRequest`, `ApplyResult`, `OpenDialogPayload`, `RpcNotification`, `NotificationScope`, `PortFileEntry`, `DiscoverPortFileOptions`, `RpcClient`, `RpcClientOptions`, `RpcServerHandle`, `RpcServerOptions`, `RpcServerAdoption`. Logging is optional channel-bound `{ warn, debug }`; directory hardening and sweep are host-selected, never inferred from environment.

#### ./rpc guarantees (agreed with antigravity-auth for its private OpenCode 1 bridge, after 0.9.2)

What the shared server and client promise, which a plugin can rely on instead of keeping its own HTTP engine:
- The server binds only to 127.0.0.1 on an ephemeral port, with a fresh 32-byte bearer token per server, never written to logs or terminal streams.
- Authorization is checked before a known call is parsed; unauthorized and malformed calls are refused and never reach `apply` or a drain. Unexpected handler errors answer with a fixed code, without their message.
- Plugin policy stays in the narrow callbacks: `apply` validates its own commands; `parsePending` sees the raw parsed body and may require the cursor or keep its own session rules; `drainAsync` results are awaited and a rejection is sanitized. Late `apply` results past `applyDeadlineMs` are discarded; that does not cancel the callback.
- Port files are published atomically as regular 0600 files in a 0700 directory (POSIX), from unpredictable exclusively created stages; an existing stage is never followed, reused or removed. `stop()` removes the port file only when it still holds this server's port and token.
- Discovery with `exactPid` never falls back to another process; malformed or mismatched entries are rejected.
- Loopback calls go straight to the socket and never through proxy environment variables. The client deadline covers connect, request and reply after discovery, as an ordinary timer (event-loop delay can make it fire late).
- `timeoutMs` (default 90 000) is the per-request socket inactivity timer and `receiptTimeoutMs` (default 2 000) bounds receipt of the request; a plugin whose `apply` runs longer sets `timeoutMs` at least that long.
- On Bun 1.3.14 that per-request timer is coarse. Its `node:http` `req.setTimeout` hands the value to uSockets in whole seconds, rounded up (`src/js/node/_http_incoming.ts:404`), and uSockets checks socket timeouts on a 4-second sweep (`LIBUS_TIMEOUT_GRANULARITY` 4, `libusockets.h:64`; scheduled in `loop.c:53-56`, applied in `socket.c:104-109`); on the node:http path the value is also capped at 255 seconds (`NodeHTTPResponse.zig:1166`). So a non-zero `timeoutMs` closes the request only at the first sweep after it lapses, possibly several seconds late, and a handler shorter than that sweep finishes normally. Measured on macOS arm64 with a silent 6.5 s `apply` and `drain`: `timeoutMs: 1500` closed at about 4.01 s on Bun 1.3.14 and at 1.51-1.54 s on Bun 1.4.2, Node 20.0.0 and Node 24.16. `0` disables the timer on all four runtimes, and the 90 000 default is unaffected. The library does not claim a precise elapsed bound, or the exact activity semantics, on Bun 1.3.14.
- `stop()` closes active and half-sent connections (verified on Bun 1.3.14, Bun 1.4.2 and Node 24.16, the runtimes CI and local runs exercise); it does not cancel callbacks already running, but from 0.9.4 a still-pending `apply` no longer keeps the process alive through its deadline timer.

Documented differences that are not reasons for another engine or option: the body cap is 1,000,000 bytes (not 1 MiB); error text capitalisation and the order of authorization versus parsing for unknown paths; the JSON charset spelling in the content type; malformed port files are left in place rather than removed. An empty body parses as `{}` and must be rejected by the plugin's `parsePending` if its policy requires fields.

### ./fs

#### Windows owner-only persistence

Windows: safe-parent everywhere. POSIX: unchanged from 0.14.2; only enrollment checks ancestry.

`@cortexkit/private-files@^0.2.1` is a **runtime dependency**, not an optional
peer. Only the Windows branch dynamically imports it; its own loader selects
the published x64/ARM64 N-API prebuild. Unsupported volumes, ambiguous/local
namespaces, reparse points, unsafe ancestors, unavailable native loading and
failed descriptor verification refuse without falling back to mode bits.
`PrivateFileError` (exported from `/fs`) identifies `path`, `stage`, normalized
`code`, optional `win32Code`/`reason`, `published`, `fileDurable`,
`durabilityConfirmed`, rename `attempts`/`elapsedMs` and an optional private
`orphanPath`. Its message contains remediation, never file contents. POSIX secret-file
bytes, modes, atomic replacement and directory syscalls are unchanged from 0.14.2.
POSIX paths do not import private-files or check ancestry; enrollment alone retains
its original realpath/stat ancestor walk, including the Ubuntu private-group rule
and sticky-ancestor acceptance. POSIX logger flushes remain synchronous.

Reads use the backend's same-handle verify-and-read, not verify-then-Node-open.
The exact published read policy (including elevated owners and file inheritance
under a pinned protected parent) supersedes the earlier design; see the dated
update in [Windows private-files design](../research/windows-private-files/DESIGN.md).
New stages are protected and verified while empty by `createPrivateFile` before
bytes are written. Windows replacement never unlinks its destination first:
only rename gets six maximum attempts, with delays 10/20/40/80/100 ms and a
500 ms monotonic elapsed cap. A pending filesystem call can overrun the cap;
no overlapping late retry is started. Lease renewal has an additional lifetime
cap and repeats the owner/expiry/marker fence before each rename attempt.
Sharing/access errors are never acquisition, release or contention success.
Only demonstrated exclusive collisions and missing-object Win32 codes are
normalized; original errors remain available as the cause.

On Windows, existing containing directories use `verifySafeParent`, not the
owner-only secret-file template. Safe real config parents can retain
SYSTEM/Administrators/user inheritance. Missing directories are created
owner-only; no existing parent, dedicated root or sibling is implicitly tightened.
Windows retains `secureDir` and `privateParents` for compatibility, not as
permission-repair opt-ins. On POSIX, sidebar parents are tightened unless
`secureDir: false`, RPC directories are tightened when `secureDir: true`, and
dump and enrollment directories are tightened to 0700. Atomic JSON and lease
locks retain their original mkdir calls without ancestry checks; Pi retains its
0700 stash-directory requirement without tightening an existing stash parent.

Only the specific secret file paths common-auth owns can be permission-migrated
after their parent passes that policy. Published `private-files@0.2.1` accepts the
user, Administrators and LocalSystem as file owners, refuses reparse points and
foreign owners, replaces the DACL by handle without changing ownership and
verifies again by handle. TrustedInstaller is accepted for parents, not secret
files. Once per process/path, migration warns that the file may previously have
been readable and credentials may need rotation. Enrollment token cleanup is
not part of migration. Enrollment token publication belongs to
claustrum-client's coordinated adoption, not this common-auth change.

The private-file writers/readers listed in the [Windows design adoption inventory](../research/windows-private-files/DESIGN.md#4-adoption-inventory)
are implemented as follows:

| Site | Windows protection and caller obligation |
| --- | --- |
| Atomic JSON (including tracked writes) | Verify the safe parent, create/verify the empty stage before bytes, replace in place, then verify the published file. Store, settings, preferences and roster inherit this writer. |
| Refresh lease | Secure acquire/renewal stages, the eviction-marker directory and its owner file; verify reads and retain ownership/lifetime fences. Acquisition access/sharing errors reject rather than implying another owner won; release access/sharing errors reject rather than reporting the lease released. |
| RPC token | Verify-and-read tokens; safe-parent validation and owner-only staging irrespective of `secureDir`, with no parent tightening. |
| Sidebar | Verify its safe parent without tightening and use the shared writer; missing parents are created owner-only. |
| Logger | Ordered asynchronous append sink under a verified safe parent; retain the handle for automatic flushes, close before verified rotation/path changes, and discard it on IO errors. Hosts await `flushLogs()` to drain and close before shutdown; writable-by-others parents refuse. |
| Dump | Dedicated private directory, exclusive private artifacts and secure baseline/response staging; unverified parents refuse rather than silently losing a dump. |
| Enrollment | Handle-based token/status reads, shared safe-parent namespace checks, owner-only creation of missing directories and pending-state publication. Specific owned legacy files may migrate in safe default or override parents. No incidental token deletion. |
| Pi slot | Handle-based auth/stash reads and owner-only staging. Existing parents must pass the safe-parent policy, irrespective of `privateParents`, and are never tightened. File-only Windows durability is explicit. |

`durable: true` retains the file-and-directory contract. On Windows directory
metadata durability is unqualified, so it throws after rename with
`published: true`, `fileDurable: true`, `durabilityConfirmed: false`. An explicit
`durability: 'file-only-on-windows'` opt-in permits that weaker guarantee:
`FlushFileBuffers` on the stage precedes rename, without a directory-metadata
promise. `onOutcome` reports these flags without bytes; tracked publication
callbacks fire once at rename even if verification/durability fails afterward.

**Bundlers:** openai-auth bundles common-auth and antigravity-auth embeds its

(0.9.2) Atomic JSON writes and refresh-lock lease updates write complete contents into exclusively created staging files, enforcing 0600 through the open descriptor before rename so readers never observe partial bytes.

0.9.0 keeps the 0.8.0 lease lock. A lease holder that stalls past its lease can still overwrite or remove a successor's lock record (measured); the replacement is an OS kernel lock (`@cortexkit/file-lock`), now background hardening with no release target. Taking the lease over needs the holder to stall past its lease while holding the lock with a contender waiting.

(0.10.0) Post-recreation marker-loss cleanup now uses the same owner-ID fence as release, preserving an already-installed successor rather than unconditionally removing its record. This closes the demonstrated case where B is already installed before A starts relinquishing. Between A's owner read and its removal, a successor record written in that interval can still be deleted; the kernel lock, when it lands, removes that window.

(0.10.0) The `onStep` union adds `stale-lock-recreated`, an awaited control barrier emitted after exclusive stale-lock recreation succeeds and before the final marker ownership check. Its rejection propagates as the acquisition's rejection, and finally releases the marker. The recreated record is left in place, without renewal or a handle, until its lease expires; no immediate cleanup is promised. Exhaustive TypeScript switches over fs `onStep` or the store's forwarded `onLockStep` fail typechecking until they handle the new member. Observers must ignore steps they do not recognise; trace consumers see the new value on successful stale recreation. With no hook there is no extra awaited scheduling boundary. This barrier does not extend the lease or guarantee marker ownership.

Runtime exports: `writeJsonAtomic(path, value, { serialize?, beforeRename? }?)`; `lockPathFor(target, name)`; `withLock(target, { name, ttlMs, timeoutMs, renew? }, fn)`; `LockContentionError`, `LockOwnershipError`, `WRITER_LOCK_CONSTANTS`. `fn` gets `{ assertOwned(): Promise<void> }`. `renew` defaults false; timeoutMs is mandatory for direct withLock calls. Atomic default bytes are two-space JSON plus newline, mode 0600; sidebar explicitly uses compact JSON without newline.

`acquireRefreshFileLock({ path, name, ttlMs, renew?, renewIntervalMs?, onContended?, onRenewalTimer?, onStep? })` returns `RefreshFileLock | null`. `onContended()` is called, synchronously and never awaited, each time an attempt finds a live owner, just before the `null` return; a throwing callback is ignored, and a returned promise or thenable is not awaited, but its rejection is absorbed and ignored, so it does not become an unhandled rejection. Asynchronous work the callback starts without returning it remains the caller's responsibility. Stale takeover, eviction-marker contention and success do not call it. The handle exposes its actual file `ownerId`, `assertOwned()`, `release()`, `hasLost()` and `whenLost(): Promise<LockLoss>`. Loss is sticky and the promise resolves once on actual renewal/assertion events, with reason `taken-over`, `expired`, `unreadable` (assertion read failure), `renewal-failed` (renewal cannot verify ownership after an error), or `marker-lost` (post-write fencing failure). Known owner and numeric expiry are included as `expectedOwnerId`, `observedOwnerId`, `observedExpiresAt`. No observer polling is added; without renewal, detection requires `assertOwned()`. Transient renewal errors still retry if a live owned lease can be verified; terminal loss stops renewal and future assertions fail even if the file later looks owned again. Owner release is not loss: `whenLost()` stays pending after release unless it already resolved, and assertions after release throw without recording loss. Release is idempotent and retains its successor-owner deletion fence.

Filesystem leases always use wall time (`Date.now`) for acquisition, expiry, renewal, staleness and eviction, including the pool, generic `withLock`, Claustrum roster/enrollment, sidebar-file and Pi-slot locks on POSIX and Windows. No public lease API accepts an injected clock. Adapters supply the target path, lease durations, and opt-in renewal (`renew` still defaults false). They receive the persisted lease `ownerId`, used to check that the same caller still owns the lock, and event-driven loss state rather than inventing an identity or polling private files. This supports lease adapters without their own ownership tracking. Callers that previously supplied `now` to the filesystem lock must remove it; store-level `now` remains supported for logical stamps only. `LockOwnershipError` keeps its existing message and adds optional `expectedOwnerId`, `observedOwnerId`, `observedExpiresAt` details when known.

(0.15.0) Missing leases now retry exclusive creation without stale eviction. Stale removal is bound to the observed owner ID and expiry, or the legacy file's device/inode/mtime identity, and revalidated immediately before removal. Renewal rechecks expiry before publishing its staged lease. These are cooperative lease fences, not kernel-lock guarantees against arbitrary direct writers or filesystem changes.

(0.15.0) `withLock` accepts and forwards optional `onStep` and `onRenewalTimer` hooks. `openPoolStore` forwards its existing `onLockStep` through every store lock and additionally accepts `onRenewalTimer(lock, event)`, where `lock` is `{ name, path }` and `event` is `scheduled` or `cancelled`; `acquirePoolLock` forwards the same timer hook from its environment. The store's `onStep` remains a separate write-step hook. Timer observers are synchronous, never awaited, and their throws/returned rejections are isolated by the primitive; lock steps are awaited control barriers. New primitive steps are `lock-read-ready`, `lock-missing`, and `renewal-write-finished`. Lock-step observers must ignore values they do not recognise, and exhaustive switches must be updated to handle the new values. Downstream runtime wrappers must pass these optional callbacks into `openPoolStore`/`withLock` to observe them; no instrumentation of published files is needed.

Type exports: `AtomicWriteOptions`, `LockOptions`, `LockOwnershipDetails`, `RefreshFileLock`, `LockLoss`. Frozen sidebar defaults: name sidebar-write, ttlMs 10000, timeoutMs 15000, renew true; preferences: name preferences, ttlMs 10000, timeoutMs 2000, renew true. Writers only permit timeoutMs override. Contention details identify target/name/timeoutMs; ownership details identify target/name plus optional expected/observed ownership.

### ./pi-slot

On Windows Pi explicitly opts into file-only durability: the stash's bytes are
file-flushed and its rename is published before the slot is changed. There is
no directory metadata guarantee: **a crash between the stash rename and its
directory metadata reaching disk could lose the stash on Windows.** This is not
a claim about NTFS journal ordering. Windows checks safe auth/stash ancestry
regardless of `privateParents`; it never tightens an existing parent. Specific
trusted secret files may be permission-migrated after that check.
Real Windows CI exercises stash enter/inspect/exit, ACLs and second-user denial.

`openPiSlot({authPath, provider, stashPath, placeholderKey, lockTimeoutMs?})`
returns asynchronous `inspect()`, `enterVault()` and `exitVault()` operations.
`inspect()` reports `{slot: 'original'|'placeholder'|'foreign'|'empty',
stash: 'valid'|'missing'}` without returning credentials. Without a stash, a
non-placeholder credential is `original`; with a stash it must have the same
canonical SHA-256 to be `original`. An absent slot is always `empty`.
`exitVault()` returns `'restored'|'conflict'|'nothing-to-do'`. `PiSlotError`
has a credential-free `code`; malformed input/stashes, unsafe paths, lost locks
and lock timeouts throw typed errors rather than exposing filesystem or JSON
parser messages. Invalid-state and conflict refusals do not rewrite either file.
An I/O error after a durable rename may have committed that step: retry using
the recovery rules below, not by deleting the stash.

The plugin owns a dedicated stash path per auth file/provider and a non-secret,
deliberately unusable placeholder key. The key must be nonempty, must not start
with `!`, and must not contain `$` anywhere (including Pi's interpolation and
escape forms). Keep the same key and paths across restarts. On POSIX the stash is 0600
inside a 0700 directory; existing non-private stash directories are refused,
not chmodded. Regular files only are accepted; do not use symlinked auth files.
POSIX reads open with `O_NOFOLLOW`, validate the open descriptor, and read from
that same descriptor; Windows uses the private-files handle-based read. A pathname replaced before the read's identity check is refused.

All operations share Pi's `<authPath>.lock` mkdir/mtime/rmdir protocol: atomically
creating the directory acquires the lock, renewing its modification time keeps
it live, and removing it releases the lock. An old modification time permits
takeover after a crashed holder. Both Pi 0.86.1 and 1.0.4 use `realpath:false`,
but have two lock paths: `FileAuthStorageBackend.acquireLockAsync` sets a
30-second stale threshold (proper-lockfile renews every 15 seconds), while
`acquireLockSyncWithRetry`/`withLock` uses proper-lockfile defaults of 10 seconds
stale and 5 seconds renewal. The helper keeps its **takeover threshold at 30
seconds** so it never reclaims a live async Pi writer, but **renews every 3
seconds** to stay fresh for sync writers with margin below their 5-second update.
ELOCKED retries remain bounded (default 30 seconds). The lock implementation
uses Node builtins and common-auth's atomic writer, not a runtime
proper-lockfile dependency; Windows private-file operations use the published
`@cortexkit/private-files` runtime dependency. Normal process exit releases owned locks; an abrupt
kill or signal may leave a lock until its mtime becomes stale. Both auth writes
and stash writes use a private same-directory temp, file fsync and rename;
directory fsync is confirmed on POSIX only. Unrelated provider values are never reserialized.

Renewal and release check that the directory's device and inode match those
recorded after acquisition and its mtime still equals the last mtime written by
this holder. A changed or missing directory compromises the
lease: no further renewal or release touches it, and the next auth or stash
rename is refused. More than 10 seconds without a confirmed successful renewal
also compromises the lease, even if the directory identity and mtime still match:
a sync Pi writer is already entitled to take over. The helper checks this bound
before renewal (including after an awaited stat) and at every write/deletion lock
assertion, including immediately before an auth or stash rename. Failed renewals
still retry after one second unless the directory is missing or the 10-second
loss bound has passed. These checks narrow, but do not eliminate, the protocol's
takeover race. `stat` and `rmdir`/`utimes` are not atomic: a holder paused between
its own check and the operation can still remove or renew a successor's
directory. Pi's own proper-lockfile writers have the same limit. The shared
protocol has no on-disk owner identity; the device/inode checks are local only
and do not change Pi's on-disk protocol. Adding an owner token would not fence
Pi's writers.

On entry, the current slot's raw JSON value (or null for absence), parsed entry,
provider and canonical SHA-256 are durably stashed **before** installing the
`{type:'api_key', key:placeholderKey}` placeholder. An existing valid stash plus
the placeholder is an idempotent no-op. A stash plus the same original resumes
the interrupted swap. A different credential with a stash throws `conflict`
without changes. A placeholder without a stash throws `missing-stash`; it is
never adopted as an original.

On exit, the placeholder is replaced with the saved raw JSON, or removed for an
originally empty slot, before the stash is durably deleted. A stash plus the
original completes deletion after an interrupted restore. Foreign logins,
including deletion of an originally populated slot, return `conflict` and keep
the stash. No stash and no placeholder returns `nothing-to-do`. Never delete
the stash to resolve a conflict automatically; let the account owner decide
which login to retain. A stash hash detects corruption, not malicious rewriting
by an actor who can already edit private credential files.

Pi's auth storage reloads when the file revision changes, but the model registry
caches availability. **After a successful swap/restore, the extension must call
and await `ctx.modelRegistry.refresh()`**, including after restart recovery.
This helper does not change Pi or register alternate providers/models: local
and vault modes retain `google/`, `openai-codex/` and `anthropic/` identifiers.
While in vault mode the plugin must route exclusively through vault accounts;
the placeholder is not a usable account or a fallback. Enter before returning
control to Pi, and exit when disconnecting. This cannot prevent a refresh Pi
already completed before the extension's first opportunity to enter vault mode.

### ./claustrum

`mutateVaultRoster` callbacks receive `{ assertOwned }` for ownership fencing immediately before a caller-managed rename; existing one-argument callbacks remain compatible. If the assertion rejects, the caller must not rename.

**Classifying families (next minor).** `ClaustrumScopedCustody` accepts the new
`ClaustrumFamilyInput = ClaustrumFamily | ClassifyingClaustrumFamily<string>`.
`ClaustrumFamily` remains the same extendable interface, including required
`refreshAdapter` and optional `apiKeys`; existing adapter families keep their
discovery behavior and inventory shape. `ClaustrumConsumerOptions.family` still
accepts only that legacy interface. Several provider consumers share one
classifying family through `ClaustrumDiscoveryHub`, below.

`ClassifyingClaustrumFamily<Code>` supplies `category`, `refusalCodes: readonly
Code[]`, and `classify(row: VaultRowFacts)`. The library first requires `read`,
the family category, and type `oauth` or `api_key`. Then the policy is called
once per eligible row, returning `{ kind: 'not-mine' }`, `{ kind: 'mine', member
}` or `{ kind: 'refused', code }`. It may admit several OAuth refresh adapters
and static keys together; provider tables, reserved ids and host policy belong
to the caller, not this library.

`VaultRowFacts` is common-auth's own non-secret structure: `credentialId`,
`credentialType`, `categories`, and optional `refreshAdapter`, `providerIds` and
`authMethod`. It does not depend on newer client declarations. A decoded row
with no `providerIds` (including claustrum-client 0.12 rows) is refused as the
fixed library code `unmapped` before calling policy. An empty array still reaches
policy: it can mean an old daemon or a row without provider mapping. Remedy text
should name both an old client and an old daemon. A missing `authMethod` on a
row with provider ids remains the policy's decision.

Only declared refusal codes matching `^[a-z][a-z0-9-]{0,31}$` are published.
Thrown classifier errors, invalid results and undeclared or malformed codes
become the fixed library code `unclassified`; error messages are never published.
Callers should account for the library codes `unmapped` and `unclassified` in
addition to their declared codes.

For classifying families only, `VaultInventory.refused` lists `{ credentialId?,
code }` (blank ids omitted), and `notMine` counts rows without listing them.
Admitted `VaultCredential` and malformed admitted `SkippedVaultRecord` values
carry optional `member`. No refusal is admitted as a credential. These are
in-memory discovery fields only: the roster file format is unchanged, including
its rejected-record representation. No existing plugin adoption is included.

**Discovery hub and hub members (next minor).** `ClaustrumDiscoveryHub` is one
per host process for a plugin that serves several providers from one
classifying family. It owns the only vault connection and the only
`ClaustrumScopedCustody` (so kept receipts, outage state and the outage probe
exist once), one vault watch, and one `list_scoped` per refresh, fanned out to
one roster per provider. It refuses a legacy `ClaustrumFamily`. Options:
`stateDir`, `hostGeneration` (for example `opencode2`), `classifierInput` (the
exact plain-JSON object the plugin hands its classifier: classifier version,
supported-table entries, reserved provider set and host facts), the fixed
`members` set (lowercase file-safe ids; Windows device names are refused),
`routePrefix` and `mapAccount` for every member, `tokenPath`, `family`,
`connect`, `isCustodyActive`, plus the custody and timer options a consumer
passes today (`parseIdentity`, `requireAssertion`, `now`, `logger`,
`setTimeoutImpl`, `clearTimeoutImpl`, `pollIntervalMs`) and `onError`.

Members are built only by `hub.member(provider, options)` with the new
`ClaustrumHubMemberOptions`: `reservedRouteIds`, `onRoster`, `onError` and
`logger`, nothing else. The factory returns an ordinary `ClaustrumConsumer`
and throws `wrong-consumer` for a provider outside the member set, a second
build of one provider, or a hub-owned field (`rosterPath`, `tokenPath`,
`family`, `connect`, `isCustodyActive`, `insula`, `pollIntervalMs`,
`routePrefix`, `mapAccount`) passed through a cast. The hub gives member `P`
the roster path `hub.rosterPath(P)` =
`<stateDir>/rosters/<hostGeneration>/<fingerprint>/<P>.json`, where the
fingerprint is 16 hex digits of a SHA-256 over the canonical JSON of
`classifierInput`, the sorted member set, `routePrefix` and `mapAccount`'s
source text (a `classifierInput` that is not plain JSON throws
`invalid-state`). Every lock file of a roster sits beside it. The member's
quota writer, `authorize` re-read and `close` use that path. A member never
connects, lists, watches or ticks: `start()` starts the hub's tick;
`refresh()` is the hub's coalesced refresh and resolves after the hub pushed
this member's committed roster into memory (`undefined` while vault mode is
off; rejects with this member's own commit error while the others resolve);
`watchState()` is the hub's watch; `grantReach()` is the hub's reach while the
member's view equals the hub's committed view; `keptReceiptState()` is the
shared custody's; `authorize()` holds one custody lease at a time;
`reportFailure()` reports only through the lease that issued the receipt;
`decline()` retains kept receipts against the union of every member's roster;
`close()`/`dispose()` release the lease and never close the shared custody.
A member without a roster while vault mode is on fails `route-unavailable` on
its own. `ClaustrumConsumerOptions` and consumers built with them are
unchanged.

`hub.acquire(signal?)` returns a `CustodyLease { custody, generation, release()
}`. Each connection is one generation; its lease count includes acquirers still
waiting. An abort or a rejected connect gives the count back; a connect that
resolves after its generation ended closes its client and never becomes a
custody; a lease's narrowed `custody` (`authorize`, `reportFailure`, `forget`,
`keptReceiptState`) throws `closed` after `release()` or once its generation
ended. The hub's own discovery holds a lease while vault mode is on, so the
connection stays open with no member lease. `hub.leaseState()` reports the
current generation and count.

`hub.start()` runs one unreferenced tick until `hub.close()`. Each tick reads
`isCustodyActive()` (local state only), installs member files that changed
under the same view (a decline, accept, reorder or quota reading written
outside the member) without calling `onRoster`, and lists when due (every tick
without an open watch, else on change notices and the five-minute safety
poll). Only the hub's own false authority read runs the inactive transition:
the current generation ends (every lease revoked, pending acquires reject
`not-active`), the watch stops, the custody closes with its kept receipts and
client, and every member is reset; later ticks make no vault request. Every
member commit, push, `retain`, committed view and watch opening checks the
generation it started in, so work in flight across off and on publishes
nothing. `hub.refusals()` (`{ view, refused, notMine }`) and `hub.grantReach()`
describe the last discovery every member committed and are undefined while
unknown.

**Several processes on one profile.** Each process's hub lists for itself;
there is no leader between processes. Each member commit is
`refreshVaultRoster` with the new optional `listedOver: { view }`: the view the
file held before the hub listed. The commit runs under the per-path discovery
lease and the roster write lock, as a plain consumer's does, and projects only
while the file still holds that view or the list's own view; otherwise another
process committed since the list, and its roster is returned unchanged.
Decline, accept, reorder and quota writes take the same write lock, so a
preference changed in one process survives another process's concurrent
commit. A tick installs a member file another writer changed under the same
view; a different view (or no roster in memory, or a route id that is one of
the member's `reservedRouteIds`) makes the member pending instead. A member is
**pending** while it holds no commit of the hub's latest list (its commit
failed, was refused, or returned another process's roster), and a pending
member makes the next tick list even while the watch is `watching`: on each of
the next three ticks, then after 2, 4, 8 ... ticks up to the five-minute safety
poll. A commit lost to another writer's roster lock (`roster-busy`, a lock
timeout or loss, or on Windows a `PrivateFileError` naming one of the roster's
lock files) is retried and is not a member error;
any other commit error goes to that member's `onError` only. A failed list and
a vault refusal of the watch go to the hub's `onError` and once to every
member's; a watch that only fails goes to the hub's alone. A member's first
roster under a new key takes the declines and account order (never the rows)
of its newest roster under an older key of the same host generation, the
layout without a fingerprint included, through the new optional
`ProjectionOptions.seed` (`vaultRosterSeed(roster)`); the older files are only
read.

### ./logger

On Windows `flushLogs()` returns a promise and hosts **must await it before
shutdown** to drain the queue and close the append handle, rather than registering
only a synchronous process-exit hook. Each instance serializes its sink operations,
verifies the protected owner-only parent, and securely creates or verifies its
log file before opening it with `fs.open(file, 'a')`. Other ordinary users cannot
create, replace or link entries in that parent between verification and open;
the owner and administrators are outside the threat model. Automatic 500 ms or
50-line flushes retain the handle and append only new bytes, without reading or
replacing the whole log. Rotation retains verified replace-in-place operations;
rotation, configure/path changes and open/append errors discard the handle, and
its next open requires fresh verification. Explicit flushes close the handle
after draining, so a later logging session opens it again. Explicit flushes reject
with typed, content-free errors; timer-triggered failures are retained for a later
flush to report. The log must live under a private dedicated directory; no
shared/custom log parent is silently chmodded. POSIX keeps the existing
synchronous append and exit behavior.
Windows preferences watchers likewise have no synchronous secret-read baseline:
they read asynchronously through the backend and surface refusals via `onError`
(or a content-free warning when it is not supplied).

Runtime exports: `initLogger({ file, level?, captureSink?, extraSecretKeys?, extraValuePatterns? })`, `createLogger(channel)`, `setLogLevel(levelOrUndefined)`, `flushLogs()`, `flushForTest()`, `resetLoggerForTest()`, `createCaptureSink()`, `createRedactor(options?)`, `redact(value)`, `redactStrings(value)`. File and level accept host providers; the host installs exit flushing. Capture returns records/sink/clear. A logger exposes error/warn/info/debug/trace methods taking message and optional data.

Type exports: `CaptureSink`, `LogTestRecord`, `InitLoggerOptions`, `SinkOnlyLoggerOptions`, `LoggerOptions`, `Level`, `RedactionOptions`, `Redactor`, `ChannelLogger`, `LoggerInstance`. ExtraSecretKeys receives the normalized key only; openai adoption supplies chatgptaccountid/email/orgname/organizationname extras and any value patterns. These are not common-set literals.

Configuration is owned by an instance. `createLoggerInstance(options)` (added in 0.4.0, same options as `initLogger`) returns `{ createLogger(channel), configure(options), setLogLevel(level), flushLogs() }` with its own file, level floor, runtime level, redaction, capture sink, buffer and flush timer; nothing one instance does reaches another. The module functions (`initLogger`, `createLogger`, `setLogLevel`, `flushLogs`, `flushForTest`, `resetLoggerForTest`) act on one default instance and behave as before; `initLogger` now also returns that default instance. A plugin whose copy of this module may be shared with another plugin in one runtime (one externalized package instance) must hold its own instance, since two `initLogger` callers on one copy still replace each other's file, level, redaction and capture sink; it installs `instance.flushLogs` as its exit handler. openai-auth's single-plugin use of the module functions is unchanged.

**Errors in logged data (added in 0.9.0).** An Error anywhere in the data (top level, in an object or array, any subclass, or one from another realm such as a vm context) is rendered as a plain object: `name`, `message`, `stack`, then `code` and `status` when defined (own or inherited, so DOMException's `code` getter counts), then `cause`, then the error's other own enumerable properties. 0.8.0 rendered only those enumerable properties, so a plain Error came out as `{}`. Every field goes through the same scrubbing as any other value: a token inside a message or stack is masked, and a secret-shaped key on the error (`accessToken`) is redacted. A cause is rendered the same way, whether it is an Error or not. A cyclic chain ends in `'[Circular]'`, and a chain is followed eight errors deep (counting every Error nested inside another), after which the next Error is the string `'[Truncated]'`. Non-Error values render exactly as before.

**Sink-only logger (added in 0.8.0).** `createLoggerInstance({ captureSink })` (and `initLogger`/`configure` with the same options) with no `file` delivers every record at or above its level to the sink, scrubbed exactly as with a file, prints nothing, buffers nothing and creates no file; it is for a host that forwards records to its own log (antigravity-auth forwards to the host's `app.log`). The options are `LoggerOptions = InitLoggerOptions | SinkOnlyLoggerOptions`: `InitLoggerOptions` keeps the file shape every earlier release accepted (`file` required), so a caller deriving a type from it with `Pick` or `extends` keeps compiling; `SinkOnlyLoggerOptions` requires `captureSink` and has no `file`. Options with neither do not type-check. A `file: () => ''` stand-in is not a supported mode. A logger with neither a file nor a sink (never configured) is still a silent no-op.

### ./redaction

`@cortexkit/common-auth/redaction` supplies `redactCredentialText`,
`redactCredentialError`, `redactCredentialFrame` and
`redactCredentialResponse`. These helpers are moved from openai-auth's
`packages/core/src/util/credential-redaction.ts`, with its three dedicated test
files, without changing their behavior. The only implementation change is the
relative import of the shared logger's `redactStrings`. Imports are static; the
subpath requires no host or vault peer dependencies and produces no lazy chunks.

Text redaction scans literal and escaped credentials. Error redaction returns a
fresh, scrubbed Error containing only the data needed for abort, quota and host
retry decisions, with 16,384-character diagnostic fields and a 64 KiB
`responseBody` projection that preserves retry markers. Frame redaction rewrites
only JSON error envelopes, retaining ordinary model output byte for byte and
keeping the escaped-error prefilters.

`await redactCredentialResponse(response, secret)` scrubs non-2xx HTTP bodies,
status text and diagnostic headers. Successful responses pass through unchanged
in the default `'http'` mode. Pass `'event-stream'` when the caller will parse
server-sent events (SSE), even if the provider omits or mislabels its content type:
the wrapper streams ordinary output and scrubs error frames, including failures
during reads and cancellation. It does not add a transport-error hook or scrub successful response
headers; callers that own the fetch must separately catch and redact thrown
errors, and scrub any successful headers they expose as diagnostics.

openai-auth's dedicated plugins keep their existing imports until they adopt this
subpath in a release; this move neither changes openai-auth nor makes common-auth
depend on it. The three source test files live under `test/redaction/`; their
existing mutation controls are carried into `mutations.toml`. Their separate
test-only TypeScript configuration keeps the original DOM response declarations
without changing the production compiler's libraries.

### ./sidebar-file

Runtime export: `createSidebarFile<T>({ path, defaultValue, normalize, timeoutMs?, secureDir?, logger?, repair?, lockName? })` returns `read()`, `write(value, hooks?)`, `update(merge, hooks?)`. The caller owns schema, normalization, quota, routing and sticky pins; merge receives current state and may return undefined to skip writing. `secureDir` (default true, since 0.1.2) tightens an existing parent directory to 0o700 before each write; pass false for a directory the user chose, such as an override path. A parent the library has to create is always created 0o700 (since 0.1.3). Internal hooks `beforeRecheck?`, `beforeCommit?` and `afterRename?` are for tests, not plugin policy. Type exports: `SidebarFile`, `SidebarFileHooks`, `SidebarFileOptions`, `SidebarRepair`, `SidebarWriteOptions`, `SidebarWriteResult`.

**Lock lost during the rename (added in 0.4.0).** The fence before the rename stops a write whose lock is already gone, but a lease that lapses between that fence and the rename lets the write land over a successor that took the lock meanwhile. After every rename the write checks ownership again and reports the outcome through the per-write `onResult(result)` callback in the write options (`write(value, options?)`, `update(merge, options?)`, where options are the hooks plus `repair?` and `onResult?`): `{ status: 'skipped' }` (merge returned undefined), `{ status: 'written' }` (lock held after the rename) or `{ status: 'lost-after-rename', repair }`. `write` and `update` still resolve to nothing, because openai-auth passes them on as `Promise<void>`. The plugin may supply `repair(current, written)`, on the file options or per write (the per-write one wins). It runs once, after the first lock is released, under a newly taken lock, on the file as it is now (the successor's state) and the value that was written; it returns what to write instead (typically the successor's state with only the fields this write is the authority on, as anthropic-auth republishes `activeId`, `route`, `relay`, `fastMode` and `cacheKeep`), or undefined to leave the file. `repair` reports `none` (no repair supplied; the write only reports, which is the earlier behaviour plus the report), `written`, `skipped`, `lock-unavailable` (the lock was not retaken within `timeoutMs`; logged, not rejected) or `lost-again` (the repaired write lost its lock too; logged and not repeated, since the newer holder is writing). Which fields a write may republish is the plugin's decision per write: anthropic-auth's writes that do not own routing (`routingAuthoritative: false`) keep the routing already on disk by re-running `resolvePreservedRouting` on the current state, and such a plugin passes a per-write `repair` that does the same. **Differs from anthropic-auth:** the repair lock waits up to `timeoutMs` like any write, where anthropic-auth tries once and drops the frame; a failed repair is reported through `onResult` instead of being swallowed by a `.catch`.

**Lock name (added in 0.8.0).** `lockName` (default `'sidebar-write'`, so openai-auth and anthropic-auth are unchanged) names the lock a write coordinates on, `<path>.<lockName>.lock`. It routes both lock acquisition and the ownership fence checked before the rename, so a takeover of the configured name between merge and rename refuses the write with `LockOwnershipError` and keeps the file. The option allows antigravity-auth to pass `lockName: 'sidebar'` and keep its existing writer's lock identity when it adopts the shared writer; that adoption is planned, not yet active. **Scope of the interop:** the library excludes another writer only while that writer holds a live lease of the same name in the same lock-file format (`wx`-created, `{ownerId, expiresAt}`), and with the same limit as every lease here (see ./fs): there is no guarantee once a holder stalls past its lease. Stale-lock reclamation, eviction markers and renewal shared with an older writer of a different implementation are not promised; that writer also checks ownership only before reading, so the library's before-rename fence is the stronger of the two during a mixed-version upgrade.

### ./tui-prefs

Runtime exports: `readTuiPreferencesFile(file)` for raw parsed object; `readTuiPreferences<T>({ file, pluginKey, defaults, schema })`, where schema receives `(entry: unknown, defaults: T)` and returns T; `createTuiPreferenceWriter({ file, pluginKey, timeoutMs?, beforeCommit? })` returning `queueTuiPreferenceUpdate(path, value)` (path is readonly string/number segments); `watchTuiPreferences(file, onChange, { watchDirectory? }?)` returning a disposer. **Watcher cost and recovery.** Subscriptions to the same canonical file path share one directory watcher and one reference-counted poll through a process-wide `Symbol.for` registry, including separately bundled library copies. Each subscriber keeps its own callback and disposer; callback errors do not block other subscribers, and the last disposer closes the native watcher and stops both timers. Native events remain the primary path with a 150 ms debounce. The safety path now probes mtime, size and inode every **1,000 ms**, and reads bytes only after a metadata change; raw-text equality still suppresses unchanged writes. Atomic replacement, an initially missing file/directory, and native-watch failure recover through the probe. **Consumer adaptation:** missed native events now take about **1 s**, rather than the former 100 ms full-file poll; callers and tests must allow that latency (plus I/O/scheduling), not rely on sub-second fallback. ### ./tui-build

Runtime exports: `buildTui(entryFile, variant, destinationDir, options?)`, `assertEmittedPublishList(packageRoot, destinationDir, emitted)`, `runtimeModules`, `runtimeModuleId(specifier)`, `loadSolidTransform()`. Variant is raw/runtime; options are `inline` (package names or `{ name, root }` pairs), `runtimeModules`, `loadSolidTransform`. Result `{ emitted, sources, selector, externals }` includes every emitted destination file and one absolute source per entry. Type exports: `BuildTuiOptions`, `TransformSolidSource`, `TuiBuildResult`. Transform takes `(code, { filename, moduleName, resolvePath })` and resolves to code. Build one destination per variant and compare the complete emitted set against the plugin publish list. The optional `@opentui/core` and `@opentui/solid` peer floor is 0.5.11; CI pins both to exactly 0.5.11 and runs the TUI build and runtime tests, build, and typecheck.

**Reproducible output (since 0.9.0).** The same source graph produces byte-identical output, file names and contents, wherever the checkout lives, so a compiled tree a plugin tracks in git stays clean on another machine. 0.8.0 named each shared copy after a hash of the source's absolute path. A shared copy is now `shared/<hash>-<basename>.js`, where the hash is the first 16 hex digits of sha256 of a key holding no absolute path: `package:<name>/<path inside the package>` for a file inside an inlined package (the innermost root when roots nest), otherwise `path:<path relative to the entry's directory>`. Distinct sources get distinct keys (one root per package name, one base directory for relative paths, distinct prefixes); the name is deliberately not derived from file contents, because two files with the same bytes at different paths are two modules with their own state, and the build throws rather than writing two sources to one name if two keys ever share a truncated hash. Names are computed from the entry's real path, so an entry passed through a symlink (macOS's `/var` temp directory, a linked checkout) no longer treats its own siblings as outside files. Consequences for a plugin: every shared file name changes once from 0.8.0, so a tracked tree is rebuilt once; a file outside every inlined package is named by its position relative to the entry, so moving the entry or that file renames its copy.

### ./quota

Pure functions over plain JSON; no file I/O, locks or clock reads (every time is a parameter).

**Quota map** (`QuotaMap`): `{ limits: QuotaEntry[], budget? }`. Each limit is keyed by `(scope, label)`: `scope` is `all` (`ALL_SCOPE`) or a model family, `label` names the provider's window. An entry is a reading `{ kind: 'reading', checkedAt, usedPercent, resetsAt?, windowMinutes? }`, a retirement tombstone `{ kind: 'retired', retiredAt }` or an absence record `{ kind: 'absent', checkedAt }`. A missing key is unknown; a tombstone or absence record is evidence that the key is unlimited, and admission treats both alike. The budget is a tri-state: absent (never reported), `{ kind: 'reading', checkedAt, reached, remainingPercent?, usedPercent?, resetsAt?, limit?, used?, remaining?, unit? }`, or `{ kind: 'cleared', checkedAt }`. Merge writes limits sorted by scope then label, so identical content serialises identically.

**Observation** (`QuotaObservation`): `{ checkedAt, readings?: [{ scope?, label, usedPercent, resetsAt?, windowMinutes? }], coverage?: [{ scope?, label }], budget?: { kind: 'reading', ... } | { kind: 'cleared' } }`; `scope` defaults to `all`. Coverage lists the pairs the observation speaks for with authority; every reading is implicitly covered. A header-shaped push covers only what it carries; a full poll covers every pair the source reports on. An absent `budget` says nothing about the budget.

**Merge rules** (`mergeQuotaObservation`). One freshness rule: an observation applies to a key when `checkedAt` is not older than the key's reading, retirement or absence time (equal applies, the observation applied last wins). A covered pair without a reading turns an existing reading or tombstone into a tombstone at `checkedAt`, and an empty or absent-recorded key into an absence record at `checkedAt`. Pairs outside the coverage are never touched. The budget follows the same rule against the stored budget's `checkedAt`. Unrecognised top-level keys of a stored map are carried over.

**Named counters (0.17.0).** `QuotaObservation` and `QuotaMap` also accept `counters?: Record<string, QuotaCounter>`, where `QuotaCounter` is `{ value: number, checkedAt: number }`: a non-negative finite integer and its finite timestamp in milliseconds. Names belong to the plugin; for example, openai-auth uses `resetCredits` for banked rate-limit resets. Each name merges by its own `checkedAt`, not the observation's limit/budget timestamp: older counts never overwrite newer ones, and equal timestamps apply last-writer-wins. An absent name (including an observation with no counters) leaves the stored count alone; report a newer zero to record depletion. Budget clears and limit coverage cannot clear counters. The codec's `decode: decodeQuotaMap` and roster reads drop malformed counters individually without losing valid quota, while validation and merge refuse malformed writes. `projectQuota` carries counters unchanged in every scope, including quota passed through a caller-owned sidebar file; counters do not affect projected limit freshness, formatting or routing. Empty counters are omitted from writes, so observations without counters keep the earlier file shape and bytes. `/store` codecs may optionally supply `decode(value)` to normalize persisted quota before validation; existing codecs need no change.

**Prepaid credits (0.23.0).** `QuotaObservation` and `QuotaMap` also accept `credits?: QuotaCredits`, where `QuotaCredits` is `{ hasCredits: boolean, unlimited: boolean, balance?: number, overageLimitReached?: boolean, checkedAt: number }` with a finite `balance` and a finite timestamp in milliseconds. It is a typed state, neither a counter nor the spend-control budget: for example openai-auth fills it from ChatGPT workspace credits (wham/usage `credits` and the `x-codex-credits-*` headers), which keep requests working after a rate-limit window is used up. The record merges by its own `checkedAt`, independently of the limits, budget and counters, exactly as one counter does: an older record never overwrites a newer one, an equal timestamp applies (the observation applied last wins), and an observation without `credits` leaves the stored record alone. Budget clears and limit coverage cannot clear it. `decodeQuotaMap` (and so the codec's `decode`, store reads and roster reads) drops a malformed stored credits record while keeping the limits, budget, counters and unknown keys, and returns a valid map as the same object; `mergeQuotaObservation` decodes the stored map the same way, so a malformed stored record is dropped on the next write instead of refusing it, while a malformed `credits` in an observation is refused like any malformed observation. `isQuotaCredits(value)` is the record check. `projectQuota` carries the record unchanged in every scope; it does not affect projected freshness, routing or any existing formatter output. Maps written without credits keep the earlier shape and bytes. Readers from 0.22 and earlier treat `credits` as an unrecognised top-level key: `isQuotaMap` tolerates it and `mergeQuotaObservation` carries it over untouched, so a pool shared with an older plugin keeps it. `quotaCreditsText(credits)` words the record as the official Codex client does: `Unlimited` when `unlimited` (even if `hasCredits` is false), `<n> credits` for a finite positive balance rounded to a whole number, `Available` when `hasCredits` with no usable balance, and `undefined` when there are no credits (or no record), so the caller shows no credits row. No existing formatter adds this text; a surface that wants a credits row calls the helper.

**Quota wording (0.13.0).** Every surface that shows quota (the command menu on OpenCode and Pi, the terminal auth menu, each plugin's sidebar) calls `formatQuota`, `quotaTextParts`, or `quotaWindowParts`, so the wording is the same in every plugin. Every figure is "% left". A general window (scope `all`) is named by its stored `windowMinutes` (`300` → `5h`, `10080` → `7d`, `1440` → `1d`, otherwise minutes); a model-scoped window keeps the label the plugin stored it under (`seven_day_opus`); a general window stored without a length falls back to its label. Windows read shortest first. A window the provider did not report is left out (never "not reported"): either an absence record (the provider answered without that window) or a tombstone (a window it reported before and has since dropped). The full form adds each reset as a short time from now (`resets 45m`, `resets 2h`, `resets 3d`; a reset already passed is left out); the compact form, for a dialog footer or a sidebar row, has none. The credit budget follows the windows (`credits 75% left`, `credits spent`, `credits available`). When the oldest reading shown is more than `QUOTA_STALE_AFTER_MS` old, both forms end with its age (`checked 3h ago`). The formatter reads no clock; `now` is a parameter.

**Narrow quota form (next minor).** `form: 'narrow'` fits one line per account in a 42-column sidebar beside the account label. Each window reads `<name> N%`, joined by ` · `, with ` left` once at the end: `5h 92% · 7d 66% left`, `7d 80% left`. `N` is the compact figure (remaining, rounded, clamped to 0–100). Account-wide windows (scope `all`) always show, first, in the compact order. After them comes at most one more item: the tightest (lowest remaining) of the model-scoped windows and the credit budget, so the longest line is like `5h 38% · 7d 59% · Fa 22% left`. On a tie a scoped window wins over the budget, and among scoped windows the first in display order wins; tightness compares the unrounded figure. The rule takes no width: the line depends only on the reading. A scoped window is named by its scope's model, not its label: any namespace before a colon is dropped and the first letter capitalized (`fable` → `Fable`, `model:claude-opus-4` → `Claude-opus-4`), then the first two letters are kept (`Fa`, `Cl`). When two scopes in the row would get the same name, each colliding name is extended one letter at a time until they differ (`fable` and `fabric` read `Fabl` and `Fabr`); a name that runs out of letters stays whole while the longer one keeps extending (`fa` and `fable` read `Fa` and `Fab`), so two different model names never share a short name; windows of the same scope share a name. Names are computed over every scoped window in the row, so a model keeps its name whichever window is tightest. Callers do not pass abbreviations. The credit budget, when it is the tightest item, reads `cr N%` (the compact remaining), `cr 0%` when spent (a spent budget counts as 0% left); a budget with no percentage never takes the slot, and when nothing else is shown the line keeps compact's `credits available`. A stale reading adds no age; `isQuotaStale` tells the caller to draw the line dim. A window whose reset arrived since the reading keeps its figure, as in compact (which has no separate wording for it). With nothing reported, narrow returns what compact returns. `quotaTextParts` with `form: 'narrow'` gives the pieces that join into the line (`['5h 92%', '7d 66% left']`). The compact and full forms are unchanged.

**Narrow quota form for named groups (next minor).** A plugin whose windows all belong to named groups, with no account-wide window (antigravity-auth: `Gemini` and `Other models`, each with its own 5h and 7d window), lists them on the projection as `ProjectedQuota.groups`: `[{ scope, label }]` in its own order, where every window stored under `scope` belongs to that group. This is an optional field; `projectQuota` never sets it, so a plugin building its own projection adds it. When the projection lists groups and has no account-wide window, the narrow line shows one item per group instead of the one-slot rule: the group's tightest window (least remaining, compared before rounding; the shorter window on a tie) as `<group> <window> N%`, then ` left` once: `Ge 7d 62% · Ot 7d 48% left`. The group is named by the short name of its label, derived exactly as a model-scoped window's is (first letter capitalized, the first two letters kept, colliding names extended one letter at a time until they differ): `Gemini` → `Ge`, `Other models` → `Ot`, `Gemini Pro` and `Gemini Flash` → `Gemini P` and `Gemini F`. Names are computed over every listed group, so a group keeps its name whichever groups show; a blank label falls back to the scope. The window is named by its stored length (`5h`, `7d`); a window stored without a length shows the group and figure only (`Ge 72% left`). Groups read in the order the projection lists them, so the line does not reorder as figures move. At most two groups show: with more, the two with least left, the earlier-listed on a tie, still in listed order. A group with no reported window is skipped and takes no place; when no listed group has a window, the ordinary narrow rule applies. Windows outside the listed groups and the credit budget are left out of a grouped line. As with every narrow line, the text takes no width and adds no age (`isQuotaStale` still reports staleness). A projection with an account-wide window, or without `groups`, reads exactly as in 0.20.0; a test compares every form against a frozen copy of the 0.20.0 formatter over generated readings. `quotaTextParts` with `form: 'narrow'` gives the grouped pieces (`['Ge 7d 62%', 'Ot 7d 48% left']`); `quotaWindowParts` has no narrow variant and is unchanged.

**Structured quota parts.** `quotaWindowParts` returns display-ordered windows, with each `kind` distinguishing a window from the budget, `name` giving its display name, `short` (0.23.0) the label the narrow line gives it (`5h` for an account-wide window, the model's short name such as `Fa` for a model-scoped one, `cr` for the budget), for rows too narrow for `name`, `figure` its shared figure wording, `remainingPercent` the clamped value when known, `resetIn` a bare future span, `checkedAt` the reading time, and `resetSinceReading` whether a reset arrived after that reading and no later than `now`; `age` is the optional stale marker. `figure` and `age` use the same wording as `quotaTextParts`, so callers can lay out rows without parsing strings.

**Where each plugin supplies a window's length.** The quota map already carries it: `windowMinutes` on a reading (`QuotaReadingEntry`, `ObservedReading`), projected as `ProjectedLimit.windowMinutes`; nothing was added to the map. openai-auth sets it from the usage response's `limit_window_seconds` (converted to minutes), the WebSocket `window_minutes` and the `x-codex-*-window-minutes` headers (`packages/core/src/pool-quota.ts`, `quota-normalize.ts`), only when the provider gave one. anthropic-auth must set `300` on `five_hour` and `10080` on `seven_day`: those field names fix the length, and without it the window is shown under its label. antigravity-auth's windows are model-scoped, so they are shown by label and a length is optional. (The anthropic-auth and antigravity-auth sources were not read for this note.)

**Projection.** A family request sees only its family's keys and the `all` keys, one entry per label. The label says how a family limit relates to a general one. Under the **same label** a family *reading* replaces the `all` entry for that label: use it only when the provider's family figure is a more specific view of the same cap (no current plugin relies on it; openai-auth stores only `all` keys). Under **different labels** both are projected and admission, selection weight and the break decision judge both, so a family cap that applies *on top of* the general cap must have its own label, or a family request never sees the general cap (pinned by `a family limit under its own label is projected beside the general limit of the same length`, `an exhausted general week refuses a family request whose own week is healthy` and `an exhausted family week refuses the family request and leaves the general request admitted`). A family *reading* shadows the `all` entry for its label; a family tombstone or absence record says only that no family-specific limit exists, so it does not hide an `all` entry for the same label and reaches the primitives only when there is none (library decision, pinned by `a family tombstone or absence record does not hide an all-models entry`). Limits are ordered longest stored `windowMinutes` first, unknown lengths last, then by label. Each limit carries its stored length as `windowMinutes`; an unknown stored length stays `undefined` and is never filled in by slot the way openai-auth's `getPresentQuotaWindows` fills `LEGACY_WINDOW_MINUTES` (declared divergence: a pre-dynamic-window snapshot migrated without a length sorts last and shows no length). `checkedAt` is the minimum reading time (the minimum evidence time when there is no reading), so a projection is only as fresh as its stalest reading; both the selection primitives and pending-bytes attribution see that minimum. A cleared budget projects no budget.

**Provider → (scope, window) mapping.** The library infers no labels; a plugin maps its provider's windows when it builds observations and passes the required labels per admission call. openai-auth: the wham/header primary window → `(all, primary)`, secondary → `(all, secondary)`, spend control → the budget, and a full poll covers both pairs; required labels `['primary']` (the default). anthropic-auth: `five_hour` and `seven_day` → `(all, five_hour)` and `(all, seven_day)`; a model-scoped week such as `seven_day_opus` → `(opus, seven_day_opus)`, keeping the provider's own field name as the label. The scoped week is an additional cap, not a more specific view of the general week, so it must **not** be stored as `(opus, seven_day)`: that label would replace the general week in an `opus` projection, and an exhausted general week would then admit an `opus` request. The adapter passes its own required labels, and records a scoped week as absent only when its source covers scoped limits with authority (a poll that lists them), never because a header-shaped push lacked one. Extra usage is not mapped to the budget by default; see *Native policy that stays in the adapter* under ./routing. antigravity-auth: each per-model quota → `(<model family>, <its window label>)`.

**Admission.** A marked row is excluded while `now < expiresAt` and readmitted at its roster position from the expiry on; a backed-off row likewise until its retry time. Neither reorders or re-weights any other row. openai-auth's `selectStickyCandidate` has no such inputs (its request path filtered rate-limited fallbacks before calling it), so both inputs, and their exclusion semantics in both modes, are new. Stage-1 gates in precedence: (1) API-key rows are admitted without quota; (2) no projected entry for the scope → `needs-first-reading`; (3) a required label with no entry → `unknown-window`; (4) a reading at or above 100% whose reset is missing, unparsable or not after `now` → `unknown-reset`; (5) a reading at or above 100% with a future reset → `exhausted`. Gates 4 and 5 judge every projected limit, including a third window. Gate 4 judges only exhausted-looking readings (library decision: a reading below 100% is admitted whatever its reset says), and it deliberately diverges from openai-auth, whose admission failed open on a passed window reset: the library refuses and requests a reading. Gates 2 to 4 request a pull: `requestPull(id)` is called synchronously, never awaited, once per refusal, and the refusal is returned without waiting. Every call evaluates every candidate, so a caller that fires a real pull from this callback should dedupe pulls already in flight. Stage 2: a survivor whose budget is spent (`budgetExhaustedResetAt`) is refused as `budget-spent` unless every survivor is spent, in which case all are kept with `lastPath: true`. API-key rows are survivors, a stage-1 refusal never counts as a path, and there is no last-path exception at any stage-1 gate. The budget signal ignores staleness, as openai-auth's `isQuotaExhausted` does.

**Ordered.** `routing.mode` absent or unrecognised resolves to `ordered` in roster order, where legacy readers defaulted to `main-first`; the persisted value is never rewritten. `main-first` and `fallback-first` place the row named by `formerMainId` (default `main`) first or last when that row exists. The follow-up supplies the recorded former-main id; nothing here reads `commonAuthPool`. The retry statuses have no default and are always the caller's.

**Sticky-balanced.** The primitives are openai-auth's, judged over the projection. Selection weight and the break decision judge **every** reading in the projection: each window's weight is its spendable percent over the hours to its reset, the account's weight is its most constrained window (and the credit budget), and the break decision migrates on any spent reading, naming the longest when several are spent. openai-auth judged two fixed slots; the library's `STICKY_WINDOW_SLOTS` export (2) was removed with that limit, because with three independent windows (a short window beside a general and a family week) the two weekly readings filled both slots and a nearly spent short window weighed nothing (pinned by `a nearly spent short window outweighs two healthy weekly windows` and `a spent third window drives the break decision`). openai-auth stores at most two readings, both `all`, so its weights and decisions are unchanged. `decideStickyBreak` reports `window: { scope, label }` instead of openai-auth's `windowKey`, and takes the status classification from the adapter (`classifyStatus`), defaulting to openai-auth's rule, so a provider whose 403 can mean an organisation or model policy rather than a dead account does not migrate the session as permanently failed (pinned by `an adapter status classifier keeps a policy 403 on its row`; a non-permanent class still migrates off a spent window). A classifier sees only the status; a provider that tells policy from account failure by the response body decides that before the call and passes a classifier closed over its verdict. `routeSticky` dispatches a valid pin whose row is admitted and not killed. Otherwise it runs selection over the non-excluded rows, drops each selected row that admission refused, and re-runs until a row is admitted or none is left (`no-admissible-account`). Reserves are per window label: `reservePercent` applies to every row, and since 0.2.3 `rowReservePercent` (a map by row id, or a function of the row) replaces it for each row it returns a value for, so a plugin whose reserves are per account (openai-auth's killswitch thresholds) weighs each row by its own. Under the default `refusedPinPolicy: 'keep'` a valid pin is always `retain`: a pin whose row is refused (quota turned unknown or exhausted), excluded or killed is routed around, not deleted, and the caller's break decision governs clearing it. Under `'move-on-confirmed-exhaustion'` (since 0.2.3, openai-auth's behaviour) the pin is reassigned (`assign`) to the row this request is dispatched to when its own row was refused `exhausted` or `budget-spent`, or killed by the killswitch; a refusal for unknown quota (`needs-first-reading`, `unknown-window`, `unknown-reset`) and an exclusion keep it (`retain`) while the request is served elsewhere, and with nothing admissible a valid pin is retained under either policy. An invalid pin, meaning its row id is not among the rows passed in or both it and the row carry known identities that differ, is replaced (`assign`, carrying the row's current identity) or `clear`ed when nothing is admissible. An unknown identity on either side keeps the pin. Pins, pending bytes and assignment maps are never written to either store file by this subpath.

**Native policy that stays in the adapter.** Each of the following was considered for a new library option or hook; none is needed, because the adapter already controls the input that decides it, and each is provider policy the library must not encode.

- *API-key admission.* Admission's first gate admits an API-key row without consulting quota, and an admitted API-key row counts as a surviving path, so a spent OAuth budget beside it is refused rather than kept as the last path. A provider whose paid fallback may serve only after fresh, confirmed exhaustion of the general OAuth windows decides that before routing: it runs `admit` over its OAuth rows alone (scope `all`, its required labels) and adds the API-key rows to the rows it routes, ordered, sticky or reactive (`nextOrderedAttempt` walks only the order it was given), only when every OAuth row was refused `exhausted` on an `all` window whose reading it judges fresh (`projectQuota` gives each limit's `checkedAt`). Model-only exhaustion, `unknown-*` refusals, token failures and an empty OAuth pool then never open the paid path.
- *Short-reset holds.* Exclusions (`rateLimitMarks`, `refreshBackoff`) route a request around a pin while keeping the pin record. A provider that instead holds the session on its row through a short window's reset decides that before calling `routeSticky`: it checks that no longer or scoped window on the pinned row is spent (gate 5 reports the longest spent window first), waits within its own bound, and dispatches to the pinned row itself. After the reset passes, a stored 100% reading with a passed reset is refused `unknown-reset` with a pull, so the adapter records the next reading before routing through the library again; a retry estimate comes from the resets in the projection.
- *Model-change pin invalidation.* `StickyPin` carries no model. The pin is caller-held, so the adapter clears it, and anything it derives from it such as a preferred keepalive route, when the user-selected model changes (within a family too), keeps it through its own internal recovery, and calls `routeSticky` without a pin to get a fresh `assign`. What counts as a model change is the provider's decision, so a model field on the pin would encode policy.
- *Extra usage versus the budget.* The budget axis has openai-auth's semantics: a reached budget is refused unless every survivor is spent (the last path), and its remaining percent weighs placement. A provider's paid overflow allowance is not that unless its billing rules say so; by default it stays out of the quota map, and any billing eligibility it gates is applied by the adapter when it chooses rows.
- *Status and refusal classification.* `classifyStatus` (above) is the seam for a 403 that is not an account failure. A model safety refusal inside a successful response is not a status at all: the adapter does not call `decideStickyBreak` for it. A provider that reports rounded utilisation stores the figure it was given (`usedPercent` is fractional); 99.5% is not 100% and admission does not treat it as spent.

Admission itself is a pure function in the `/routing` subpath over rows the caller passes in; `/store` supplies the rows (`PoolRow.quota` is the codec's opaque map) and `requestReading` is how a refusal fires the pull.

**Lock-free validated reads (0.12.0).** Every pool snapshot reads config bytes, then state bytes, then config bytes again. If the config changed, the reader discards the pair and retries, at most three attempts; continued churn returns `snapshot-contended`, `retryable: true`, with the fixed message `The store was changing; retry the operation once writes settle.` Readers and lock-key pre-reads share this classification; parse/load errors remain non-retryable. Attempts yield for a jittered 2–5 ms before the next attempt, never taking a lock. Readers take no locks and never write. In particular, a read that captured the old roster before publication cannot pair it with state after removed credentials were cleaned away. Tests park the first config read while publication and cleanup finish to exercise that exact interleaving, and separately force all three attempts to change. This byte check is a best-effort race detector, **not a correctness fence**: an ABA sequence such as reorder → state-only rotate → reorder back can restore identical config bytes and let a pair be accepted. It does not prove a generation-consistent snapshot against every writer. Publication receipts and their correctness rely on the store locks, stamps, permanent plan digest and ordered durability barriers, not on this lock-free check.

**Reserved secrets and refusal ordering (0.12.0).** All add modes scan state-only staged orphans for the same secret under another id; a hit refuses `row-staged` before writes or repair, and the owner can still replay the original id exactly. For `onExisting: 'refuse'`, this staged-orphan refusal used to be `credential-exists`; callers must now handle `row-staged` as a reservation, not an ordinary duplicate. A rotating add checks the store-owned staging marker of the exact account whose credential it is about to update. An earlier account with the same secret but an invalid entry (for example epoch zero) is not selected for rotation, so checking only that earlier account would miss the reserved account actually selected. Enable/disable decide attribution, identity quarantine, duplicate-identity and provider-state mutator refusals on the completed projection before repairing any row. Only an accepted call repairs interrupted writes. `add` likewise plans the endpoint, provider-state merge and full stamped account, and decides occupied/invalid ids, binding, type, identity and epoch exhaustion on the projection before any repair. A fenced enable/disable whose target is itself torn is pinned against an already-completed control: credential epoch, binding, full state account and provider-state stamp remain the same for replacements and pending transitions. A reserved pull capture exits before even pool-wide repair, and quota recording refuses the reserved row without writing, even when the row is enabled-shaped or has no valid entry.

#### Staged replacement (0.12.0)

Prepare fresh ids with `add` using `onExisting: 'refuse'` (no held secret accepted) or `'stage-duplicate'` (the same secret may be staged beside an old holder), plus both `disabled` and `stage`. A `stage` with omitted or explicit `'rotate'` refuses `invalid-input` before locks or writes: staging requires one of the two non-rotating modes explicitly. `'stage-duplicate'` also refuses a `disabled` without `stage`; an ordinary disabled add without `stage` stays allowed under `'refuse'` or `'rotate'`. Preparation never rotates an old holder and does no torn repair or pull capture that might repair an old row. The first, state-first write puts a store-owned replay record in the credential stamp: `staged: {reservation, label?, disabledReason, providerState?}`. `label` is raw, absence included; `providerState` is SHA-256 of the **full canonical encoded provider state**, not merely `credentialBound`, and is absent only when the add had none. Parsing rejects unknown staged-record keys, wrong types and empty reservations. The following config write records `staged: {reservation}` in the per-row entry and the disabled flag/reason.

After a crash, repeat the exact staged add. Ownership requires the id, type, label (including absence), secret, full dispatch material (OAuth access/expiry; API trimmed endpoint/effective header), exact identity including absence, full canonical provider state, stamp reservation and disabled reason to agree. An orphan is verified by loading its stored material against its stamped descriptor, not by trusting public status or a caller's desired reservation. Complete rows must also have the same config marker. A proved orphan completes with a config-only write and returns its stored epoch; a complete replay returns `exists` without writing. No missing marker is synthesized.

A config reservation, or a state-only orphan's stamp reservation, reserves the row until publication. Every credential/identity/quota/provider-state writer and plain deduplicating add refuses it; only exactly fenced removal may delete it. Readers never make it a candidate, even when another writer enabled its on-disk roster shape. Older library/plugin writers do not enforce this rule: staged replacement requires all writers to adopt the new store.

Pass the complete final roster order to `publishRoster`. Under all locks it checks removed rows exist, their stored credentials match their stamps, no interrupted write needs completion, no staging marker reserves them, and their epoch and recorded identity exactly equal the supplied attribution; optional fingerprints must match their current secrets. Finalized rows must be disabled and carry the exact config **and** stamp reservation, and their attribution must match. The stamp's original label, disabled reason and full canonical provider-state hash must still match the files, including absence. Enabled finalizations forbid a reason; disabled ones require it. Duplicate string ids in the raw roster are refused. The order must name exactly the valid named surviving roster descriptors, without repeats or unknown ids; unnamed and invalid descriptors are carried separately. Any surviving row with an interrupted credential or transition write refuses `attribution`, **non-retryable**, naming the row and directing a normal store operation to complete it first; publication does no repair. Unnamed rows and invalid roster descriptors do not enter the order bijection or become candidates: their parsed contents are carried verbatim after ordered survivors, in their original relative order. Duplicate named ids still refuse. A valid roster descriptor with an invalid per-row entry retains its ordinary roster position in the order. No two final enabled OAuth rows may share a known identity. No two rows in the resulting pool, including untouched survivors and disabled finalized rows, may share a secret under different known identities; a finalized secret that is also removed cannot claim a different known identity either. Absent identities are never normalized or collisions. Rows outside the plan keep their roster fields, entry and state, apart from position. Then publication calls its protect hook.

The publication's single durable config rename removes old roster/entry records, retires their epochs, clears finalized config markers and writes their flags/reasons, applies the order and records `commonAuthPool.publications[operationId]` with phase `committed`. This is the only irreversible decision. Cleanup uses only that receipt's references: one durable state write drops matching removed epochs and clears the finalized stamps' whole staged records without unbinding credentials, then a durable config write advances the receipt to `cleaned`. Cleanup checks the receipt's stored row ids and epochs, plus each finalized reservation. It never deletes a credential written later at another epoch or clears another operation's staged stamp just because the same local id appears in the old receipt. Re-running a committed receipt with the same digest first fsyncs the visible config file and its directory, then finishes cleanup without plan re-validation and returns `cleaned`; an equal cleaned receipt returns `already-cleaned` without writes. A different digest refuses `publication-mismatch`. Query `publication()` after any failure. **Every full receipt is retained forever**, committed or cleaned, with its genuine reference epochs: the receipt is the permanent operation-id/digest fence. No separate tombstone or completion-order list is needed, and no receipt is compacted. Publications are rare user-driven replacements, so this small history's growth is negligible; never reuse an operation id for another plan. The committed-receipt preservation test is a regression pin of behavior that was already correct, not a red-first defect fix; its mutation explicitly deletes a committed receipt to prove the pin fails.

**Digest definition.** `planDigest` is lowercase hexadecimal SHA-256 of the UTF-8 canonical JSON serialization of the full plan: JSON round-trip encoding (undefined object members omitted), object keys sorted recursively by JavaScript's default string sort, no insignificant whitespace, array order preserved. The full encoded provider-state digest uses the same canonicalization. Credential lineage and dispatch digests keep their existing definitions.

**Locks and durability.** Publication takes every named row's `rowLockKey`, deduplicated and sorted, then `options.providerLock ?? rt.providerLock`, then extra locks, then store locks. It recomputes keys under store locks and releases/retries once if any changed, refusing `row-key-changed` on the second change. This is the only multi-row-lock operation. A refresh acquires one row lock before its provider lock and never waits for another row while holding that provider lock. Publication acquires its entire sorted row set before requesting the provider lock. Consequently publication cannot hold the provider lock while waiting for a row owned by refresh, and refresh cannot hold the provider lock while waiting for a second row owned by publication. Every rename asserts every lease, and cleanup also asserts them before editing/writing state. `writeJsonAtomic({durable:true})` fsyncs the temp file before rename and the parent directory after rename. Before the durable roster decision, publication fsyncs the existing state file and its directory, making staged credentials durable before the old rows can be durably gone. The publication rename then syncs config temp file → config rename → config directory. Cleanup syncs state temp file → state rename → state directory **before** the cleaned receipt's config temp file → config rename → config directory. A visible committed receipt is re-synced (config file → config directory) before any recovery cleanup write. Failure of any barrier stops the next irreversible write. A sync failure before the decision is `publication-sync`, retryable, with nothing written to the pool. Once the decision rename landed, or a matching committed receipt was loaded, failures are `publication-incomplete`, retryable, with fixed guidance to replay the **same plan** or check `publication(operationId)`. This includes the decision directory sync, committed-config resync, cleanup-state sync and cleaned-receipt sync. Failure phases count writes made in the current call, so committed-receipt recovery can report `before-first-write` while its kind correctly signals the earlier decision. Ordinary writes and staged preparation remain atomic-rename-only; publication supplies their required durability barrier. Process crashes recover through stamps/receipts as above. A before-config-write observer or lost lease refuses before the publication rename; removed ids enter process memory only after a successful rename, so an aborted removal does not poison later adds. An after-config-write observer failure leaves the committed receipt and can only resume forward.

**Schema.** `commonAuthPool` is one top-level key of the config file holding `schemaVersion: 1` and `rows`, a map keyed by local id. An entry holds `credentialEpoch` (an integer from 1 to `Number.MAX_SAFE_INTEGER`; since 0.4.1 an epoch outside that range makes the entry malformed, so the row is invalid and never a candidate, because past it adding one can give back the same number and a replace would not move the epoch), `needsFirstReading`, `disabledReason` and the codec's `quota` map; every other sub-key of the pool and of an entry is preserved. The recorded wire identity lives in the legacy roster row's `accountId`, which the older normaliser round-trips. Every config write emits `version: 1` and the legacy-shaped `accounts` array (id, label, type, addedAt, accountId, enabled, and baseURL/authHeader for api rows), never `mainAccountId`, and keeps every other top-level key. Credentials stay in the state file under the older field names (`access`, `refresh`, `expires`, `lastRefreshedAt`, `apiKey`); unknown state keys survive. Both files go through `writeJsonAtomic`. A missing config is an empty pool; a config with no `accounts` is an empty roster; `accounts` without `commonAuthPool` is pending migration; malformed JSON, a non-object root, a non-array `accounts`, a malformed `commonAuthPool` or `rows`, a newer `schemaVersion`, and a malformed or non-object state file (or a non-object state `accounts`) are load errors. Pending migration and load errors refuse every write, bytes unchanged. A roster row the older normaliser rejects, a second row with an already-seen id, and a malformed entry are row-level: never candidates, preserved verbatim. A pool created here carries `commonAuthPool` with no migration marker; the migration work must treat key-present/marker-absent as a pool to import into.

**Credential stamps and torn rows (since 0.3.1).** Every credential the store writes to the state file carries, in the same account entry, `commonAuthPool: {credentialEpoch, digest, dispatch, binding, replace?}`: the credential epoch the credential belongs to, a SHA-256 digest of its secret (refresh token or API key) under a prefix of its own (so it is not the dedupe fingerprint), the dispatch digest (since 0.4.4, see *Dispatch digest and complete bindings*), and the `binding` (`identity` when known, and `baseURL`/`authHeader` for an API key): for `replace` the config it is about to write, marked `replace: true`; for every other write (since 0.4.4) the row's config as it stands when the credential is written. Up to 0.4.3 only `replace` wrote a binding and no write wrote `dispatch` or `replace`. `replace` and `add` write the state file first. A row whose stamp is well formed, is a replace's (it carries `replace: true`, or, written by 0.4.3 or earlier, a binding and no dispatch digest), matches the credential beside it by digest, and names an epoch above the config's (a row without an entry is at epoch 1) is torn: a `replace` stopped between its writes. Every reader (`load`, `read`, every operation's re-read) shows a torn row as that replace leaves it once completed (the stamped identity or endpoint and epoch beside the stamped credential, quota dropped, needs-first-reading set, later rows sharing the identity disabled), marks it `torn: true`, and never makes it a candidate. Every row write (`add`, `replace`, `rotate`, `disable`, `enable`, `remove`, `recordIdentity`, a refresh, a pull's capture) first writes the config of every torn row to match its stamp, in one config write of its own counted as setup (a later refusal still reports `before-first-write`); `recordQuota` and `reorder` never do, and `recordQuota` refuses a torn row. `load()` fires the pull of an enabled torn OAuth row, so it heals at the next load when a pull hook is set; an API-key row heals at its next row write. A state entry without a stamp (written by 0.3.0 or earlier, or by an older writer that rebuilds state entries), with a malformed stamp (since 0.4.1 that includes an epoch outside the safe integer range), with a stamp whose digest does not match the credential beside it (another writer put the credential there), or with a stamp at or behind the config's epoch loads exactly as before.

**Stamp status and strict stamps (since 0.4.3).** Every loaded row carries `stamp: 'none' | 'bound' | 'missing' | 'malformed' | 'mismatched'` (since 0.4.4 also `'legacy'`, and `bound` also requires the dispatch digest; see below) (typed optional on `PoolRow` only so rows built by hand, such as openai-auth's test fixtures, still type; the store always sets it). `none`: no credential is loaded for the row (an invalid roster row is `none` too). `bound`: the stamp parses, its digest is the loaded credential's, its epoch is the row's `credentialEpoch` (1 without an entry), and a binding it carries agrees with the row: a bound `identity` equals the roster `accountId`, a bound `baseURL`/`authHeader` equals the API-key row's endpoint; a binding without an identity (a `replace` that named none) is not contradicted by an identity recorded later for the same epoch (in 0.4.3; since 0.4.4 the identity must match exactly, see below). `missing`: a credential with no stamp key. `malformed`: a stamp this store would not write (wrong shape, or an epoch outside the positive safe integers). `mismatched`: the digest, epoch or binding disagrees. A torn row reports the stamp of the row as it is shown completed, so it is `bound` and still `torn`, never a candidate until the completion is written. With the option unset nothing else changes: candidacy and every operation are as in 0.4.2, and `stamp` is the only new field. `openPoolStore({ requireCredentialStamps: true })` makes the store refuse what it did not stamp: a row whose `stamp` is not `bound` loads `unbound: true` and `candidate: false` (the new `unbound` field is the stated reason; it is never set with the option off), `load()` fires no pull for it, and `refresh`, a pull (reported to `onPullFailure`), `recordQuota`, `recordIdentity` and `rotate` refuse it with the new failure kind `unbound-credential` (not retryable; phase `before-first-write`, or `pull` for pulls and `recordQuota`) before any provider call or write. The check runs on every locked read the operation makes: a refresh checks at its locked capture (before giving a row without an entry its entry) and again at commit after the provider call, because a credential another writer swaps in under the same epoch passes the epoch-and-identity attribution fence; a pull checks at its capture and again when `recordQuota` records the reading; `rotate` and `recordIdentity` check at their locked re-read, after any lock wait. Where an operation already needs a credential, a credential-less row keeps its earlier refusal (`no-credential` from `refresh` and `recordQuota`); `rotate`, `recordIdentity` and `add` refuse it with `unbound-credential`. **No healing:** nothing but `replace` makes an unbound row bound. `rotate` and `refresh` keep the row's epoch, identity, quota and runtime fields, the very record that is unproved, so they refuse rather than stamp it. `replace` (any credential the caller supplies, with the binding it names) advances the epoch, sets or clears the identity, drops the quota and sets needs-first-reading exactly as it always has, and the row is then `bound`. Library decision for `add`: a fingerprint-equal re-add of an unbound row's secret, and an `add` that would complete a credential-less roster row under its id, refuse with `unbound-credential` instead of rotating or completing it, since both paths keep the row's epoch, identity and quota and the re-added secret is exactly what is unproved; the caller replaces the row, which keeps the epoch move and the dropped readings visible. An `add` of a new secret under a new id is unaffected. An interrupted `replace` under strict mode is the existing torn row: its new credential is stamped and binds the completed row, it loads torn and not a candidate, and the existing forward completion (any row write, or the pull `load()` fires) completes it to a bound candidate. Only a replace's stamp that parses, matches the credential's digest and is ahead of the config's epoch is torn; any other stamp ahead (written by `add`, `rotate` or a refresh, or one with no binding) or a stamp beside another credential is `mismatched` (or `malformed`, see below) and is never completed. Rows that are unbound still count for identity dedupe as before (an earlier unbound row holding an identity keeps a later row with that identity disabled).

**Dispatch digest and complete bindings (since 0.4.4).** In 0.4.3 a stamp was `bound` while its lineage `digest` (refresh token or API key only) matched, so another writer that swapped only an OAuth access token, or changed only an API row's `baseURL`/`authHeader` or a row's `accountId` in the config, left the row `bound` and admitted under strict mode; only `replace` wrote a binding, so a row stamped by `add`, `rotate` or a refresh had no identity or endpoint bound at all (a rotate even dropped the binding a replace wrote), and an identity learnt by `recordIdentity` was never bound. Four changes close that. (1) Every stamp carries `dispatch`, a SHA-256 over everything a request sends or is served by, under its own input prefix (`credential-dispatch`), so it never equals the fingerprint or `digest`: the OAuth access token, refresh token and `expires` (the expiry decides whether the access token is used or refreshed first; an access token or expiry the state file cannot hold counts as absent, as the loader reads it); the API key, its trimmed `baseURL` and its `authHeader`. `digest` keeps its exact 0.4.3 definition: it is the lineage value torn detection matches, including against stamps older versions wrote, and redefining it would stop a torn replace an older version wrote from being recognised and completed. The fingerprint is unchanged too. (2) Every stamp write carries a complete binding: `replace` passes the binding it is about to write; every other write (`add`, a re-`add` that rotates, `rotate`, a refresh) binds the row's config as it stands in the transaction when the credential is written (its recorded identity, an API row's endpoint), plus the identity the same operation is about to record. (3) The identity is bound exactly: for a stamp with `dispatch`, the binding's identity, or its naming none, must equal the roster `accountId`; an identity-less binding no longer accepts a later identity. Every write that gives a row an identity writes the stamp naming it first and the config second: `recordIdentity` on a bound row restamps the unchanged credential with the identity (same epoch, one state write), then records it in the config (one config write), so it is now two writes; a `rotate` or refresh that learns the first identity stamps it in the rotated credential's binding before its config write. So this store never leaves a config identity beside a stamp that names none or another, and that shape is `mismatched`: another writer's doing. The reverse shape, a stamp at the row's epoch that matches the credential beside it by `digest` and `dispatch` and names an identity the config does not record, is such a write stopped between its writes: every reader shows the row with that identity, `torn: true` and no candidate (stamp `bound`), and the next store write on it (or the pull `load()` fires) records the identity in the config, disabling later rows sharing it, exactly as `recordIdentity` would. A row whose stamp is not `bound` (default mode only; strict refuses `recordIdentity` on it) gets no new stamp from `recordIdentity`: its identity is recorded in the config only, as before, and the row stays as unproved as it was. (4) `bound` requires `dispatch` present and equal to the loaded row's. A well-formed stamp with no `dispatch` whose digest matches (written by 0.4.3 or earlier) is the new status `legacy`, whatever its epoch or binding says, since it proves neither the token sent nor the account: strict mode refuses it like every non-`bound` status (recovery is `replace`, as for any unbound row), and default mode loads and routes it as before; a default-mode `rotate` or refresh rewrites it with a dispatch digest and binding. Adopters turning on strict mode after upgrading from 0.4.3 therefore see every row stamped by 0.4.3 as `legacy` until it is refreshed or rotated in default mode, or replaced. A stamp carrying `dispatch` or `replace` but no binding, a non-string `dispatch`, or a `replace` other than `true` is `malformed`. Torn replace detection keeps its rule (a replace's stamp, matched by `digest`, ahead of the config's epoch); because every stamp now has a binding, "has a binding" no longer means "written by replace", so a 0.4.4 replace marks its stamp `replace: true` and only such a stamp, or a 0.4.3-shaped one with a binding (only a 0.4.3 replace wrote one), is completed as a replace. A torn replace written by 0.4.3 is completed forward by a store without `requireCredentialStamps`, as before, and once completed loads `legacy`; a strict store does not complete it, in its reads or its writes, so it loads as on disk (the old epoch and identity beside the new credential), `legacy`, unbound and no candidate, and strict mode never shows it bound. Older readers (0.4.3 and earlier) ignore `dispatch` and `replace` and still read the binding identity-leniently; they would treat a 0.4.4 non-replace stamp sitting ahead of the config's epoch, which only a foreign epoch rollback produces, as torn.

**Strict completion of a torn replace checks the dispatch digest (since 0.4.5).** In 0.4.4 a replace's stamp ahead of the config's epoch was completed on its lineage `digest` (refresh token or API key) and, under `requireCredentialStamps`, the mere presence of a `dispatch` digest. Another writer that changed only the access token or `expires` beside an interrupted replace's credential left a row that loaded `mismatched` and unbound, yet every strict row write (a refresh or a pull's capture included) first wrote the replace's completion into the config (new epoch, the stamped identity, quota dropped) and only then refused the row with `unbound-credential`: no provider call, but the config moved on a stamp that did not describe the credential. Since 0.4.5 a strict store completes a replace's stamp only when its `dispatch` equals the dispatch digest of the projected replacement: the credential loaded beside the stamp, with an API key's `baseURL` and `authHeader` taken from the stamp's binding rather than the config (a replace that moves a key to a new endpoint leaves the old endpoint in the config until its config write, so comparing against the config's would refuse every legitimate torn API replace); an OAuth credential is projected as loaded (access token, refresh token, expiry). Otherwise the row is not completed, in reads or writes: it loads as on disk (old epoch, identity, quota and endpoint beside the new credential), `mismatched`, unbound and no candidate, `refresh`, a pull, `recordQuota`, `recordIdentity` and `rotate` refuse it with the config byte for byte unchanged and no provider call, and no store write (`disable`, `enable` and the rest included) completes it; recovery is `replace`, as for any unbound row. An untouched interrupted replace still loads torn and `bound` and is completed forward by the next write, an API replace to a new endpoint included. A store without `requireCredentialStamps` keeps its 0.4.4 rule and never compares the dispatch digest when completing a replace: such a row is still shown completed and `torn`, and the next write still completes it (it then loads `mismatched`, as the dispatch digest disagrees). Every other strict path was checked for a write ahead of its `requireBound` check: completing a row whose identity was stamped but not yet recorded already requires the stamp's `dispatch` to equal the loaded credential's (and moves nothing but the identity); a refresh's or pull's entry materialisation runs after the check; `rotate`, `recordIdentity` and `add` check before their first write; `recordQuota` and `reorder` never complete torn rows. Completion of torn rows is pool-wide (a write on one row completes every torn row), so the guard also keeps an operation on another row from completing the corrupted one.

**Provider state (since 0.6.0).** A plugin may keep its own per-row state beside each credential: what belongs to the account the credential signs in to (antigravity-auth: the Google project id, the managed project id, the device fingerprint and its history, eligibility times) and what only tracks its use (cooldowns, cursors). It passes `providerState: ProviderStateCodec` to `openPoolStore`; the store never interprets the value. *The seam.* `validate(value)` is asked before every write and on every load. `credentialBound?(value)` projects the part that belongs to the credential (pure, JSON with a deterministic key order; without it the whole value is credential-bound). `merge?(onDisk, incoming)` combines the stored value with one a credential write brings (a re-`add` of the secret a row holds, `rotate`, a refresh whose provider returned `providerState`); it is called only when the row shows a value, and without it the incoming value wins. `onReplace?(previous, {id, credentialEpoch, previousIdentity?, identity?, incoming?})` decides the value after a `replace`: `previousIdentity` is the identity the locked row recorded before the replace, and `identity` is the incoming one; each is omitted when absent. Neither the whole row nor its credential is passed. Every hook is synchronous and runs under the store locks; each result is validated, and a value is stored as its JSON round trip (`invalid-provider-state` when it is not JSON or the codec rejects it, `invalid-input` when the store has no codec), refused before anything is written. *Where it is stored.* In the state file, in the row's account entry under `commonAuthProviderState`, beside the credential. That is the only place it can change in the same atomic file write as the credential: every write that changes both (`add`, `replace`, `rotate`, a refresh) writes the value, the credential and the stamp in its one state write, so no reader, and no crash at any write point, ever pairs a credential with the other credential's value. A torn `replace` (stopped after its state write) is shown completed with the new credential and the new value; stopped before it, the old credential and the old value. The config entry was not used: it is written in a separate file write, so a torn replace would show the new credential beside the old value. A sidecar file would race the store locks and lose the crash guarantees. Older readers ignore the key. *Binding rule.* The stamp beside the credential carries `providerState`, a SHA-256 of the credential-bound projection under its own prefix (`provider-state`). `digest` and `dispatch` keep their definitions and the stamp status never depends on `providerState`; a row without provider state gets a stamp without the field, byte for byte what 0.5.0 wrote. A row shows `providerState` only when the stamp beside its credential carries the field, matches the credential by lineage `digest`, names the row's credential epoch (1 without an entry) and its recorded identity exactly, the codec accepts the value, and the projection of the value has the stamped digest. So a reader serving a credential reads, in one state-file read, a credential-bound part bound to that row's exact credential, epoch and identity. A foreign edit of the bound part, a credential swapped by a writer that does not know stamps, a config that moved to another epoch or identity, or a stamp written by 0.5.0 (which names no provider state) leaves the value hidden: the row shows `providerStateDropped: 'uncovered'`. A covered value the codec rejects, or any value read by a store opened without a codec, shows `providerStateDropped: 'invalid'`. A dropped value is kept on disk untouched and the row stays usable (candidacy, `invalid` and `stamp` are unchanged): the value is the plugin's derived data, which it can rebuild by setting a new one, and marking the row invalid as a malformed quota map does would take a working credential out of rotation and leave `remove` as the only way out, since `replace` refuses invalid rows. The part outside the projection is not covered and may change through `updateProviderState` without the stamp being rewritten; a foreign edit of that part is not detected, by design. *Writes.* `add` writes the value given (a new row, or completing a credential-less one) or merges it (a re-`add` that rotates); `rotate` and a refresh merge a given value, and without one keep the row's value, carrying the stamp's digest forward only when the old stamp bound it to the row as it stood (same lineage, epoch and identity), so a hidden value stays hidden rather than being vouched for. `recordIdentity`, and a `rotate` or refresh that learns the first identity, keep the value bound to the identity now recorded. `disable`, `enable` and `reorder` do not touch it. *Replace policy.* `replace` moves the row to a new epoch, so the old value never carries over by default: the new value is what `onReplace(previous, ...)` returns (`previous` is the old shown value, undefined when none; returning undefined clears), and without that hook the `providerState` passed to `replace`, else nothing (the key and the stamp's digest are both removed). An `onReplace` that throws or returns a rejected value fails the replace before anything is written. *Fences.* `updateProviderState(id, {credentialEpoch, identity?}, mutator)` takes the row lock, runs the mutator on a copy under the store locks, and refuses (`attribution`, retryable, nothing written) when the row is no longer at that epoch or identity, so a writer that read the row before a `replace` or `recordIdentity` cannot land a value on it. A refresh commits its provider's value under its existing commit fence (epoch, identity, stamp). `remove` drops the row's whole account entry, value included; every later write naming the id refuses (`unknown-row`, and `add` `id-removed` in the same process), and an `add` of the id from another process drops any state entry an interrupted removal left before writing, so no stale writer brings a removed row's value back. *Strict stamps.* With `requireCredentialStamps`, an unbound row refuses `updateProviderState` (`unbound-credential`), as `rotate`, `recordIdentity`, `recordQuota` and `refresh` already do. Without it, `updateProviderState` still refuses (`unbound-credential`) a row whose stamp was not written by this store with this credential at the row's epoch and identity: no stamp could bind the value, so no reader would show it, and writing a fresh stamp would vouch for a credential the store never proved; `rotate` or `replace` stamps such a row. *What differs from the plugins.* None of them had a pool; antigravity-auth keeps these fields on its own account records and moves them here.

**Strict interrupted-add and transition recovery (since 0.11.3).** With `requireCredentialStamps`, a state-only orphan left by an interrupted `add` is completed only when the store can bind its stored material at the expected new-row epoch and compare it with the replay: the secret, OAuth access token and expiry, a supplied identity, and an API key's complete trimmed `baseURL` and effective `authHeader`. Missing, malformed, legacy or mismatched stamps refuse with existing `PoolOperationError` kind `unbound-credential` (not retryable, `before-first-write`), before any file write or unrelated torn-row repair. A matching replay returns `added` (or the existing duplicate-identity `added-disabled`), retains the stamped identity when omitted, and writes only the config, preserving the credential, stamp and any covered provider state byte for byte. Covered provider state must still validate and match its stamp; a supplied value must have the same credential-bound digest. `remove(id)` already discards a state-only orphan as `completed`, under the row lock, extra locks, then store locks; a subsequent add can use new material. Add's lock order is unchanged (row, provider-wide for OAuth, extras, store), and non-strict replay still overwrites an orphan as before. No consumer decodes the private stamp. Strict completion of a pending stamped transition (including a contradicted refresh's quarantine) also requires `dispatch` to match the loaded credential, in addition to lineage, epoch and identity. An access-token-only or expiry-only edit, or a missing dispatch digest, leaves the row as on disk, unbound and never a candidate; credential-preserving operations refuse with existing `unbound-credential` without repairing the config or changing file bytes. Unchanged dispatch still completes the transition forward, and non-strict completion retains its previous behavior. These rules add no exported union member.

**Attributed replace and rotate.** Both accept optional `attribution: {credentialEpoch, identity?}` in `RowWriteOptions` (which extends `RowOperationOptions`; `add` and `recordIdentity` keep their existing options). A fence compares the epoch and exact recorded identity under the row and store locks, before any write or `onReplace` hook; an absent identity matches only a row recording none. A mismatch refuses `attribution` (retryable, nothing written, `onFailure` awaited); a removed id stays `unknown-row`. The lock order is unchanged: row, provider-wide when applicable, extra locks, store locks. For an interrupted replace, the fence compares the projected replacement every reader sees: a mismatch leaves even its pending config completion untouched, while a match completes it forward as before, including in strict mode. Without attribution the existing behavior is unchanged.

**Attributed disable and enable (since 0.7.0).** A provider refusal that means the account cannot serve (antigravity-auth's `ACCOUNT_INELIGIBLE`, or a permanent 401/403 a plugin acts on) has to record the provider state (an ineligibility time) and disable the row, both fenced on the credential that was refused; a verification that finds the account eligible again has to record that and enable the row, fenced the same way. In 0.6.0 `updateProviderState` was fenced but `disable` and `enable` were not, so a request served by credential A at epoch 1, whose 403 arrived after the row was replaced with credential B (epoch 2), had its state update refused but its `disable` land on the row now holding B; likewise a late enable from A's verification switched B back on after B had been disabled for its own refusal (antigravity-auth's verify flow probes a credential, then clears the access blocks and re-enables the account). Two separate calls could also interleave with other writers. *What a plugin supplies.* `disable(id, reason, options)` and `enable(id, options)` take the same two optional fields. `attribution: {credentialEpoch, identity?}` is the fence `recordQuota` and `updateProviderState` use (an identity left out means the row had none): another epoch or identity refuses with `attribution` (retryable) and nothing is written; an invalid entry refuses `invalid-row`, an epoch outside the positive safe integers `invalid-input`. `providerState: (current, row) => next | undefined | DECLINE_TRANSITION` runs under every lock in the same transaction, with the rules of `updateProviderState` (a private copy of the shown value, undefined clears it, codec validation, the stamp's provider-state digest rebound only when the credential-bound part moves, `no-credential` and `unbound-credential` refusals); it requires `attribution` and a codec (`invalid-input` otherwise). Returning `DECLINE_TRANSITION` (a `Symbol.for` value, since `undefined` already means clear) declines the whole call: nothing is written, the flag included, and the call resolves `{id, declined: true}`; this is how a late refusal steps aside for an eligibility recorded after the request it is about. `updateProviderState` has no transition to decline and refuses that value as not JSON (`invalid-provider-state`). *Disable and enable share one shape and one internal transition* rather than a new generic status operation: the two differ only in the flag they set and in `enable`'s duplicate-identity rule, which still applies before the mutator runs. Lock order is `updateProviderState`'s: row lock, `extraLocks`, store locks. A call with neither field is byte for byte what 0.6.0 did. *How the two land together.* The flag lives in the config and the value in the state file, so a transition that changes both is written as a replace is. The state write carries the new value and, in the credential stamp, `transition: {mark, enabled, reason?}` (`mark` a random UUID unique to the write); the config write then flips the row and records the mark in the entry as `transitionMark` (older readers ignore both keys). A stamp bound to the row (same lineage digest, epoch and recorded identity: the binding that also decides whether the value beside it is shown) whose mark the entry does not record is a transition stopped between its writes; every reader shows the row as the transition leaves it, beside the new value, marked `torn` and never a candidate, and the next store write completes it (an enable then applies the duplicate-identity rule, earlier row in roster order winning). So no reader, and no crash at any write point, sees the flag without the value or the value without the flag; once the stamp no longer binds the row (another epoch or identity), the value and the transition are hidden together. Once the entry records the mark the transition says nothing more, so a later plain `enable` or `disable` is never undone by it; a credential write replaces the stamp and drops it. When the config already says what the transition writes (an `enable` of an enabled row) only the value is written, in one state write and without a transition; when the value is unchanged only the config is written, as a plain call would. *Strict stamps.* With `requireCredentialStamps`, an attributed `disable` or `enable` without a mutator is allowed on an unbound row: disabling a credential the store cannot prove is safe, plain `disable` already does it, and an unbound row is never a candidate either way. With a mutator it refuses `unbound-credential` and writes nothing, as `updateProviderState` does: writing provider state for an unproved credential would vouch for it, and the call asked for both or neither. *What differs from each plugin.* antigravity-auth's `markAccountIneligible` and verify-then-`clearAccountAccessBlocks` become one attributed call each, with the eligibility fields in its provider state; openai-auth and anthropic-auth keep calling `disable`/`enable` without the options and see no change.

**Ids and dedupe.** Ids are stored verbatim; an empty id, an id with surrounding whitespace (older readers trim it) and prototype keys are refused as `invalid-input`. `disable` sets the roster row's `enabled: false` and the entry's `disabledReason`; `enable` sets `enabled: true` and drops the reason; only `remove` deletes a row. A removed id is remembered, like every id a library write drops, and `add` refuses it (`id-removed`) for the rest of the process. A crash between `remove`'s config and state writes leaves a pool from which every reader (this store and the older openai-auth reader, which ignores state entries without a roster row) has already lost the row, plus an orphaned state entry that a second `remove` of the id drops. Two enabled OAuth rows with one wire identity: the earlier in roster order stays enabled, later ones are disabled with `duplicate-identity`. The credential fingerprint (SHA-256 of the refresh token or API key) is computed on load, never persisted, and is only a dedupe key.

**Rows without an entry.** A roster row appended or stripped by an older writer loads as a candidate needing a first reading. Before a pull or refresh is issued for it, the store gives it an entry at `credentialEpoch: 1` in its own locked config write; there is no epoch-0 capture. `load()` rewrites nothing.

**Locks.** Order everywhere: row lock, provider-wide lock, extra locks (mapping order), store locks (config then state); release in reverse. The row lock is `row-<encodeURIComponent(key)>` beside the state file, where `key(row)` is the recorded identity when known, else the local id. The provider-wide lock is one `(name, path)` per provider, not keyed by identity; `add` and `replace` of an OAuth row, `recordIdentity`, `rotate` carrying an identity, and every refresh take it. `disable`, `enable` and `remove` take the row lock and extra locks but not the provider-wide lock, so a removal waits for a refresh of its row instead of landing during the provider call; a caller holding its own legacy locks around one of them passes those locks as `extraLocks` rather than holding them outside the call. `reorder` names no row and takes only its extra locks, then the store locks. Defaults (`POOL_LOCK_DEFAULTS`): ttlMs 10 000, timeoutMs 15 000, retry 50 ms plus up to 50 ms jitter, renew true; `renewIntervalMs` is optional; all overridable per store, per lock spec and for row locks. Each wait is bounded and ends in `lock-contention` wrapping `LockContentionError`. `assertOwned()` runs on every held lease after each acquisition, immediately before the provider call and immediately before each file rename; a lost lease fails `lock-ownership`, retryable. The store locks are never held across the provider call. A refresh whose row-lock key is stale at the locked re-read releases, retries once under the new key and aborts `row-key-changed` on a second change.

**Account-keyed refresh lock (supported since 0.4.2).** A plugin may pass its own `providerLock` to a single `refresh` call, keyed by the account being refreshed (anthropic-auth does this so different accounts refresh side by side), while `add`, `replace`, `recordIdentity` and `rotate` with an identity keep the provider-wide lock. The spec is fixed for the call: a refresh that re-keys at its locked re-read retries under the new row lock but the same override. Compared with a refresh under the default provider-wide lock, what still holds: a refresh's row lock is never re-keyed while it is held, because every identity change on a row takes that row's lock; a row's refresh token reaches the provider once; a rotation the provider has consumed is committed to its row even if that row was disabled as a duplicate while the call was in flight, or is disabled by the dedupe of its own commit, and the refresh never re-enables it; after each commit exactly one enabled OAuth row holds each identity, the earlier in roster order; an `add` given a known identity waits on that identity's row lock. What changes: refreshes of different accounts overlap, and an identity-changing operation on another row (an `add` of an unknown or not-yet-held identity, a `recordIdentity` on a row still keyed by its local id) no longer waits for the refresh, so it can land during the provider call and change which row the dedupe keeps; and an `add` of an unknown-identity row no longer waits for a running refresh. An override must not name a row lock (`row-…` beside the state file): lock files are not re-entrant, so the refresh waits on its own row lock until the override's `timeoutMs` and fails `lock-contention` without calling the provider.

**Failure value.** One `PoolOperationError {operation, rowId, phase, retryable, kind, committed?}`. `operation` is `initialize`, `add`, `replace`, `rotate`, `disable`, `enable`, `remove`, `reorder`, `updateSettings`, `recordIdentity`, `updateProviderState` (since 0.6.0), `refresh` or `pull` (`rowId` is absent for `initialize`, `reorder` and `updateSettings`); `phase` is `before-first-write`, `after-first-write` or `pull` (a provider failure is `before-first-write`, kind `provider`). `committed` is present only on `after-first-write` when the operation's state write had landed: since 0.3.1 every two-write operation except `remove` writes the state first, so a rotate, add or replace failing before its config write carries the credential it wrote (for a replace, the row is then torn). Nothing is rolled back. `add`, `replace`, `rotate`, `disable`, `enable`, `remove`, `recordIdentity` and `refresh` take `onFailure(rowId, error)`, and `reorder` takes `onFailure(error)`, each awaited once on every non-success path with the store locks released and the outer locks still held. Pull failures (a rejecting pull, a failed attribution) go to the store-level `onPullFailure`, phase `pull`, leaving needs-first-reading set and releasing the once-per-process load guard.

**Hooks.** A refresh's `onPersisted(rowId, credential)` runs once the rotation is persisted and the store locks released, before any extra or outer lock is released; there is none when attribution or persistence failed. If it throws, the caller gets kind `after-persist-hook`, phase `after-first-write`, with the committed credential; the commit stands, the provider is not called again and `onFailure` does not fire. Inside `onPersisted` and every `onFailure`, and in every timer, promise or continuation created inside them (async context is inherited), `add`, `replace`, `rotate`, `disable`, `enable`, `remove`, `reorder`, `recordIdentity`, `updateProviderState` and `refresh` reject at once with `PoolReentryError` before touching a lock. Reads and `recordQuota` are permitted. A hook that needs a row operation hands it to its caller's continuation after the operation returns. A throwing `onFailure` or `onPullFailure` is logged through `logger.warn` and swallowed.

**`refuse`.** `refuse(row) → reason | undefined | Promise<…>` is awaited before any lock, at the locked re-read and at commit time under the store locks; a reason returns `{status:'refused'}` and leaves the stored credential untouched, discarding rotated material. The row carries the stored credential including `refresh`.

**Refresh stamps.** A rotation's `lastRefreshedAt` is the injected clock at commit time, raised to one past a prior stamp that is still trusted (at most `now + 5 min`), so an older copy of the token never compares newer in the older writers' `applyNewerTokenState`; a prior stamp above the bound is ignored. When that floor would itself pass the bound (a prior stamp at exactly `now + 5 min`), the refresh refuses with `refresh-stamp-ahead`, retryable, before the provider call, and again at commit. `expires` is the provider's value verbatim.

**Attribution.** A pull or refresh captures the credential and `(id, credentialEpoch, identity)` in one read under the store locks and applies only if all three still match. `add` starts a new row at epoch 1 (since 0.8.0 one past the highest epoch its id held before, see the next paragraph), and the entry materialisation above starts a row without an entry at epoch 1; `replace` bumps it, sets identity to the given one or clears it, clears the quota map and sets needs-first-reading; `rotate` changes none of them. Learning a row's first identity and rotating a credential of the same known account are rotations; a credential of another known account is a replacement, so `rotate` and `recordIdentity` refuse an identity other than the recorded one (`identity-mismatch`) rather than relabel the row and keep its epoch, quota and errors. Identity learning is attributed like a reading: `recordIdentity` takes the credential epoch its lookup was issued for and refuses (`attribution`) when the row has been replaced since, so the first credential's account is never recorded beside the second credential. A refresh's identity write-back is already fenced by the epoch and identity it captured; a refresh that reports an identity other than a known one records nothing. Since 0.4.1 every epoch is a positive safe integer: a captured epoch passed to `recordIdentity` or `recordQuota` outside that range refuses (`invalid-input`) before writing, and a `replace` of a row at `Number.MAX_SAFE_INTEGER` refuses (`invalid-row`, not retryable) before writing, leaving the row as it was; such a row takes a new credential only as a new row (`remove`, then `add`).

**What an attribution proves, and a reused id (since 0.8.0).** An attribution `{credentialEpoch, identity?}` (with the row id beside it) names one credential lineage: the credential an `add` or `replace` gave the row, through every refresh and `rotate` of it, which keep the epoch. Work attributed to it (`recordQuota`, `recordIdentity`, `updateProviderState`, an attributed `disable` or `enable`, a pull, a refresh's write-back) applies only while the row holds that lineage, so quota recorded for a response served just before a refresh still lands. Up to 0.7.0 a lineage was told apart only within one row's life: `remove` dropped the row's entry, and an `add` of the same id, with a new credential, started at epoch 1 again. Plugins choose their ids and reuse them (`main`), so process 1 could add `main` with credential A (epoch 1, identity X), serve a request, and remove it; process 2 could add `main` with credential B and identity X (or, as A, none); and process 1's late `disable(main, {attribution: {credentialEpoch: 1, identity: X}, providerState})` then disabled B and gave it A's provider state. The same reuse let every attributed write through, and the in-process guard on removed ids (`id-removed`) does not reach another process. Since 0.8.0 epochs never repeat for an id: every config write that drops an id (a `remove`, or an entry left behind by a writer that removed only the roster row) records the epoch it held in `commonAuthPool.retiredEpochs` (`{[id]: epoch}`, 1 for a row without an entry; a value only ever rises), and `add` starts a new row one past the highest of that record and any entry left under the id. Every existing fence then refuses the stale attribution by its epoch, so no API changes and every caller is covered, including those that build `{credentialEpoch, identity}` themselves. An id that held `Number.MAX_SAFE_INTEGER` refuses `add` (`id-removed`, before writing). Rows and configs written by 0.7.0 and earlier load unchanged (no record means epoch 1, as before); older readers ignore the record and older writers keep it as they keep every pool key. Alternatives not taken: the stamp's lineage digest covers only the refresh token or API key, so it changes on a refresh that rotates the refresh token and cannot name a lineage across refreshes; a random lineage id carried in the attribution would protect only callers that pass the new field. Limits: a writer older than 0.8.0 ignores the record and re-adds at epoch 1, and a writer that does not know the pool can remove and re-add a row without the store seeing it (see *D7 compatibility limits*); an entry whose epoch cannot be read records epoch 1. The record keeps one number per id ever dropped. `requireCredentialStamps` refuses exactly what it refused before (see *Stamp status and strict stamps*).

**Pulls.** `pull(request) → Promise<observation>`, where `request` is `{id, credential, credentialEpoch, identity?, reason: 'load'|'add'|'replace'|'admission'}`, is never awaited by a caller. It fires from `load()` once per process per row while needs-first-reading is set, on `add` of an enabled OAuth row, on `replace` of an OAuth row, and on `requestReading`; never for api-key, disabled, credential-less or invalid rows, and never from a refresh's re-read.

**Test and migration seams.** `now` affects logical stamps only (refresh stamps and `addedAt`), never filesystem leases, which always use wall time (`Date.now`); `onStep(step, {operation, rowId})` awaited at `before-config-write`, `after-config-write`, `before-state-write`, `after-state-write` (the `before-*` steps run inside `writeJsonAtomic`'s `beforeRename`, ahead of the ownership assertion); `hold(point, rowId)` awaited at `refresh-before-provider` and `pull-before-request`; `onLockEvent` (acquired/released, per lock) and `onLockStep` (the primitive's renewal steps). Crash rows exit a child process from `onStep`. `onStep` is also supported as a production guard (since 0.11.7 this is a stated contract, not only a test seam): each `before-*` step is awaited inside the atomic writer's `beforeRename`, after the new file is staged and immediately before the store asserts its own leases and renames, so a rejection there aborts that write with the target file unchanged and fails the operation. A rejection at an `after-*` step fails the call after the file was already renamed into place. The hook is one per opened store and fires for every operation on it, so a guard filters on `info.operation` (and `info.rowId`). New step names may be added in a minor release; a guard must ignore steps it does not recognise. Any change to the timing or abort semantics above ships as a minor release with a note here. Plugins migrating a legacy store and host-slot credential into the pool can use: `add` with a given id and credential, `disable` with a reason, `extraLocks` taken after the provider-wide lock, and `onPersisted` after a successful refresh.

### ./cachekeep

Keeps idle prompt caches warm: one target per session holding its latest request body, replayed just before the provider's cache would expire. The manager is openai-auth's (`packages/opencode/src/core/cachekeep.ts` at b7ceb56), chosen because it is the better-tested copy: its suite tests sustain, the clock window, both idle caps, LRU and byte eviction, backoff, abort on stop and per-model TTL and warm caps, where anthropic-auth's tests scheduling, body shaping and the hybrid-mode gate. From anthropic-auth (`packages/core/src/cachekeep.ts` at 77e4c900) it takes coalesced ticks (an overlapping `tick()` returns the run in flight), an injectable `setInterval`/`clearInterval`, and a backoff that may depend on the consecutive failure count, which expresses anthropic-auth's exponential-with-jitter retry.

**The plugin supplies** `new CacheKeepManager<M>({ adapter, now, logger?, ttlMs? = 5 min, leadMs? = tick + 15 s, maxIdleWarmMs? = 1 h, maxSubagentIdleMs? = 30 min, tickIntervalMs? = 60 s, maxTargets? = 32, maxBytes? = 8 MiB, warmTimeoutMs? = 30 s, backoffMs? = 10 min or ({ sessionKey, failures }) => ms, getWindow?, getSustain?, setIntervalImpl?, clearIntervalImpl? })`. `getWindow` and `getSustain` are read on every call, so a config change applies without recreating the manager. The adapter is the provider half:

| adapter member | contract |
| --- | --- |
| `buildBody(target)` | the replay body from the captured one; a throw backs the target off |
| `send({ target, body, signal })` | resolve the account's credential and send; returns a `Response`; a throw (including no credential) or a non-2xx backs off. Provider auth-failure reporting and a 401 retry with a rotated credential live here |
| `readUsage?({ target, response, text })` | usage fields for the `cachekeep fired` log line; a throw is ignored |
| `profile?({ bodyText, isSubagent, accountId, meta })` | `{ ttlMs?, maxWarms?, maxIdleMs? }`, evaluated once at capture and kept on the target: the model-aware TTL, per-model warm cap and idle bound |
| `activeAccount?(sessionKey, target)` | the account the session routes to now, asked before every warm. A different account than the captured one drops the target without sending; `undefined` (no session binding, e.g. ordered routing) keeps the captured account; a throw backs off |

**It gets** `track({ sessionKey, bodyText, accountId?, isSubagent?, meta })` → `{ tracked: true } | { tracked: false, reason: 'body-exceeds-max-bytes' | 'outside-window' }` (arms the timer; the freshest body replaces the previous one and restarts its cache clock, idle clock and warm count), `remove(sessionKey)`, `start()`, `stop()` (aborts a warm in flight, whose result then changes nothing, and forgets every target), `tick()`, and `status()` (no bodies: per target the account, subagent flag, expiry, last real request, last warm, backoff, failures, warm count, TTL and bytes). `meta` is plugin data handed back to the adapter, such as replay headers. Also `normalizeCacheKeepWindow(value)` (a persisted `{ startHour, endHour }` block, or undefined) and `isWithinCacheKeepWindow(window, date)`.

**Bounds.** A target retires once its last confirmed cache lifetime ends (`cacheExpiresAt`: its capture plus its TTL, moved on by each successful warm), checked on every `track` and `tick` and again before each send, whatever the window, sustain or a pending retry say: replaying a history whose cache has expired rebuilds a cold cache instead of keeping a warm one alive, and with large histories that is a real cost, not a heartbeat (library decision, from anthropic-auth's native keeper). A failed warm still backs off, but a retry is sent only while the lifetime lasts; a backoff that runs past it means the target retires instead, which with the manager's defaults (`backoffMs` 10 minutes, `ttlMs` 5 minutes) is every failure. Explicit cold prewarming (sending a source body whose cache is not known to be live) is a separate operation the manager does not offer; a plugin that wants one sends it from its own code. The window gates capture and warming; targets captured inside it survive outside it until their lifetime ends, and warm when it reopens if they are still alive. A target idle past its bound (the profile's `maxIdleMs`, else `maxSubagentIdleMs` or `maxIdleWarmMs`) is pruned on every `track` and `tick`, including while it is backing off. `sustain` exempts main sessions from that idle pruning only: the lifetime, subagents, the window, the count and byte caps and warm caps still apply. The count and byte caps evict the target touched least recently, where a warm counts as a touch; an oversized body is refused without evicting anything. Library decision: byte caps count UTF-8 bytes.

**Differs from openai-auth.** Header capture (`buildKeepwarmCapture`), the replay body (`buildKeepwarmBody`), `ttlForModel` and the gpt-5.6 subagent policy (two warms, 75-minute idle bound), token resolution (`getMainToken`, `refreshFallback`, `onAuthFailure`), the account-id header and JSON/SSE usage parsing stay in the plugin as adapter members and a profile. `track` takes an object and reports why it skipped; `route` is gone from targets; log payloads no longer add the pid. Byte caps count UTF-8 bytes rather than string length. A tick warms in one pass in insertion order; openai-auth ran backed-off-and-expired targets first. A failed warm also counts consecutive failures. openai-auth retried a failed warm after its backoff even when the cache had expired meanwhile, and kept a failing target until its idle bound; the manager retires it at the end of its cache lifetime instead. The active-account check is new; openai-auth always warmed the captured account.

**Differs from anthropic-auth.** The manager reads no storage: the plugin calls `track` only when keep-warm is enabled and the hybrid cache mode is on, and passes `getWindow` (no window is its `always`). Its 60-minute TTL and 5-minute lead are `ttlMs` and `leadMs`. As in anthropic-auth, a target is dropped when its confirmed cache lifetime ends without a successful warm, so a failed warm is never followed by a replay into an expired cache; it is not dropped at the end of a window period while its lifetime lasts. An unbuildable body backs off instead of deleting the target (an adapter that wants deletion calls `remove` before throwing). `prewarmNow`, `trackedOAuthRoute`, `onTrackedSessionsChanged` and the per-attempt hooks are not carried: `status()` and the adapter cover them. A plugin that dumps warm requests does so from its adapter's `send`, with `./dump`.

### ./dump

Request-body dumps for cache debugging, from openai-auth's `packages/opencode/src/dump.ts` (b7ceb56) with anthropic-auth's choice of the newest earlier dump on disk as the diff baseline (`packages/core/src/dump.ts`, 77e4c900).

**The plugin supplies** `createDumper({ dir, enabled? = false, pid? = process.pid, now? = Date.now, logger?, secretKeys?, secretPatterns?, schemaKeys? = ['tools'], summarize? })`. `dir` may be a function read on every dump. `secretKeys` are key names redacted wherever they appear (compared lower-cased without `-` and `_`) on top of the common credential set (`authorization`, `x-api-key`, `cookie`, `set-cookie`, any `*apikey*`, `*secret`, `*password`, `*token`); openai-auth passes `chatgpt-account-id`. `secretPatterns` add value patterns to the common token patterns. `schemaKeys` name keys, at any depth of the body, whose values are declarations: their strings are scrubbed but their key names are never redacted, so a tool parameter named `api_key` keeps its schema. `summarize(redactedBody)` is the provider's body summary, stored as metadata `body`.

**It gets** `{ isEnabled(), setEnabled(enabled), dump(input) }` and `diffDumpBodies(previous, current)`. `dump({ session?, channel, phase?, bodyText, accountId?, url?, method?, headers?, status?, error?, meta? })` writes `<id>.body.json` (the redacted body; the original bytes when nothing was redacted), `<id>.meta.json` and `<id>.request.json` (url, method, account and headers, redacted), each 0600 and created exclusively, in a directory created or tightened to 0700, and returns `{ id, files }`, or undefined when dumps are off or the write failed (logged, never thrown). The id is `<ISO time>-<pid>-<6-digit counter>-<session>-<channel>[-<phase>]`; the pid keeps processes sharing a directory apart. A dump is diffed against the previous dump of the same session and channel; phases share the baseline. The baseline is the last body in memory, else the newest earlier dump on disk whose metadata `baselineKey` (sha256 of channel and session) matches, so it survives a restart and is cleared with the directory; it is never stored anywhere else. The diff runs on the redacted text, so its offsets index the body file.

**Differs from openai-auth.** `transport` becomes `channel`. The mask is the common `***REDACTED***`, not `[redacted]`. Bodies that are not JSON are string-scrubbed instead of written raw. The disk baseline is matched by `baselineKey`, so dumps written before adoption (which have none) are not used as baselines; it is looked up whenever the memory baseline is missing, including after eviction from the 100-key memory, instead of once per key per process. The counter has six digits. Its `bodySummary` (which reads OpenAI Responses fields), `dumpDiagnostic`, `DUMP_SESSION_HEADER` and reading the settings stay in the plugin.

**Operational options (added in 0.4.0; each defaults to the earlier behaviour).** `maxBytes` (default 0, no cap) holds the dump artifacts in the directory to a byte cap: after a successful dump, at most once per `sweepIntervalMs` (default five minutes, and on a dumper's first dump), a background sweep evicts whole dumps (body, metadata, request and response files together, grouped by id), oldest first by each group's newest mtime, until the total fits. Dumps younger than `sweepMinAgeMs` (default one minute) and the dump just written are kept; response staging files older than `partialStaleMs` (default ten minutes) are removed even under the cap. Only names a dumper writes (`<ISO>-<pid>-<counter of six or more digits>-<segments>.(body|meta|request|response).json` and their `.<24 hex>.partial` staging files) are counted or removed, so a directory the user chose may hold other files; a symlinked directory is refused. `dumper.sweep(protectedPaths?)` applies the cap now, and `sweepDumpDirectory({ dir, maxBytes, protectedPaths?, now?, minAgeMs?, partialStaleMs?, logger? })` is the same sweep for any directory. `cleanupFailedDumps` (default false) removes the files a failed dump did write once all its writes have settled, so no half group is left; a file whose exclusive create failed with EEXIST belongs to another writer and is left. `dumper.dumpResponse(dump, { status?, requestId?, usage?, complete? = true, fields? })` writes the dump's `<id>.response.json` (path in `DumpResult.responseFile`), redacted like the request, 0600, through an exclusively created staging file renamed into place, replacing any earlier artifact so a stream can record its opening and then its final usage; it does nothing for an undefined dump and returns the path, or undefined after a logged failure. The plugin passes evidence about the response, never its content.

**Differs from anthropic-auth.** Bodies, request headers and metadata are redacted; files are 0600 in a 0700 directory; names carry the pid. The byte cap, grouped eviction, stale-partial reclaim and response artifacts are ported (`packages/core/src/dump.ts` at 77e4c900, with its test titles), with these differences: the cap and its timings are options instead of `OPENCODE_ANTHROPIC_AUTH_DUMP_MAX_BYTES` and constants, and default off instead of 512 MiB (anthropic-auth passes `maxBytes: 512 * 1024 * 1024`); there is no environment-configured directory, so the guard that refuses a directory other than the configured one (its test "refuses a directory that is not configured for dumps") is not carried: a dumper sweeps only its own directory and a direct `sweepDumpDirectory` caller names it; the response artifact's fields are generic (`requestId` for `message_id`, `complete` for `stream_complete`, provider fields such as `model`, `diagnostics` and `stop_reason` under `fields`) and redacted; body, metadata and request files are created exclusively in place rather than through staging files, which is why failed-group cleanup exists. The relay payload file and the `/claude-dump` command stay in the plugin. Its `direct`/`http`/`websocket` transports and `cachekeep`/`start` tags map to channel and phase; the ported tests' "failed request dumps" case fails a write by stubbing it rather than by a read-only directory, because the dumper tightens its directory to 0700 first.
### ./auth-menu

The `opencode auth login` account menu. Three layers, each usable alone: the menu runtime, the OpenCode v1 `authorize` contract around it, and the account actions over a `/store` pool. Nothing here reads the environment, a host path or the host's login slot; the terminal, the store, the login and every provider detail come in as parameters.

| export | parameters | returns |
| --- | --- | --- |
| `runMenu(options)` | `{ title, subtitle?, status?: string[], actions: MenuAction[], terminal? }`; `MenuAction` is `{ id, label, hint?, destructive?, confirm?, run(context) }` | `{status:'ran'\|'declined'\|'failed', action}`, `{status:'cancelled'}` or `{status:'not-interactive'}` |
| `menuContext(terminal)` | a `MenuTerminal` | `{ terminal, interactive, print, confirm, select }`, what an action is handed |
| `select(terminal, items, options)`, `confirm(terminal, message, defaultYes?)` | items `{ label, value, color?, hint? }`; options `{ message, subtitle?, lines?, clearScreen? }` | the chosen value or `null`; `confirm` a boolean |
| `processTerminal()`, `isInteractive(terminal)`, `printLine(terminal, line)` | — | the process's stdin/stdout/signals; whether keys can be read |
| `menuCompletedResult()` | — | `{url:'', instructions:'', method:'auto', callback: async () => ({type:'failed'})}` |
| `isCliAuthorize(inputs)`, `menuAuthorize({ hasCredential, openMenu, login })` | `authorize`'s `inputs` | an `authorize(inputs?)` |
| `runAccountMenu(options)`, `accountMenuActions(options)` | `AccountMenuOptions` below | a `MenuOutcome`; the actions for the current mode |
| `addAccountAction`, `reauthenticateAction`, `removeAccountAction`, `toggleAccountAction`, `listAccountsAction`, `checkQuotasAction`, `deleteAllAction` | `AccountMenuOptions` | one `MenuAction` each, for a plugin composing its own list |
| `doctorAction({ checks, title?, label? })`, `runDoctorChecks(checks)`, `applyChosenRepairs(context, report)`, `formatDoctorReport(title, report)` | `DoctorCheck` is `{ id, run() → DoctorFinding[] }`; `DoctorFinding` is `{ code, message, accountId?, repair?: { label, apply() } }` | a `MenuAction`; `{findings}`; `{applied, declined, failed}`; lines |
| `runMenuLogin(login, context)`, `openBrowserForMenu(url, platform?, exec?)` | `MenuLogin` below | the login's `LoginAccount`; whether a browser opened |
| `poolHasCredential(store)`, `quotaLines(row, now?)`, `MENU_DISABLE_REASON`, `DOCTOR_CHECK_FAILED`, `ANSI`, `parseKeys`, `parseKey`, `stripAnsi`, `truncateAnsi` | — | helpers; `parseKeys` (0.11.0) splits one terminal read into its keys in order, and `parseKey` returns the first of them |

**What a plugin supplies.** `AccountMenuOptions` is `{ title, store, terminal?, login?, newAccountId?, protect?, extraLocks?, pollQuota?, doctor?, custody?, status?, extraActions?, disableReason?, now? }` (`now`, 0.13.0: the clock quota resets and reading ages are measured from, default `Date.now`). `login` is `MenuLogin { begin({headless, signal?}) → {url, instructions, completion: Promise<LoginAccount>}, openBrowser?(url) }`, where `LoginAccount` is `{ credential, identity?, label?, id? }`: the provider's browser and device-code flows, its URLs and token parsing all stay in the plugin. `protect` is the store's `remove` predicate and is passed to every removal the menu makes, delete-all included. `pollQuota(row)` returns an observation for the store's quota codec (a `/quota` `QuotaObservation` when the store was opened with `quotaCodec`). `doctor` is the plugin's checks; each repair is the plugin's own write. `custody()` says whether accounts come from a vault. Around the menu, the plugin builds its OAuth method's `authorize` with `menuAuthorize`, supplying `hasCredential` (see the rule below), `openMenu` (usually `runAccountMenu`) and its normal `login`.

**What it gets.** A full-screen menu drawn with first-party code (ported from openai-auth's `auth/ui/{ansi,select,confirm}.ts`, no prompt library): arrow keys, Enter, Escape (a lone Escape byte after 50 ms, so a split arrow sequence is not read as cancel) and Ctrl-C. Since 0.11.0, several keys arriving in one terminal read (a fast typist, a paste, a scripted terminal) are each handled in order, and an escape sequence cut off at the end of a read is ignored rather than read as a key. `KeyAction` gained `'left'`, `'right'` and `'char'` (any printable character), so code that narrows it exhaustively must handle them; raw mode and the cursor are restored on every exit. The heading shows the plugin's status lines and up to eight account lines. Local mode lists Add account and Re-authenticate (only with a `login`), Remove account, Enable or disable account, Check quotas, Auth doctor (only with checks), the plugin's extra actions, then Delete all accounts in red. Custody mode lists List accounts, Enable or disable account, Check quotas, the doctor and the extras: nothing that adds, signs in or removes, since those happen in the vault. Check quotas and the doctor stay under custody: neither changes which accounts exist or what they sign in with, so neither competes with the vault, and both still help an operator see why an account is not being used.

**Decisions.**

- *Single shot.* The menu runs one action and returns, as openai-auth's does; the operator reruns `opencode auth login` for another.
- *The failed callback.* OpenCode v1's `AuthOAuthResult` has no top-level "done, store nothing": every result ends in a callback whose success the host files as the provider's credential. After any menu action the plugin returns `menuCompletedResult()`, whose callback fails, so the host stores nothing and the operator sees `Failed to authorize` (openai-auth's capture `docs/baselines/opencode-auth-menu.v1.18.30.txt`, OpenCode 1.18.30). The library declares its own types matching the host's result shape, so it does not import `@opencode-ai/plugin`.
- *When the menu opens.* `menuAuthorize` never calls `hasCredential` on the TUI path (no `inputs`), so the TUI signs in as before. On the CLI path, the plugin's `hasCredential` must answer "a real credential exists" (the host's slot or a stored credential, `poolHasCredential` for the second half), never "the roster is non-empty": the signed-in account is usually the only one and may not be a roster row, and a roster check hid the menu from the operator adding their first extra account.
- *No TTY.* `runMenu` prints the title, status and actions as a plain list, says nothing was changed, and returns `not-interactive` without reading a key. `confirm` answers no without a TTY, so nothing destructive runs unconfirmed. openai-auth's selector threw instead; antigravity-auth's CLI fell back to a readline prompt.
- *Destructive actions.* A `destructive` action is drawn red and runs only after an explicit yes ("No" is listed first). Remove confirms by account name after the account is picked. Delete all removes row by row through `store.remove` with the plugin's `protect`, reporting what was deleted and what was kept and why; a protected id stays with its files untouched.
- *Re-authenticate.* Replaces the chosen row's credential through `store.replace`, keeping the row's identity when the login reports none, and refuses (writing nothing) when the login reports a different identity from the row's: replacing would silently turn the row into another account.
- *Check quotas.* Polls each valid row with a credential once, in roster order, records each observation through `store.recordQuota` with the row's epoch and identity (so a reading cannot land on a credential replaced meanwhile), then prints every row's windows from the stored map through `projectQuota` and `quotaTextParts`, one line per window in the shared wording (`5h 58% left, resets 2h`; was `primary: 58% left, resets <ISO time>` before 0.13.0). A failed poll is printed beside the row; the others still run.
- *Doctor.* Checks only read; findings are printed, then each available repair is asked about in turn and only the ones answered yes are applied. A check that throws becomes a `doctor-check-failed` finding instead of hiding the rest. openai-auth's separate Auth doctor and Apply repairs entries become this one entry.
- *Single-item lists are shown.* openai-auth's selector returned a one-item list's value without drawing it; this one draws it, so a menu or account picker with one entry still asks.
- *Errors.* An action that throws is printed (`<label> failed: <message>`) and reported as `failed`; the menu never throws past the plugin's `authorize`, which still owes the host its result.

### ./commands

One slash command per plugin (`/openai`, `/claude`, `/antigravity`) opening one menu, drawn by OpenCode's TUI from a payload sent over the loopback RPC and by Pi with its extension UI. The per-feature commands (`/openai-account`, `/openai-quota`, `/openai-routing`, `/openai-killswitch`, `/openai-cachekeep`, `/openai-dump`, `/openai-logging`, `/openai-reset`; `/claude-account`, `/claude-quota`, `/claude-routing`, `/claude-killswitch`, `/claude-cache`, `/claude-cachekeep`, `/claude-dump`, `/claude-logging`, `/claude-fast`, `/claude-prime`, `/claude-start`; `/antigravity-account`, `/antigravity-quota`, `/antigravity-routing`, `/antigravity-killswitch`, `/antigravity-dump`, `/antigravity-logging`, `/gemini-dump`) are removed at adoption, not kept as aliases; what they did becomes a section or an action of the one menu.

Runtime exports: `createCommandMenu(options)`, `runPiCommandMenu(menu, ui, {sessionId?}?)`, `parseApplyRequest(value)`, `SECTION_SLOTS`, `DEFAULT_IRREVERSIBLE_CONFIRMATION`, `MENU_DISABLED_REASON`, `CommandError`, `projectFailure(error)`, `ACTION_FAILED`, `createTextRedactor(redaction?)`. Type exports: the menu model (`CommandMenuModel`, `MenuSection`, `MenuItem`, `MenuAction`, `MenuKnob`, `MenuChoice`, `MenuConfirmation`, `MenuAccount`, `KnobValue`, `KnobValues`, `SectionSlot`), the wire types (`CommandDialogPayload`, `CommandApplyRequest`, `CommandApplyResult`), the definitions a plugin writes (`PluginSection`, `PluginExtraSection`, `SectionContent`, `ItemDefinition`, `ActionDefinition`, `ActionInput`, `ActionOutcome`), the per-section options (`AccountsSectionOptions`, `QuotaSectionOptions`, `RoutingSectionOptions`, `LimitsSectionOptions`, `LoginOutcome`, `VaultRoutingOrder`), `CommandMenu`, `CommandMenuOptions`, `CommandInvocation`, `NotifyKind`, `PiMenuUi`, `PiMenuOptions`, `SeamLogger`, `ProjectedFailure`, `TextRedactor`.

**Model.** Sections, in one fixed order everywhere: Accounts, Quota, Routing, Limits (built in), then Cache and Diagnostics (plugin slots, shown only when supplied), then provider extras in the order given. A section has read-only `lines`, `items` and section-level `actions`; an item has a `label`, an optional `detail`, an optional `group` and `status` (0.13.0), the projected `account` (built-in sections only) and `actions`. An action has an `id`, a `label`, an optional `description` and `group` (0.13.0), typed inputs (`choice`, `toggle`, `number`, `text`; `number` and `text` may be left empty, which the action receives as `null`) and an optional confirmation `{message, irreversible}`. An irreversible action always carries one: the `ActionDefinition` type requires `confirm` with `irreversible: true`, and a definition that names none (plain JS) gets `DEFAULT_IRREVERSIBLE_CONFIRMATION`. `apply` refuses an action that carries a confirmation unless the request says `confirmed: true` (`{ok:false, needsConfirmation:true}`), so both renderers confirm before applying; Pi confirms with `ui.confirm`.

**Rendering contract (0.13.0).** Every renderer (the plugins' OpenCode dialogs, `runPiCommandMenu`) draws a section the same way:

- Every option a renderer shows can be selected and does something: an item with at least one action, or a section-level action. Text that does nothing is never an option; it is a group header or a line.
- `lines` are read-only text. On OpenCode they are drawn as header text (a `category`) above the first group; on Pi they are part of the select title. A line is a short summary (at most about 32 characters, real plurals, no `(s)`, no trailing period), a problem message, or a note about a row that cannot be acted on (Quota's `acct-b (disabled): 5h 1% left`).
- The options are the items, then the section-level actions. When an option's `group` differs from the previous one's, a header naming the group is drawn first; a header is never selectable. On OpenCode 1 a header is the `TuiDialogSelectOption` `category`.
- `disabled` is not used: OpenCode's `DialogSelect` drops `disabled` options from the list altogether (`packages/tui/src/ui/dialog-select.tsx`, `props.options.filter((x) => x.disabled !== true)`), so a disabled row would vanish rather than show as text. The built-in sections never emit an item without actions; a plugin section should not either, and a renderer that meets one writes it as header text (OpenCode) or title text (Pi), never as an option.
- `status` is a short value drawn right-aligned beside the label (OpenCode `footer`); an item's `detail` and an action's `description` are the secondary text (OpenCode `description`).
- Pi's `select` cannot put text between options, so `runPiCommandMenu` writes the lines, then each group header with its action-less rows (one line each, `label · status`), into the select title; the options are only the rows that do something, labelled `label · status`, and a closing `Back`. The header of a group whose rows are all selectable is therefore not shown on Pi, which is why Limits also keeps its `Killswitch off` line.

**What a plugin supplies.** `createCommandMenu({command, title, store?, replace?, extraLocks?, accounts?, quota?, routing?, limits?, cache?, diagnostics?, extras?, logger?, redaction?, now?})`:

- `store`: its `PoolStore`; `extraLocks`: its legacy locks, passed to every store write the menu makes. Required unless `replace` supplies all four store sections.
- `replace` (since 0.11.6): `{accounts?, quota?, routing?, limits?}`, each a `PluginSection` that takes the built-in section's place, keeping its slot id, slot and the fixed order. For a plugin whose accounts are not pool rows (a single host login, or rows it must not expose by id): it builds its own items, with ids of its choosing, and actions. Slots not replaced are still built from `store`. `createCommandMenu` throws when a built-in slot has no store, or when a replaced slot also gets its built-in options. Type export: `StoreSectionSlot`.
- `accounts.login {label?, knobs?, run(values, invocation) → LoginOutcome}`: `{status:'ready', account}` adds now; `{status:'pending', message, completion}` shows `message` (the login URL or device code) and adds the account when `completion` resolves, reporting through the invocation that asked; `{status:'cancelled', message?}`. Without it, Accounts has no add action. `accounts.protect` is passed to `store.remove` (the plugin's reserved ids and pending-operation records). `accounts.describeIdentity(row)` chooses what is shown as the identity (defaults to the recorded identity).
- `quota.check(ids, invocation)`: the plugin's "check now" poll; without it the menu calls `store.requestReading` for each id and awaits `store.pullsSettled()`. `quota.scope` picks the projection scope (default `all`).
- `routing.orderedVariants`: further `routing.mode` values offered between `ordered` and `sticky-balanced` (openai-auth: `main-first`, `fallback-first`); `routing.formerMainId` for the "tried in order" line.
- `routing.vaultOrder` (0.25.0): `() → VaultRoutingOrder | undefined` (sync or async), called on every build. While the plugin routes through vault accounts it returns `{ rows, reorder(ids) }`: `rows` is every vault roster row in row order as `{ id, label }` (`id` the route id, `label` the name the plugin's menu shows for that account), and `reorder` takes route ids and sets a new order. Route ids (`vault:chatgpt:openai~ffdbede18a`) are long and opaque, so the section works in labels where it can and accepts route ids where it must: it shows `Vault account order: work, personal, …` instead of `Roster order:`, and its "Set order" input (`Vault accounts, first to last, separated by commas`) starts with the labels in order. Entries are separated by commas or line breaks, not spaces, since a label may contain spaces; each entry may be a label or a route id, and must name exactly one row (an exact match of either). The menu maps the entries to route ids before calling `reorder`; the pool roster is not touched. An account's input default is its route id instead of its label when the label would not name it alone (two accounts share the label, or the label contains a comma or line break), so the default always applies as is. Refusals write nothing and use the code `vault-invalid-order`; each quotes only the entry the user typed: `"<entry>" is not a vault account.` (matches no row), `"<entry>" matches more than one vault account; enter those accounts by route id.` (two accounts share that label), `"<entry>" names an account already in the order.` (the same account twice, by label or id). A left-out account is refused by the roster, `the order leaves out N roster route ids`, which counts without naming. Any other failure is projected as usual. A changed order reads `Order set to <labels>.`; an order already in place reads `The order is unchanged.` and writes nothing. In local mode it returns undefined and the section shows and sets the pool roster as before. Wiring: a plugin with a `ClaustrumConsumer` returns `{ rows: consumer.snapshot()?.rows.map((row) => ({ id: row.routeId, label: row.label })) ?? [], reorder: (ids) => consumer.reorder(ids) }` when `isCustodyActive()` holds. `VaultRosterRow.label` is the `mapAccount` label, defaulting to the trailing segment of `oauth:<provider>:<label>`, then the email, then the credential id; a plugin whose menu names vault accounts by email passes `row.email ?? row.label` instead. A plugin that keeps its own roster with `ClaustrumScopedCustody` builds the rows from `readVaultRoster(rosterPath)` the same way, calls `reorderVaultRoster(rosterPath, ids)` and then updates its own in-memory roster. Without `vaultOrder`, "Set order" in vault mode still orders the pool roster, which routing does not use there. Type export: `VaultRoutingOrder`.
- `limits.labels`: the window labels floors can be set for (defaults to the labels in the pool's quota readings, else `primary`).
- `cache`, `diagnostics`: `{title, build(invocation) → SectionContent}`; `extras`: the same with an `id` (not one of the fixed ids). A section whose `build` throws shows "This section could not be loaded." and the rest of the menu still opens.
- `logger`: receives the seam's warnings and failed actions (defaults to the library logger's `commands` channel).
- `redaction`: the logger's `RedactionOptions`; its `extraValuePatterns` name the provider's key shapes (an arbitrary key format is not recognisable otherwise). Every string leaving the menu goes through them.
- To show a failure's own words, an action throws `new CommandError(code, message)` (`code` lowercase letters, digits and dashes) or returns `{ok: false, text, code?}`; the text is still redacted.

**What it gets.** Since 0.13.0 the built-in sections use groups. Accounts: summary `3 accounts, 2 enabled`; the roster in order under `Accounts`, each with `enabled`, `disabled` or `invalid` as its status and type, identity and disabled reason as its detail (the quota summary moved to Quota); then `Actions` with add (through the plugin's login), remove (irreversible, `store.remove` with `protect`), enable, disable (reason `MENU_DISABLED_REASON`), and move to a position (`store.reorder`). Quota: no summary line (the `Scope:` line is gone; a scoped menu's header reads `Accounts · <scope>`); each account under `Accounts`, with `formatQuota`'s compact form as its status and its full form as its detail (the per-window `facts` with `% used` are gone), each with a "Check this account" action that polls just that account (through `quota.check([id])`, or `store.requestReading(id)` and `pullsSettled()`); then `Actions` with "Check now", which checks every candidate account (its former account-choice input is gone: the per-row action replaces it). An account that is not a candidate (disabled, invalid, without a credential) cannot be checked, so it is not a row: it is a line, `<name> (<reason>): <compact quota>`. Routing: summary `Mode: <mode>` and the roster order as lines; under `Actions`, the mode as a choice over `ordered`, the plugin's variants and `sticky-balanced`, written to `routing.mode`; and the roster order as an editable list (`store.reorder`). Limits: summary `Killswitch off` (or `on`); the accounts under `Floors · killswitch off`, each with its floors as status (`5h ≥10%`, or `no floors`); then `Actions` with the killswitch on/off (`killswitch.enabled`), whose description explains it. Floors are the minimum % left per window label, shown under the window's name (`Minimum % left for 5h`), under `killswitch.accounts.<id>.<label>` (an empty input clears a floor; an account left with no floors loses its entry). Every settings write goes through `store.updateSettings` with the plugin's `extraLocks`.

**Migration for plugin sidebars and dialogs (0.13.0).** A plugin's own quota text (openai-auth's `QuotaRow` and `formatResetIn` in `packages/opencode/src/tui.tsx`, its Pi `commands.ts` window details, and each plugin's sidebar rows) should call `formatQuota(projectQuota(row.quota, scope), { now, form: 'compact' })` for a row or `quotaTextParts` for one line per window, instead of formatting windows itself, so a sidebar reads exactly like the dialog. A plugin's own sections and summaries follow the rendering contract above: a short summary line (`3 accounts can route`, `2 set aside`), never an explanation drawn as a row; explanations go in an action's `description`. A drawer maps a section to `TuiDialogSelectOption`s by emitting each row with `category: row.group`, `footer: row.status`, `description: row.detail ?? action.description` and draws `lines` as header text above the first group; it never sets `disabled`, which would hide the option.

**Wiring.** OpenCode: on the slash command, `menu.open({sessionId, notify})` and send the `CommandDialogPayload` to the TUI; on the TUI's apply RPC, `parseApplyRequest(body)` and `menu.apply(request, {sessionId: request.sessionId, notify})`, and send back the `CommandApplyResult` (its `menu` is the refreshed model, so the drawer redraws from it). The drawer is plugin code; the payload carries everything a generic drawer needs (titles, lines, items, typed inputs with current values, confirmations), so it no longer needs per-command dialogs. Pi: `runPiCommandMenu(menu, ctx.ui, {sessionId})` from the command handler.

**The seam.** `open` and `apply` are the only producers of payloads, and both go through one function: every part is projected field by field (an account is `{id, label, enabled, type, identity}` and nothing else), then the whole payload is scrubbed of credential-shaped property names (case, `-` and `_` ignored: names ending in `token`, `key` or `secret`, and `access`, `refresh`, `apiKey`, `password`, `authHeader`, `credential`, `credentials`), and each drop is warned with the field paths, never the values. The section and action bodies stay in the process. A plugin's `facts` (free name/value display pairs on a section or item) are the one place plugin data passes through unprojected, so they are where the scrub matters.

Projecting declared fields does not make their values safe, so every string value in the payload (labels, lines, facts, knob defaults, result text) then passes through the logger's redactor (bearer tokens, `sk-` keys, JWTs, vault host tokens) plus two seam patterns (a value assigned to a secret-named field such as `client_secret=` or `"requestSecret":`, and a run of 32 or more hex digits, the shape of a minted enrollment request secret) and the plugin's `redaction.extraValuePatterns`; each masked value is warned by path (`secret-shaped text masked in a command payload`). A `masked` text knob's current value is never sent (the action still receives it when the input is left alone). Notifications sent through the invocation, including a late login's, go through the same redactor.

**Failures (library decision).** A failed apply carries a stable `code` beside its `text`. The menu's own: `unavailable`, `needs-confirmation`, `invalid-input`; an `ActionOutcome` with `ok: false` is `refused` unless it names a code. An action that throws never shows its exception text, which can quote a request, a response or a credential: a `CommandError` shows its code and message; a store `PoolOperationError` is `pool-<kind>` with the store's own message for kinds whose message the store composes from ids and the plugin's `protect` reason (`unknown-row`, `row-protected`, `invalid-order` and the like), else a generic line; anything else is `action-failed`, `That action failed.`. The raw text goes, redacted, only to `logger` (`command menu action failed`, with the code). When a pending login's `completion` rejects after the apply has returned, the invocation is notified `Adding the account failed: <projected message>`.

**Per-invocation context.** `open` and `apply` copy the `{sessionId, notify}` they are given before their first await, and work an invocation leaves running (a pending login) reports through that copy. A host can therefore reuse one context object across sessions without one session's feedback reaching another; the menu keeps no state between invocations.

Differences from each plugin's current behaviour:

- openai-auth: one dialog instead of eight; `/openai-reset` becomes a provider extra, `/openai-cachekeep` the Cache section, `/openai-dump` and `/openai-logging` the Diagnostics section, all supplied by the plugin. The payload is the generic model, not `{command, text, knobs}`, so `command-dialogs.tsx` is replaced by one generic drawer. `routing.mode` gains `ordered` (written explicitly when chosen; openai-auth's legacy readers do not know the value and route `main-first` for it, as they do for an absent mode; see the `routing.mode default` limit below). The killswitch's `main` thresholds have no menu entry: the main account is a pool row like any other under `killswitch.accounts`. `buildDialogPayload`'s scrub is kept and widened from `*token` to `*token`, `*key` and `*secret`.
- anthropic-auth: the same sections replace eleven OpenCode commands and nine Pi commands; `/claude-cache`, `/claude-fast`, `/claude-prime` and `/claude-start` become Cache or provider-extra entries. On Pi the menu is now interactive (`select`, `confirm`, `input`) where the commands took arguments and answered with `notify`.
- antigravity-auth: the same sections replace its seven OpenCode commands; `/gemini-dump` is not kept. Its Pi package registers no command today; adopting gives it the one command.
### ./claustrum

(0.9.5) Setup writes accept group-writable ancestors without a sticky bit only when owned by the process's effective user and group and local `/etc/passwd` and `/etc/group` records show that the user exists, the group exists, no other named group member belongs to it and no other user has it as their primary group (files read lazily once per check, unreadable or malformed records refuse); world-writable ancestors still require the sticky bit, while request reads reject symlinks and require regular files owned by the effective user with owner-only permissions, without ancestor or account-file I/O.

(0.9.5) The approved token is written by `@cortexkit/claustrum-client`'s own writer, which applies the same private-group rule from 0.6.1 (0.6.2 also decodes inventory rows from vault daemons that predate `provider_ids`), so the client floor is `>=0.6.2`: with an older client, Connect on a default Ubuntu or Fedora account (umask 0002, `~/.config` mode 0775) stops after the pending request, at the token write. That writer reads the real `/etc/passwd` and `/etc/group`, so the end-to-end Connect test runs only where the user's real group is private and is declared skipped elsewhere (macOS, CI runners in shared groups).

The `/claustrum` subpath lets a plugin enroll with a credential vault and use the vault's scoped credentials for account discovery and authorization. It was adapted from anthropic-auth's enrollment, scoped-client, roster and runtime modules and their tests; openai-auth's handle-based custody was not carried over. It needs the optional peers `@cortexkit/claustrum-client` (>= 0.6.2) and `@cortexkit/subc-client` (`^0.16.0 || ^0.22.0`) together: both are imported statically when `/claustrum` or `/setup` loads. claustrum-client 0.6.2 through 0.10 depend on subc-client 0.16.x and 0.11 onward on 0.22.x, so installing it brings the matching line. A plugin that moves to claustrum-client 0.12 (for the vault watch below) must move its own `@cortexkit/subc-client` to 0.22 in the same change, so its bundle keeps one shared external copy. common-auth uses only `SubcClient.connect`, `routeOpen`, `request`, `subscribe` and `close` and the `SocketClosedError`, `SocketTimeoutError` and `SubcCallError` classes, which have the same shape in both lines. The floor job (`check:claustrum-floor`) runs claustrum-client 0.6.2 with subc-client 0.16.1, checks that exactly one subc-client copy loads, and runs the full Claustrum suite there, which covers the polling fallback of a client without `watchScoped`. A plugin that bundles common-auth declares both as externals, never inlined, so the vault client and the insula transport share one subc-client; a lazy import would only move a missing peer to first use and make the bundler emit a separate chunk. A consumer that never imports `/claustrum` or `/setup` needs neither; CI runs the full Claustrum test suite and typechecks the source against 0.9.0. On macOS and Linux, 0.6.2 and later behave the same here. On Windows, enrollment works end to end only with 0.9.0 or later: from 0.9.0 the client writes the enrollment token owner-only (through `@cortexkit/store`, on the same contract common-auth's reader verifies). With an older client on Windows, common-auth refuses the token it reads, so Connect fails closed rather than trusting a token other users could read. A plugin that supports Windows enrollment should require claustrum-client 0.9.0 itself. Importing `/claustrum` without that peer fails, while every other subpath is unaffected. The plugin supplies the vault connection file, token and roster paths, clock and logger; the library reads no environment variables or host paths.

**Pool integration.** A vault credential becomes a `RoutingRow { id: routeId, kind: 'oauth' \| 'api-key', quota? }` through `routingRows()`; the plugin concatenates them with its local rows (from `/store`) and passes the lot to `admit`, `routeOrdered` or `routeSticky` unchanged. Only enabled rows in state `active` route; declined or cold rows stay in `snapshot()` for the menu. Quota for a vault row lives in the roster file and is merged with `/quota`'s `mergeQuotaObservation` by `recordQuota`, which requires the receipt the reading was taken with. The fence is mandatory and exact: the receipt's credential must still be the row's representative or alias, and its account must equal the row's (a known account on one side never matches an absent one; the only absent-absent match is a row that has never had a known account and a receipt that names none either). Since 0.4.1 a receipt issued for a row that has never had a known account (no `expectedAccountIdentity`) whose `asserted` or `parsed` identity names an account binds that account to the row in the same write as the reading (the row is marked `unclaimed`, since the vault's list has not named it): the reading is that account's, and keeping it without the account let a later list naming a different account inherit it as a first identity learning. A later list naming another account is then a known replacement (new route, no quota); one naming the same account keeps the route and quota. Library decision: bind rather than refuse the reading, so a vault that never names accounts still keeps readings for a credential whose served reply or token proves which account it logs into. A row with more than one credential is never bound this way (one credential's account says nothing about the others) and the reading is refused. Once bound, `authorize` expects that account for the row, so a served token proving another account is `identity-changed`. While the row is `unclaimed` only an `asserted` or `parsed` identity is accepted, never the roster's own expectation. An observation for a replaced account is dropped, and the authorizing account is never inferred by reading the roster after the request. An admission refusal's `requestPull(id)` for a vault id is the plugin's cue to fetch a reading through `send(id, …, { site: 'quota' })`. Nothing in `/store`, `/routing` or `/quota` changed: the store never holds a vault row, and a vault row never holds a token, so there is no local refresh. The roster file (`rosterPath`) is the plugin's, separate from the store's files, secret-free, written 0600 through `writeJsonAtomic` under a `withLock` write lock.
**Vault routing order (0.25.0).** With routing `ordered`, the order vault accounts are tried in is the roster file's row order: `vaultRoutingRows` returns rows in file order, and discovery keeps each account at its position and appends new accounts sorted by credential id. The vault has no order of its own; the order is this host's routing preference, kept in its roster. `reorderVaultRoster(path, routeIds)` sets it, with the shape of the pool store's `reorder`: `routeIds` is the full new order and must name every roster route id exactly once (including declined and inactive rows, which keep their place but do not route). An unknown, missing or repeated id, or a list that is not all strings, refuses with `ClaustrumConsumerError` kind `invalid-order` and writes nothing; the message quotes only ids the caller gave (`route id X is not in the roster`, `route id X appears more than once`) and counts the ones it left out (`the order leaves out N roster route ids`). It runs under the roster's write lock through `mutateVaultRoster`, so a quota reading, decline or discovery committed meanwhile is kept, and only positions change: every row's fields and the rest of the file are written back as they were. The current order writes nothing (`outcome: 'unchanged'`); with no roster file only the empty order is accepted. It never contacts the vault. `ClaustrumConsumer.reorder(routeIds)` calls it and re-reads the roster into memory, so the next `routingRows()` in the same process uses the new order without waiting for a discovery; a plugin that calls `reorderVaultRoster` directly while also holding a consumer for the same roster sees the order in `routingRows()` only after the consumer's next refresh. `invalid-order` is a new `ClaustrumConsumerFailureKind`, so an exhaustive switch over the kinds needs a case for it.

**Grant reach (0.19.0).** `grantReach()` explains a roster the vault serves no account into. It returns `VaultGrantReach { grants, tuples }` from this consumer's latest discovery, where `grants` counts the enrollment's non-deposit grants and each `VaultGrantTuple` is `{ selectorKind, selector, operation }` (for example `{ selectorKind: 'category', selector: 'openai-native', operation: 'read' }`). Three cases matter when `snapshot()` has no rows: `undefined` is **unknown**, never zero: the vault (or the installed claustrum-client, below 0.10.0) does not send the fields, nothing has been discovered yet, or the roster in memory is a different view than the one this instance discovered (a peer process held the discovery lease); say nothing about grants. `grants === 0` is **no grant**: the remedy is `ck auth grant …`. `grants > 0` is **a grant that reaches nothing**, usually logins without the category: the remedy is on the credential side (`ck auth reclassify --from-registry`, or `ck auth set-category`), and `tuples` names the selector that matched nothing. Each discovery replaces the value, including with unknown. It is in memory only: the roster file never stores it, so older readers are unaffected. Plugins read it here and never call `listScoped` themselves; malformed fields are refused by claustrum-client's own decoder, and a reply carrying only one of the two fields reads as unknown. The peer floor stays `>=0.6.2`: an older client leaves it undefined.

**Change watches (0.21.0).** Before 0.21.0, `start()` listed the vault (`list_scoped`) on every tick, every `pollIntervalMs` (5 s by default, so 12 lists a minute), and read insula's `usage.get` once a minute. Both modules now push change notices over the route the plugin already holds, so an idle consumer in vault mode lists the vault once every five minutes and reads insula only when insula announces a change. Measured over ten virtual minutes against the test daemon, that is 0.2 lists and 0 usage reads a minute, against 12 and 1 before. Nothing on the request path changes: `authorize` and `send` behave as before.

- *Vault.* After its first discovery, `start()` opens one `watchScoped` (claustrum-client 0.12.0; detected at run time, so an older client keeps polling). The vault sends notice seq 1 at once and another whenever this consumer's visible account list changes; each carries the same `view` digest `list_scoped` returns. The consumer runs its normal discovery only when the notice's view differs from the last discovered roster's view, when a notice shows a sequence gap or a new epoch, or on the first notice of a re-subscribed watch. That discovery is the same `refresh()` a poll runs, so the roster commit, `onRoster` and the kept-receipt reconciliation through `custody.retain` all happen as before. Notices that arrive during a discovery share it: one in flight and at most one queued. While the watch is open, a tick still lists the roster every five minutes as a safety net (the watch keeps no history). It also still checks `isCustodyActive` on every tick, so leaving vault mode closes the watch and the connection as quickly as before. Since 0.21.1 the consumer opens this watch through `ClaustrumScopedCustody.watchRoster`, the entry point below for hosts without a consumer, so both follow the same rules.
- *Insula.* The consumer also holds one `usage.watch` per daemon and enrollment token. Every consumer on the same `InsulaQuotaSource` shares it, since insula admits 64 watches per process. insula knows the request by its method: subc-client does not send the `SUBSCRIPTION` flag yet, and insula does not require it. Seq 1 (which names no account) reads `usage.get`. Each later notice that names this consumer's insula provider reads it again, and a sequence gap or a new epoch reads it whatever provider the notice names. One read is in flight and at most one queued, however many notices arrive. While the watch is open the minute poll reads nothing. The four-minute freshness gate in `current()` is unchanged, so an account insula stays quiet about goes back to the plugin's own provider poll. The transport holds the watch on its own connection, and `usage.get` keeps its short-lived one. A custom transport opts in by adding `watchUsage(onNotice)`; without it the source polls as before.
- *When a watch cannot run, polling continues exactly as before.* An accepted watch always sends seq 1 at once, so a watch that closes before any notice was not accepted. It is read once to learn why (the client's own `list_scoped` confirmation for the vault, one `usage.get` for insula) and is not re-subscribed in a loop. `unknown_method` (a vault or insula from before watches), insula's `usage_watch_limit` and any other refusal insula answered (such as `invalid_request`) leave polling at today's pace until the source is released. A vault refusal is handled as the same refusal from `list_scoped` is: a revoked enrollment ends the watch, its re-subscription is refused with `not_found`, kept receipts are dropped and `onError` is called, and each later poll meets the same refusal, as before. A close the module did not explain (the vault draining, a lost connection, a timeout) keeps polling and tries one new watch five minutes later. A watch that closes after notices (a module restart or shutdown) is re-subscribed once, after a 1 s backoff that doubles for each further close in a row up to five minutes, and the new watch's seq 1 reads again.
- *State for logs.* `watchState()` returns `{ vault, insula? }`, each `watching` (a watch is open and polling is reduced as above), `polling` (no watch yet, or re-subscribing) or `fallback` (the module or client cannot watch, or refused it; polling at the usual pace). It carries no secrets. A host in local mode opens no watch and sends no vault or insula request.

**Vault watch without a `ClaustrumConsumer` (0.21.1).** A plugin whose vault mode runs `ClaustrumScopedCustody` with its own roster and its own `list_scoped` timer takes the same vault watch from custody: `custody.watchRoster(options)` returns `{ mode, close() }`. Do not call the client's `watchScoped` directly, and do not wrap a stub `ClaustrumConsumer` around the custody. The rules are the consumer's, listed above, because the consumer uses this same entry point:

- `onView(view)` asks the host to run its own discovery: `custody.discover()`, then its roster commit. It is called with the newest notice's view when that view differs from the last discovered one, when a notice shows a sequence gap or a new epoch, and on the first notice of a watch re-opened after a close. The seq 1 notice of the first watch carries the view the host's start-up discovery already read, so it calls nothing. One call runs at a time; any number of notices during it earn at most one more call, which runs only if the view still differs. A rejected call goes to `onError`.
- `view()` (optional) returns the view of the roster the host last committed. Without it, custody uses the view of its last successful `discover()`; outage probes do not count, since they commit no roster. Pass it when the host can commit a roster it did not list itself (a peer process held the discovery lease) or can fail after listing, so a failed commit is listed again on the next notice.
- `onMode(mode)` reports each mode change, and `mode` reads the current one. A watch starts in `polling` (opening, or re-opening after a close) and reports `watching` once the vault accepts it. `fallback` means it cannot run: a claustrum-client without `watchScoped` (the peer floor stays `>=0.6.2`, so it is detected at run time and nothing is opened), a vault that answers `unknown_method`, a refusal, or a watch that closed before its first notice. A watch that closed before any notice was read once by the client, is not re-opened in a loop, and is tried again after `WATCH_RETRY_MS` (five minutes). A watch that closed after notices is re-opened after `RESUBSCRIBE_BACKOFF_MS` (1 s), doubling per close in a row up to five minutes.
- A refusal (a revoked enrollment answers `not_found`) is applied by custody as a refused discovery is: every kept receipt is dropped (`listFailed`). `onRefused(error)` then lets the host handle it as it handles the same refusal from its discovery. A lost transport starts custody's outage (`transportLost()`), exactly as an unreachable `get_scoped` or `list_scoped` does, and the first notice of a watch ends it (`reachable()`). The client reconnects only for a call of its own, so after a lost connection the re-opened watch usually waits for the host's own next list.
- `close()` on the watch, or `custody.close()`, stops it and its timers; all its timers are unreferenced. `watchRoster` on a closed custody throws `closed`.

The host's job is its timer. Keep the existing list timer at its usual pace (2 s on OpenCode 1, 60 s on OpenCode 2, a few seconds on Pi) whenever `mode` is not `watching`. While it is `watching`, list only every `SAFETY_POLL_MS` (five minutes): the watch keeps no history, so this safety list catches a shed notice or a silently dead stream. Open the watch only in vault mode and close it on leaving vault mode or on dispose.

```ts
import {
  ClaustrumScopedCustody,
  SAFETY_POLL_MS,
} from '@cortexkit/common-auth/claustrum'

const custody = new ClaustrumScopedCustody({ client, family, tokenPath })
let lastList = 0
// The host's own discovery: list through custody, then commit its roster.
const discover = async () => {
  lastList = Date.now()
  await commitRoster(await custody.discover())
}
await discover()

const watch = custody.watchRoster({
  onView: () => discover(),
  onRefused: (error) => reportVaultRefusal(error),
  onError: (error) => log.warn('vault watch', error),
  onMode: (mode) => log.debug('vault watch', { mode }),
})

// The existing timer keeps its pace (POLL_MS) and lists every tick unless
// the watch is open; then it lists only every five minutes.
const timer = setInterval(() => {
  const due = watch.mode === 'watching' ? SAFETY_POLL_MS : 0
  if (Date.now() - lastList >= due) void discover().catch(reportError)
}, POLL_MS)
timer.unref()

// On dispose or leaving vault mode:
clearInterval(timer)
watch.close() // custody.close() also stops it
```

**Detached roster quota publication.** `recordVaultQuota(path, input)`,
`recordVaultAccountQuota(path, input)`, `consumer.recordQuota(routeId, observation, receipt)`
and `consumer.recordAccountQuota(routeId, accountIdentity, observation)` retain their
`Promise<boolean>` signatures and their meaning, but now **resolve after a
lock-free fence check and enqueue, never on a file write**. The fence runs against
the roster as it stands (the file, read without a lock, plus this process's
unwritten readings): `false` means the reading was refused (a replaced or other
account, an unbound route, a missing row, or a malformed observation), as in
0.22; `true` means it passed and is queued. The write applies the fence again
under the write lock, so a rebind between the answer and the write still keeps
the reading out of the file.
Do not use the acknowledgement as a durable receipt or fail a request over quota
bookkeeping. Every consumer sharing the resolved roster path updates its in-memory
quota immediately, including routing/admission; persisted-file reloads overlay
pending observations without reviving an account removed by a peer.

There is one mailbox per resolved roster path per process, one pending entry per
known account identity (or per route while its identity is unknown), and at most
one flush/lock waiter. Fields coalesce by their own freshness
rules: checkedAt per window/budget, and each counter/credits record's own checkedAt.
Receipt provenance stays attached to fields so an invalid newer credential cannot
erase a valid pending reading. A flush publishes all accounts in one mutation.
Lock failures retain the mailbox and retry with jittered backoff, with one warning
per uninterrupted failure run, not one warning per observation. The roster write
lock renews its existing 10-second lease; its 5-second acquisition budget is unchanged.

On unload, `close(): void` starts a detached bounded drain; hosts with an awaitable
dispose hook should use **`await consumer.dispose()`**. Only the last consumer of
a shared file drains/stops its writer. Custody-only hosts should call
**`await drainVaultQuota(path)`** from `/claustrum` during disposal. Its default
one-second shutdown budget can lose pending observations quietly; ordinary
publication never drops them on lock contention. Do not drain on request paths.
Discovery refreshes still retry on their next poll: after a write-lock timeout,
the discovered inventory is retained and reused only if the roster still has the
view that was current when discovery began, or already has the discovered inventory's
view. The discovery lease is reacquired and checked again at rename.

**Opt-in local pool quota publication (next minor).** The separate `/store`
API now offers a detached quota mailbox for local accounts, with any pool codec:

```ts
const store = openPoolStore({
  provider, configPath, statePath,
  quota: quotaCodec, // or the plugin's own codec, such as nativeQuotaCodec
  coalesceQuota: true,
  quotaDrainTimeoutMs: 1_000, // optional shutdown budget
})
await store.recordQuota(id, { credentialEpoch, identity }, observation)
// At plugin unload, not after each request:
await store.dispose() // or await store.close()
```

Without `coalesceQuota: true`, `recordQuota` still awaits its locked write exactly
as before. The existing `Promise<void>` signature is unchanged: current-row
refusals still reject with the same `PoolOperationError` before enqueue,
including stale epoch/identity, reserved, unbound, missing and invalid rows.
Success means accepted into memory, **not a durable receipt**. Stop plugin
producers before disposal; new opted-in quota calls after close reject. Provider
pulls already in flight are not joined by disposal; use `pullsSettled()`
separately if the host needs that join.

**Codec contract.** The mailbox never looks inside an observation. Opting in asks
nothing more of the codec than the immediate writer does: `merge(stored,
observation)` returns the new stored map (`stored` is `undefined` for a row with
no map yet) and `validate` accepts it. Each accepted observation is queued whole,
per row, and applied at flush in arrival order through the codec's `merge`:
`merge(merge(stored, first), second)`, and so on. `read()` and `load()` show the
same fold over what is stored now. So the codec alone decides which fields a
newer or older reading replaces, and keeps any fields the library has no name
for (provider metadata, money, source and identity). It must also be safe to
merge an observation into a map that another process changed after the reading
was accepted: `recordQuota` refuses a reading the codec refuses against what
`read()` shows at that moment, but a reading the codec refuses later, at flush,
is dropped alone with the warning `pool quota publication dropped; the quota
codec refused it` (once per binding) while the rest of the batch lands. With
`quotaCodec`, `mergeQuotaObservation` keeps its per-key times: pending windows,
coverage, spend budget, counters and credits keep their own timestamps, partial
headers cannot erase poll-only fields, a header merges into a poll in either
arrival order, and late older polls lose to newer observations both in memory
and against disk. Equal times use the last enqueue.

Each opted-in store handle owns one mailbox and at most one flush/lock waiter,
batching accounts in a single config transaction. Use one long-lived handle per
local pool. Its `read()` and `load()` overlay pending quota immediately, including
clearing `needsFirstReading`. Other handles/processes see only committed quota.
Every queued reading keeps its row, credential epoch and identity binding;
different bindings never coalesce. The locked flush checks the current row again
and drops a stale binding with one stable warning, `pool quota publication
dropped; account binding changed`, rather than attaching it to a replacement.

Each row queues at most 128 readings. Hosts record
one about every 100 ms at most, so for them a full queue means another writer
has held the store locks for many seconds. Reaching the cap starts a flush at once
instead of waiting for the coalescing timer or a retry backoff. A further
reading for that row is never dropped and never displaces an older one: its
`recordQuota` waits for room for up to the store's own lock budget (the longest
`timeoutMs` of the store locks), then rejects with a retryable
`lock-contention` `PoolOperationError`, just as the immediate writer would after
the same wait. A reading still waiting when `close()` finishes its drain is
refused then as closed.

Lock attempts are capped at 100 ms for the detached writer only. Failed attempts
keep every queued reading and retry with jittered exponential backoff, warning
once per uninterrupted failure run. `close()` and `dispose()` are idempotent
promises for a bounded drain (default one second). A timed-out drain logs the
remaining account and reading counts with `pool quota drain timed out; pending
readings left` and stops retries; shutdown can lose those pending readings. They
are no-ops for the immediate writer. The existing atomic config writer and its
Windows private file handling are unchanged.

**Optional insula background quota.** Supply `insula: { provider: 'codex' | 'claude' | 'antigravity', normalize(entry, context) }` to `ClaustrumConsumer<Q>`; `Q` is the plugin's snapshot type (defaults to `/quota`'s `QuotaObservation`). `context` exposes `fetchedAt` as epoch milliseconds and `source`, and the entry retains the original timestamp and open usage fields. A normalizer returns `Q`, or `undefined` to keep the plugin's own poll. `connectClaustrumScopedClient` supplies an optional `insula` transport without changing its scoped methods; custom scoped clients can supply `insula: { connectionFile, getUsage(), watchUsage? }`. The transport imports the `@cortexkit/subc-client` peer statically: claustrum-client already loads it with `/claustrum`, and a dynamic import would make a plugin's bundler emit a separate chunk that a running host can lose on rebuild. The transport opens the literal management surface `insula` on the same daemon connection file and bind identity, and reads the full `usage.get` envelope. The quota read uses a short-lived, separately owned socket; the scoped credential connection is untouched. It does not resolve a catalog claimant by capability and needs no grant beyond the enrolled principal.

The source is process-local and refcounted by **resolved daemon connection file plus enrollment token path**, not project or provider. Consumers with the same pair share all entries and one attempt per minute, including concurrent ticks and failed attempts; different pairs never share. `close()` releases the consumer's reference, while the minute budget survives project unload/reload. No polling timer is added: `start()` drives it on the existing metadata tick, or a plugin's own background loop can explicitly `await consumer.refreshInsulaQuota()` once before visiting accounts. Neither `authorize` nor `send` calls insula. Local/standalone mode and a missing or unreadable enrollment token never call it.

For background polling, after the tick's `refreshInsulaQuota()`, use **`await consumer.pollInsulaQuotaForRoute(routeId, fallback)` (0.22.0)**, where `fallback` is the existing due-account provider poll. It returns the normalized current reading without calling `fallback`, calls `fallback` only for `stale`, `absent`, `credential` or `unreachable`, and returns `undefined` without polling on `cold` or `upstream-failed`. It logs `skipped insula provider poll` once per route/account reason transition, with only `{ reason: 'cold' | 'upstream-failed' }`, never an identity, email or route id. A successful lookup or an allowed fallback resets the once-per-transition logging state. The wrapper does not schedule polls or persist readings: enqueue an insula observation with `await consumer.recordAccountQuota(routeId, row.accountIdentity, observation)`, which updates memory immediately and publishes detached, only while the route is still bound to that known account (it never binds one). In-band `recordQuota` updates use the same shared mailbox and retain their receipt fence.

**`consumer.lookupInsulaQuotaForRoute(routeId): Promise<InsulaQuotaResult<Q>>`** exposes `{ reading: Q } | { miss: InsulaQuotaMiss, reading?: Q }` for callers needing a dated stale display. Both new methods re-read the persisted roster and use its known `accountIdentity`; they never authorize or call `get_scoped` just to ask the cache. An unbound row cannot match, and a known replacement committed by another consumer invalidates the old route even before this instance's next metadata refresh. A normalizer refusing an echo or unsupported reading is `unreachable` for fallback purposes. **`cachedInsulaQuotaForRoute` remains unchanged** (`Q | undefined`, all misses return `undefined`); existing callers must switch to the wrapper to suppress duplicate polls. The row's identity comes from `list_scoped.account_id` (the same vault identity as `get_scoped.account_id`), or from an asserted/parsed served receipt bound by `recordQuota`; identity omissions retain that last known binding. For an insula provider, **`parseIdentity` must return the same provider identity insula keys on for a vault record without `account_id`**; for Codex, that is the token's **ChatGPT account id**, not an email or display label.

For unknown-quota admission with a served receipt, use `await consumer.cachedInsulaQuota(receipt)`, then the existing one-shot provider poll on a miss. This method still joins only the receipt's **`assertedAccountIdentity`**, the unmodified `get_scoped.account_id`; parsed/expected receipt identity cannot substitute. Both lookups read the insula cache only: never call `refreshInsulaQuota` on the request path. The account join is exact: `entry.provider` equals the configured insula provider and `entry.account.trim()` equals the chosen provider account identity. Neither method joins on email, label or `accountInfo`. An entry is current only with `usage`, no `stale` or `errorClass` field, and a parseable `fetchedAt` less than four minutes old by the injected clock. Error text is never inspected. Missing accounts fall back individually, even in a partial response. `completeProviders` alone signals completeness; this source never prunes vault accounts, and neither `pending`, array count nor stability implies completeness.

All route refusals (`unknown_module`, `module_removed`, `module_warming`, `target_unavailable`, `module_reloading`, `capability_denied` and future codes), module errors and malformed envelopes or a hung call mean the optional source is absent for that tick, clearing its cached entries so even a previously young reading cannot suppress fallback. The transport makes one `route.open` and one `usage.get`, with no managed retry or waiting for a warming module. A three-second whole-call deadline bounds connection setup, route opening and the read; its timer is unreferenced so a pending optional call cannot keep an otherwise idle host process alive. The separately owned socket is closed on success, refusal and expiry (including a connection that resolves late). Provider polling, response headers and WebSocket quota handling otherwise stay unchanged.

**Without a `ClaustrumConsumer`.** A plugin whose vault mode runs on `ClaustrumScopedCustody` and its own roster reads insula through the same source directly (since 0.19.1). `acquireInsulaQuotaSource(transport, tokenPath)` takes the `insula` transport of its custody connection (`connectClaustrumScopedClient(...).insula`) and its real enrollment token path, and returns `{ source, release }`. Sources share the key and minute budget described above; call `release()` once on dispose. Use it only while the host is in vault mode, read freshly at the start of each background tick, and skip the tick otherwise. On the tick, `await source.refresh(now)` once, then call `source.current(provider, accountId, now)` for each vault account, where `accountId` is that row's vault `account_id`. `current` applies the same exact join and freshness gate (no `stale` or `errorClass`, `usage` present, `fetchedAt` under four minutes) and returns `{ entry, context }` or `undefined`. A hit means normalize it under the obligations below and skip that account's own poll. A miss means run the plugin's poll for that account immediately. On the request path call only `current`, never `refresh`. Since 0.21.0 such a plugin can also hold the insula watch described above with `const stop = source.watch({ provider })` while it is in vault mode, and call `stop()` when it leaves vault mode or disposes. `refresh(now)` then reads nothing while the watch is open, and `source.watchMode()` reports `watching`, `polling` or `fallback`. Do not wrap a stub `ClaustrumConsumer` around a custody connection to reach insula: a live consumer runs discovery and roster work of its own.

**Classified background misses (0.22.0).** Direct-source hosts such as anthropic-auth should replace their background `current()` call with **`source.lookup(provider, accountId, now): InsulaQuotaLookup`**. `current()` is unchanged for compatibility and request-time use. `lookup` returns `{ reading: { entry, context } }` on a current hit, or `{ miss, reading? }`; `stale` retains its parseable, usage-bearing reading so it can be displayed with its original date, not merged as fresh. `/claustrum` exports `InsulaQuotaMiss`, `InsulaQuotaReading`, `InsulaQuotaLookup`, and the normalized `InsulaQuotaResult<Q>`.

| Miss | Wire mapping and background action |
| --- | --- |
| `cold` | Successful `result` snapshot, no matching entry and provider absent from `completeProviders`: wait, no own poll. Neither `pending` nor entry counts establish completeness. |
| `stale` | Matching usage-bearing entry has a `stale` field or its `fetchedAt` is at least the existing four minutes old: own poll allowed; retain the dated reading. |
| `upstream-failed` | Matching entry (or unlabelled provider error) has `errorClass: 'upstream_failed'`: no own poll, even if the entry is also stale. Another labelled account's error never supplies this verdict. |
| `absent` | Successful snapshot names the provider in `completeProviders` but has no entry for this account: own poll allowed. Insula does not cover the account; this says nothing about credential health and does not remove a vault account. |
| `credential` | `errorClass` is `credential_absent`, `credential_unusable` or `credential_rejected`: own poll allowed. This does not remove a vault account. |
| `unreachable` | No successful snapshot, route refusal, module error, malformed answer/reading, three-second deadline, unknown/other error class, or expired cold wait: own poll allowed. |

Field authority: insula's [`docs/consumer-contract.md`](../../insula/docs/consumer-contract.md), lines **70–98** (`result` snapshots and in-band failures), **253–286** (`fetchedAt` is producer reading time; failures do not advance it), **422–467** (open `errorClass` vocabulary, `upstream_failed` includes 429/5xx/network; never branch on error prose), and **1214–1243** (`completeProviders` is a sibling of `result`, unknown is not empty, cold starts name nobody). The cold wait is **120,000 ms per provider from its first cold lookup**, shared across accounts/projects using the source, not restarted on each poll. This is a consumer fallback bound of two 60-second refetch intervals from contract **331–336**, not a claim of sweep completion: the contract deliberately does not guarantee a global sweep duration and warns against inferring completeness from elapsed time (**177–182**). A later successful snapshot naming the provider in `completeProviders` resets the bound, even if no lookup occurs while it is complete.

**openai-auth adoption:** its `packages/core/src/vault.ts` background `#pollQuota` currently calls `refreshInsulaQuota`, tries the cache, then falls through to `consumer.send` and `whamUsageFn` on every miss. Switch that background branch to `pollInsulaQuotaForRoute(routeId, fallback)`, moving the existing vault-authorized Wham poll into `fallback`; keep account-bound `recordAccountQuota` for usable insula results and the existing receipt-bound writes for Wham. Treat the wrapper's skipped `undefined` as deferred, not as permission to fall through a second time. Preserve per-route single-flight and the `requestReading`/`pollQuota(routeId, false)` request-time path. Update the dependency from 0.21.x to 0.22.0 and tests/log reasons that currently collapse misses into `no-insula-reading`; no plugin files are changed here.

**Normalizer obligations:** set **every window's reading time to `context.fetchedAt`**, never the tick time (for `/quota`, set `QuotaObservation.checkedAt`). The plugin's existing newest-per-window merge then protects newer in-band readings. Walk the supported slots and `extraRateWindows`; do not invent absent windows or identify accounts using their display metadata. Codex must use **`rawUsedPercent ?? usedPercent`** per window, because insula's effective percentage can relax a limit using saved resets while the auth plugin needs the provider's unrelaxed usage. Antigravity must refuse its own echo: accept only when **`source === 'vault'` or `context.fetchedAt` is newer than the plugin's last reading**. That policy belongs in antigravity's normalizer, not this library. Returning `undefined` for an echo, an unsupported shape or an unusable window leaves the existing poll in charge.
**Token acquisition (0.20.0; connection outage state).** While reachable, every physical send calls `get_scoped` first, without single-flight, and each `dispatch` gets its own receipt. After a validated read, custody keeps one last-known-good receipt per vault credential/account binding **in this process's memory only**. The first unreachable vault call (`get_scoped`, `list_scoped`, or a watch losing its transport) starts an outage for that custody instance/connection. During the outage, authorization re-reads enrollment authority and immediately issues a usable kept receipt **without waiting for any vault call or reconnect**, using that token or API key, its original record version, identity, expiry and served metadata (including `projectId`). An account with no kept receipt instead tries a normal fresh `get_scoped`: success ends the outage, while an unreachable call refuses with the existing unreachable error. It pays the connection wait because there is nothing kept to serve. OAuth fallback needs **more than 60 seconds** until expiry; an API key without expiry remains usable. Nothing is written to disk or shared between processes, and a process that never received a token cannot serve while the vault is unreachable. Exclusive vault mode never uses local accounts. Metadata remains coalesced; failed discovery leaves the existing roster and routing in place.

`VAULT_FAILURE_CLASSES` is the exported, frozen code classification table; `classifyVaultFailure(error)` also recognizes native subc socket/connect errors. Only reviewed connection/timeout/route-unavailable codes permit reuse, not a transient action by itself. All unknown codes, malformed replies, account refusals and adapter shutdowns fail closed and discard the kept receipt. For injected adapters whose connect fails before `getScoped`, throw **`new ClaustrumUnreachableError()` only for an unreachable transport**; never wrap shutdown, cancellation, validation errors or vault refusals. This marker preserves `ClaustrumConsumerError.kind === 'unavailable'`: no new error kind needs handling. A fallback receipt adds optional `fromKeptReceipt: true`, not a new error. Custody-only hosts must call `retain(currentRosterRows)` after roster updates, `forget(credentialId)` on removal/decline/rebinding, and `close()` when enrollment authority is no longer `vault`. The consumer does this automatically, including observing peer roster changes before dispatch.

Any answered refusal, identity contradiction, missing enrollment, roster removal/rebinding/disable/decline, or disconnect immediately discards the affected receipt (discovery refusals and missing enrollment files clear all custody receipts). A **401 using a kept receipt** discards it, performs **no retry and no vault report**, and logs that it was not reported. That account needs a successful fresh vault read before it can send again. Direct custody hosts must still call `reportFailure` on that 401; the shared rotation predicate also refuses retries of kept receipts. `keptReceiptState()` on consumer or custody returns a frozen `{ active, since }` summary, with no identity or bearer material. An outage logs one warning and recovery logs one info line, both containing only a fixed reason class, never a route, account identity or token. Kept sends kick a non-blocking `list_scoped` probe, at most once per second and with at most one probe in flight across sends and timers; the send never waits for discovery. A failed send-triggered probe does not increase the backoff or delay the next send-triggered probe beyond that one-second limit. The idle recovery path still starts after 2 seconds, doubles its delay on failure up to 30 seconds, and uses an unreferenced timer that `close()` cancels. `close()` also prevents new probes and ignores late probe answers. Listing is supported even without watches and does not fetch bearer material; watch recovery would still require a confirming list. A successful probe or any other successful vault call (including watch acceptance) ends the outage; an answered probe refusal also ends it and applies the existing discovery drop rules. The next authorization fetches a fresh receipt/version from the vault. Recovery resets the probe delay to 2 seconds. Loggers may implement optional `info`; otherwise recovery uses the default info logger.

Fresh OAuth reads still demand `minTtlMs` 300 000 and refuse a served token with less validity; API keys have no TTL demand and may have no expiry. A 401 on a freshly fetched receipt is retried once only when another fresh `get_scoped` serves a new record version of the same credential and account; final 401 reports retain the exact failing version and enrollment authorization. 429, 402 and 5xx are never reported. After a reported 401 the consumer refreshes the roster in the background so cold accounts leave routing before the next poll.

**Enrollment.** Propose and poll run only in `ClaustrumEnrollmentManager.reconcile()`, which setup calls; `ClaustrumConsumer` never enrolls, and a missing token fails a send with `not-enrolled`. The request secret is written (0600, under the `ceremony` lock beside the state file) before the propose call, so a restart between propose and poll resumes the poll, and a crash before the request id is saved re-proposes with the same secret (the vault returns the same request id). The token is written before the pending state (and its secret) is replaced. Terminal codes `invalid_params`, `pending_exists`, `not_found`, `already_consumed`, `superseded`, `stale_generation` block the ceremony and scrub the secret whatever action the client reports; `pending_queue_full` is always retried; other codes follow the client's action. The token and state directory is created 0700 and an existing one with group or other bits is tightened to 0700; files must be owner-only regular files (no symlinks) under no group- or world-writable non-sticky ancestor.

**Exclusive vault mode.** Each unit of work—requests, background ticks, menu renders and sidebar writes—checks `enrollmentAuthority(paths, proposedName)` when it starts. An approved enrollment selects vault accounts exclusively; local accounts are neither used nor touched. Disconnect is the reverse transition and selects local accounts. Work already in flight when the mode changes may finish, and a local refresh that completes after the switch still persists its successor because the previous refresh token has been spent. Consumers observe the switch within their enrollment-file poll interval. An unreadable enrollment refuses with a fixed message rather than choosing either account source.

**Disconnect (0.13.0).** `disconnectClaustrumEnrollment(paths, proposedName)` is the disconnect for every plugin; none deletes the enrollment files itself. Removing the token alone is not a disconnect: an approved state without a token is still vault mode and refuses, by design. Under the same `ceremony` lock `reconcile()` and `resetClaustrumEnrollmentState` take (held elsewhere: `busy`, nothing deleted), it refuses state that names another consumer (`wrong-consumer`, both files unchanged), then removes the token and then the state, and `enrollmentAuthority` reports `local`. A crash between the two deletions leaves an approved state without a token, which is still vault mode (refusing, never falling back), and calling it again finishes. It returns `idle` when neither file exists, removes nothing else in the directory, and removes the token without parsing it, so a corrupt token does not block it. A malformed state file (bad JSON or wrong shape, which makes `enrollmentAuthority` report `unreadable`) is removed too: the path is per host, so the file is this host's, and disconnect is the remedy the plugin names for `unreadable`. A state file that fails the safety checks (symlink, wrong owner, not owner-only) refuses with `unsafe-file` and both files stay, because it is not provably this host's. It never contacts the vault: the enrollment stays approved there until the operator revokes it, and a later Connect starts a new ceremony. A pending request is abandoned the same way. `resetClaustrumEnrollmentState` still clears only terminal state and still refuses while a token exists. Replaces openai-auth's unlocked removal of both files.

**Discovery and the view cursor.** `list_scoped` returns `view`, a digest over this consumer's visible credentials, grants, state and identity, not over `record_version`. `onRoster` fires once per view change (the first roster included); a token refresh never fires it. An absent `account_id` is no claim, not a failure. A record the consumer cannot use (empty id, duplicate id, blank identity, empty state) is skipped with a `logger.warn('skipped malformed vault record', { credentialId, reason })` (a safe id, omitted when the id itself was unusable, and one of four fixed reasons) and the rest of the list is used. Such a reply is incomplete: the roster records `complete: false` and `rejected` (the same id and reason pairs), and no previous member the reply does not account for is removed. A member is unaccounted for when its record was rejected, or when any rejected record has no usable id (it could be any of them). An unaccounted member of a live account stays one of its aliases; an account with no member listed stays as its last good projection marked `stale`. A credential the same reply lists under a live account is taken out of every stale row (the next remaining member becomes the stale row's credential), so one credential is never authorized or quota-recorded under two account bindings; a stale row left with no member is dropped rather than kept as unavailable (the primary hook reads the inventory, not stale rows, so it is unaffected). A valid newcomer is added either way, and only a complete reply removes an account. The client's own decoder still refuses a whole reply whose rows are wire-malformed (a non-string id, a non-array field); that fails safe (the last committed roster keeps serving) and is declared below. Several records logged into the same provider account collapse into one row (active first, then the existing binding, then by id), listing the rest as `aliases`. There is no main: the record named `oauth:<provider>` is an ordinary pool account. The discovery lease (`claustrum-roster`, 30 s, renewed) covers the list call and the commit; a run that lost it is refused at commit, a peer holding it means the last committed roster is served, and a failed list or custody switching off mid-run writes nothing.

**Route ids.** `<routePrefix><credentialId>` plus `~<10 hex of sha256(identity)>` when the account is known; a reserved local id gets a numeric suffix. A route keeps its id and quota while its credential keeps the same account (an identity learned for the first time counts as the same account); a credential that now logs into a different known account gets a new id and no quota. A record listed without an identity keeps the last account it was known to log into (as representative or alias), and the row is marked `unclaimed`: the omission is neither proof of continuity nor of replacement. When the account comes back the route continues; when a different known account appears, it is a replacement and inherits no route id, quota or decline. A record that claims the account is preferred as representative over one only remembered as belonging to it.

**Receipt identity.** A receipt's `accountIdentity` is what it is bound to: the vault's assertion, else the plugin's parse of the token, else the roster's expectation, and `accountIdentitySource` says which (`asserted`, `parsed`, `expected`, `none`). `assertedCredentialId` and `assertedAccountIdentity` hold only what the served reply itself said and are never filled from the roster or a parse; `expectedAccountIdentity` is the roster's account at request time. With `requireAssertion` a receipt is refused (`identity-unasserted`) unless the reply asserts the credential id and the expected account and the roster's account is known; a different asserted account is `identity-changed`. Receipt validation (safe-integer record version, serving margin), the fresh `get_scoped` per physical attempt, the one bounded 401 replay on a different version of the same credential and account, and reporting against the failing send's own receipt are unchanged by this.

**Primary hook.** The library has no main. A plugin that keeps a host-owned main calls `resolveVaultPrimary` with its filtered inventory, whether it is complete, the previous verified binding, the request's expected account (on the request path) and the record id that holds the role. Main follows the account that record claims; another credential of that same account may serve it when the record is not active, and no credential of another account is ever promoted. A complete inventory without the record is `absent` (`authorize('main')` should fail; ordinary fallback routing is unaffected but must not be renamed main). A rejected primary record (`malformed`), a record without an identity claim (`unclaimed`), or a reply with a rejected record of unknown id or `complete: false` (`incomplete`) is `unavailable`, never absent, and hands back the last verified binding untouched; continuing to serve it still needs a fresh receipt that matches it (`requireAssertion`). A known different account is `ready` with `replaced` set to the previous binding: the plugin drops quota, profile, backoff and cache affinity owned by that account and fences outstanding observations, while the logical route and the host slot or device identity stay. A request whose expected account is no longer main's is `unavailable` (`identity-changed`).

**Declined-account interlock.** The consumer keeps declines in the roster file, keyed by account (or credential id while the account is unknown), never by record version. A decline follows the provider account: an entry made while the account was known matches every credential id and alias that logs into that account, so relabelling, a new alias, or removal and return keep it declined. A credential id that now logs into a different known account does not match; that account has its own policy, and the declined account's entry is kept (entries are never pruned). While the account is unknown on either side the entry matches by credential id. `accept` lifts every entry that declines the accepted route's account and credential ids, and leaves a different account's entries alone.

**Host slot.** In custody mode the host slot holds `custodyPlaceholder(provider)` (an OAuth-shaped value with an empty access token). `assertHostSlotMatchesMode` fails closed on a real login in the slot under custody (anthropic-auth's behaviour, and the answer to openai-auth #173: serving either the host login or the vault would silently pick one of two accounts the user may not mean, so the plugin refuses until the user leaves custody or removes the login) and refuses the placeholder in local mode; `assertNotCustodyPlaceholder` guards a local refresh.

**Differences from each plugin today.**

- anthropic-auth: no main and no `oauth:anthropic` convention in the library; the plugin keeps its main through `resolveVaultPrimary` with `primaryCredentialId: 'oauth:anthropic'` and `requireAssertion: true`; the roster lives in its own file instead of anthropic's account config, so `disabledAccountIdentities` becomes the account-keyed interlock (same account-level semantics) and a declined account no longer lifts when a local row is re-enabled; a row with no identity is accepted (anthropic refused the whole inventory), but under `requireAssertion` it is not served; a malformed record is skipped instead of refusing the list, and the reply is then marked incomplete and removes nothing; `fetchQuota`/`fetchProfile` become the plugin's `dispatch` closures through `send`; the provider-specific `ScopedRetrySite` union becomes a string; logging goes through an injected logger; host enrollment paths come from a plugin-supplied state directory instead of `XDG_STATE_HOME` and `*_ANTHROPIC_AUTH_CLAUSTRUM_ENROLLMENT_FILE`; poll `pending_queue_full` with action `gone` now retries; the enrollment directory is tightened to 0700.
- openai-auth: replaces handle-based custody entirely (handle files, `credential.get` by handle, its cache); vault accounts join the flat pool as routing rows. It leaves `requireAssertion` unset, so a vault reply without an account still serves (its JWT parse is recorded as `parsed`). `recordQuota` now requires the receipt: a caller that kept only `{ accountIdentity }` (the Pi runtime's token association) must keep the receipt, or at least its `credentialId`, `accountIdentity`, `expectedAccountIdentity` and `accountIdentitySource`. `pruneDeclined` is gone (no caller there).
- antigravity-auth: has no custody today; adopting is additive.

**Declared limits.**

1. **Wire-malformed rows.** Skipping per record works for records the client decodes. A row the client's decoder rejects (wrong JSON types) still fails the whole `list_scoped` call inside `@cortexkit/claustrum-client`; the consumer keeps serving the last committed roster. It must be a deterministic function of the frame, stable per session; it may add `input` items or settings fields but must never alter, drop or reorder the items the host put in `input`, nor touch `previous_response_id` (see below); `attempt` is `undefined` for a frame no attempt can be tied to, and the rewrite still runs |
| `quotaFromHeaders?(headers, status, attempt)` | quota in HTTP response headers |
| `limitFromResponse?({status, headers, body(), attempt})` | an account-level refusal from an HTTP response before streaming; `body()` reads a copy |
| `inspectEvent?({transport, data, event?, attempt})` | one SSE event's `data` or one WebSocket frame → `{outputStarted?, quota?, limit?, done?, error?}`; `done` (last event of the response) or `error` (the response failed) ends the attempt |
| `limitFromError?(error, attempt)` | a refusal recognised only from the error the retry hook receives |
| `onAttemptEnd?(attempt, {status?, outputStarted, limit?, error?})` | called once per attempt when it ends (rules below); `error.reason` is `failed`, `cancelled` or `abandoned`, absent when the response completed whatever its status. The retry hook waits for it to settle |

Options: `gateOnPlaceholder` (opt-in request ownership, below), `hostCredentials` (values that must never reach the wire on owned requests; default `[placeholderSecret(providerID)]`), `maxRecords`, `logger` (`{warn}`).

**Request ownership (opt-in since 0.11.8).** Auth plugins must enable `gateOnPlaceholder: {credential(headers: Headers): string | undefined}` to act only when the user chose their own login method. OpenCode 2.0.22 does not expose the selected connection or method on request hooks: `model.request` runs before auth, while the transport hooks see the prepared credential for that request. The extractor must read that credential from the supplied headers, not reread `connection.active()` or other global login state. The installer compares the extracted secret byte for byte with `placeholderSecret(adapter.providerID)`: no prefix match, placeholder parsing, metadata test or provider-wide takeover. After a successful plugin login, `registerOpenCode2AuthMethods` waits for the plugin's `onLogin` callback to save the real account in its pool, then returns only the placeholder to the host. The placeholder is a synthetic marker, not a provider-issued credential, so it cannot authenticate an upstream request.

**Login method ownership.** Register the plugin's OAuth methods under method IDs it owns; do not replace an existing host login such as a built-in ChatGPT method. After a user signs in through the plugin's method, the plugin stores the real account in its pool and returns OpenCode a placeholder: a synthetic, non-provider credential that keeps the login method connected in the host. Refresh renews only a placeholder belonging to that integration and refuses every other credential, so an existing host login stays stored as-is. To import an existing login, read it through `ctx.integration.connection` instead of claiming its method ID or relying on refresh to convert it.

For an OpenAI bearer header:

```ts
await installOpenCode2Auth(ctx, adapter, {
  gateOnPlaceholder: {
    credential(headers) {
      const value = headers.get('authorization')
      return value?.startsWith('Bearer ') ? value.slice(7) : undefined
    },
  },
})
```

For an Anthropic `x-api-key`, return `headers.get('x-api-key') ?? undefined`; if the driver instead uses Authorization, extract that prepared secret with the same literal bearer-scheme check. An adapter supporting both must choose the header its driver uses for that request, rather than treating an unrelated header as authorization. Scheme removal is the extractor's responsibility; the installer neither parses nor partially matches the secret.

With this option, `model.request` makes no changes and chooses no account. Each owned HTTP send or WebSocket handshake chooses its own attempt at the transport hook, so even concurrent HTTP attempts of the same session and kind need no correlation header. No internal mark is exposed to intervening plugins. The legacy path without the option still sets `ATTEMPT_HEADER` in `model.request`; intervening plugins can see that internal mark, and the transport hook strips it before dispatch.

A different credential (API key, host OAuth bearer, absent value, or placeholder with extra bytes) passes through with the same URL, headers, body and request object; this transport creates no attempt, adapter callback, event, response rewrite or attribution. It still contributes foreign transport history that can affect later retries in a mixed session. With `refuseMisplaced`, a header containing the placeholder with extra bytes is instead a placement refusal. Ownership is checked anew on every transport call, so switching logins takes effect on the next request. A non-owned handshake also disables outgoing frame rewrites and incoming frame attribution for that session and kind, even if an older owned attempt remains held. Owned sockets still rewrite every frame, including after the previous attempt ended: the host builds incremental turns using `previous_response_id` from its own unmodified history, so the adapter must apply the same deterministic edits at every frame boundary (see the WebSocket rewrite policy below). Forgetting a session clears socket and latest-transport ownership, but retains foreign ownership history for delayed retries under a reused session id; only disposing clears all ownership history.

Owned-only transforms reuse the existing adapter seams: put HTTP endpoint and body rewrites (including removing OpenAI `max_output_tokens`) in `rewriteRequest`, WebSocket endpoint changes in `rewriteHandshakeURL`, session/account headers such as `session-id` in `accountHeaders`, and WebSocket body edits in `rewriteWebSocketFrame`. Do not make provider-wide edits in separate `model.request` hooks. All these seams now run only for owned traffic when gated. Account refusal fails locally at the transport hook before dispatch, and the wire guard still refuses any placeholder left after account headers are applied. On gated requests the placeholder is always forbidden, even if `hostCredentials` is customized. Without the option, account choice, headers, rewrites, attribution and retry behavior are unchanged from 0.11.7.

**Placement refusal (opt-in).** `gateOnPlaceholder.refuseMisplaced?: (header: string) => string` counts every header containing the provider's exact placeholder before account selection. If any carrier exists, exactly one must carry it and `credential(headers)` must return that secret; otherwise `OpenCode2AuthError` with kind `placement-refused` and the callback's message stops HTTP or WebSocket before `chooseAccount` or `accountHeaders`. With this option only, `rewriteHandshakeURL` runs before account headers are applied to the handshake draft, so an origin refusal cannot leave a served secret in it. Without the option, including openai-auth, anthropic-auth and antigravity-auth's existing installations, placement and handshake success/failure order are unchanged.

**Mixed-ownership compatibility change.** The retry taint intentionally changes every `gateOnPlaceholder` installation, including openai-auth and anthropic-auth, not just claustrum-auth. Owned-only sessions still reroute as before. Login switches, title/compaction calls with another credential, per-request user keys and opt-in placement refusals all taint a session, even without overlapping calls. In particular an opencode-go session mixing OpenAI-shaped owned models with Anthropic-/Google-shaped refused models loses account failover. The host retains its backoff and give-up decisions for that session's remaining lifetime. `session.deleted` and exported `forgetSession` do not clear foreign history: an already-sent foreign call can retry after the id is reused. A reused mixed id remains mixed until `dispose()` (normally process exit); a new session id is clean. Memory is two flags per session that saw foreign traffic, plus live owned-only sessions. The host's terminal execution events do not reset taint: no real-host proof yet establishes that every model request belongs to an execution period and that its terminal event arrives before the next period's transport hooks. A failure before any transport hook is outside this taint. Treating an opt-in placement refusal as neither owned nor foreign would need proof that the real host preserves the installer's error identity in retry, which is not yet established.

**What it gets.** `installOpenCode2Auth` registers `model.request`, `http.request`, `http.response`, `experimental.ws.handshake`, `experimental.ws.receive` and `retry`, holds every attempt still needed for attribution (`maxRecords` of them at most, oldest abandoned and dropped first, cleared on the host's `session.deleted` event or `forgetSession`), and returns `{on, accountFor, forgetSession, size, dispose}`; `accountFor(sessionID, kind)` names the account of the newest attempt of that session and kind (each attempt's own account is on its handle), `size` counts held attempts. Every event that belongs to an attempt carries it as `handle` (`retry` already uses `attempt` for the host's retry count). Events: `select` (with the hook that picked), `quota` (attributed through the record, since neither headers nor frames name the account), `limit` (`via: http | ws | error`, with `outputStarted`), `retry` (`reason: reroute | hold | output-started | no-account | host-decides-last-account | host-decides`, host and final decisions; `host-decides-last-account` is a limit before output with no other account to reroute to, `host-decides` no recognised limit). Listener errors are logged and swallowed. The retry hook awaits every `limit` listener before asking for the retry, so a plugin that records the rate-limit mark there has it in place when `chooseAccount` runs again.

**Attempts (library decision).** An attempt is one physical send: `{attemptId, providerID, modelID, sessionID, agent, kind, accountId, transport, data, reboundFrom?}`, created when the account is chosen, in `model.request`, or in `http.request`/`experimental.ws.handshake` when no attempt is waiting for that send (the host skipped `model.request`, or a second send of an attempt that already went out). `transport` is `undefined` until a transport hook has carried the attempt. `data` is what `accountHeaders` returned as `attempt`. Several attempts of one session and kind can be open at once (two concurrent `generate` calls of one session, say), each on its own account. The attempt is handed back on everything that belongs to it, and attribution follows fixed rules, so an event that cannot be tied to an attempt reaches no adapter callback and no listener rather than a wrong one:

- a send belongs to the attempt `model.request` started for it. The hooks name only the session and kind, so `model.request` marks its headers with the attempt (`ATTEMPT_HEADER: attemptId`); the host builds both the HTTP request and the WebSocket handshake from the headers `model.request` leaves (checked on 2.0.22 by the placement contract), so `http.request` and `experimental.ws.handshake` find their attempt by that mark and remove it before anything else sees the request (`rewriteRequest` included): it never reaches the wire, and the WebSocket, which the host keys on the handshake headers after the hook, is still reused. A send without a mark (a host or plugin that dropped it) goes to the newest attempt of its session and kind if that one has not gone out yet, as before marks existed, with one `warn` when several attempts were waiting; a mark naming an attempt of another session or kind is ignored;
- an HTTP response belongs to the attempt whose `http.request` produced its request object, and its body events to the same attempt. A response on any other request object is dropped (one `warn` per installation): the host hands `http.response` the very object the `http.request` hooks left, so another object means a later plugin's hook replaced it, and nothing proves which send it answers. Recency cannot: an earlier attempt's send may still be in flight, and its late response (or an older credential version's 401) would land on the newer attempt. The mark cannot do it either, since it is gone from the request by then. If another plugin must replace the request, its `http.request` hook has to run before this installer's, which then registers the object it builds from that replacement;
- a WebSocket frame names no attempt, so attribution there stays serial per session and kind: a frame belongs to the newest open attempt of its session and kind that went out over WebSocket (its handshake ran). An open WebSocket attempt is abandoned as soon as a newer attempt of its session and kind begins (`model.request`) or goes out over WebSocket (its handshake), because the host runs one exchange at a time on a session's socket and nothing in a frame could tell two exchanges apart; a frame after a newer `model.request` but before its handshake goes nowhere. Two WebSocket exchanges of one session and kind overlapping on the wire therefore cannot both be attributed: the earlier one stops receiving frames at the later one's handshake, and any late frame of it would be read as the later one's;
- the retry hook names only the session, so it judges the attempt chosen as described under the retry policy, and hands that attempt, and no other, to `limitFromError` and the `retry` event.

An attempt ends once: an HTTP body read to the end, errored (`failed`) or cancelled by the host (`cancelled`, with `outputStarted` as observed); an HTTP response with an error status or no body, at once, with its status, so the end does not depend on whether the host reads an error body (the host does read it); an event verdict with `done` or `error`; a transport hook (or `answeredBy`) that throws (`failed`); or `abandoned`, when it can no longer be observed: it was on WebSocket, or the retry hook had already judged it, when a newer attempt of its session and kind began; another attempt of its session and kind went out over WebSocket; its session was forgotten; it was dropped for space; or the installation was disposed. A newer attempt does not abandon an HTTP attempt still waiting for its response, nor one chosen in `model.request` and not yet sent: either may still be answered, and its response names it. The host has no hook for a WebSocket closing or a turn being cancelled on WebSocket, so such an attempt ends `abandoned` at the next of those points; a plugin should flag `done` on the provider's terminal events so a WebSocket attempt ends when its response does.

**Adapter-internal account change (library decision).** An adapter whose own sender can move a request to another account (a bridge behind `rewriteRequest` that answers a 401 or 403 from the chosen account by retrying on the next one) supplies `answeredBy`. It runs first in `http.response`, before quota, refusal, output and end detection, and returns the account that actually answered (`{accountId, data?}`, read from whatever the sender reports, a response header say) or `undefined`. A different account rebinds the attempt: `accountId` becomes the answering account, `reboundFrom` the chosen one, and `data` is replaced when the answer carries the key. The response's quota, refusal, stream events, end and any retry reroute are then attributed to the answering account, once; the chosen account gets nothing from this response, and what the sender saw from it before moving on (the 401 itself) never reaches the installer, so the adapter accounts for it where it saw it. If `answeredBy` throws, the attempt ends `failed` and the response hook fails: the installer cannot know whose response it is, so it attributes it to no one. Rebinding was chosen over letting the adapter mark a response as already accounted for: a bypass would leave the response's quota, refusal, output detection and the retry reroute to every adapter to rebuild, while a rebind keeps that machinery and only corrects whose account it describes. A rebind applies to HTTP responses only; a WebSocket exchange has no response object to report it on.

**Cancellation and disposal, as they are.** There is no cancel API. What each path reports through `onAttemptEnd(attempt, outcome)` (where `attempt.data` is the attempt's own value, or what `answeredBy` replaced it with, and `attempt.accountId` the account the attempt is attributed to) and what it leaves behind:

- the host cancels an HTTP response body (the user stops the turn while it streams): `error: {reason: 'cancelled', message?}`, the message being the host's cancel reason when it gave one, with `status`, `outputStarted` and `limit` as observed;
- the host aborts an HTTP send before any response, or a WebSocket closes or is cancelled mid-response: no hook tells the installer, so nothing is reported then. A WebSocket attempt ends `abandoned` with `a newer attempt of its session and kind began` (or `… went out over WebSocket`) at the next attempt of its session and kind. An HTTP attempt stays open until the retry hook judges it and the next attempt of its session and kind abandons it, or until one of the points below; a newer attempt alone does not end it, since it might still be answered;
- `forgetSession(sessionID)`, or the host's `session.deleted`: every held attempt of the session ends `abandoned` with `its session was forgotten`, and the session's pending retry information (the next attempt's `previousAccountId` and `rerouteFrom`) is dropped;
- the record bound: the oldest held attempt ends `abandoned` with `dropped to keep the record bound`;
- `dispose()`: every held attempt ends `abandoned` with `the installation was disposed`; pending retry information and listeners are cleared and every hook is removed. `dispose` does not wait for `onAttemptEnd` to settle. A response still streaming afterwards reaches the host unchanged, but no adapter callback or listener runs for it any more, so its quota and end are lost.

None of these touches the host's own request: the installer never cancels a send, and an abandoned attempt's response, should it still arrive before `dispose`, is attributed to that attempt as usual (its end is not reported twice). Per-attempt values belong in `data`, not in headers: the host keys a session's WebSocket on its handshake headers, so a header that changes per attempt opens a new socket every turn and loses incremental continuation: on 2.0.21, with a per-attempt header on the handshake, the second turn of the placement test's frame-rewrite scenario went out on a new socket with no `previous_response_id` and the full input. The attempt mark does not count: the host keys the socket on the headers the handshake hook leaves, and the installer removes the mark there (the same scenario reuses the socket on 2.0.22).

**WebSocket frame rewrite (library decision).** The host chains turns by diffing its own request as it was before `experimental.ws.send` ran (`research/opencode2-thin/REPORT.md` §4), so a rewrite applied uniformly to every frame keeps `previous_response_id` continuation incremental; a rewrite that alters, drops or reorders the host's `input` items, changes `previous_response_id`, or is applied to some frames and not others, leaves the server's view out of step. Items the rewrite adds become part of the server's history, which the host never re-reads on an incremental turn, so adding (for example a settings update just before a new user message) keeps the follow-up turn incremental. The hook therefore rewrites every frame of the provider, attributed or not.

That guarantee is narrower than history equivalence. "Add-only" keeps the host's order and its continuation; it does not make a history replayed in full after a reconnect equal the history accumulated incrementally. Incrementally, each frame carries only the new items, so a deterministic insertion made in every frame lands at every network boundary of the accumulated history; a full replay is one frame, and the same rewrite inserts the item once. The server-side histories, and their cache prefixes, then differ after every reconnect. A rewrite that only adds or changes settings fields is unaffected. An adapter that inserts `input` items must prove, for its own insertion, that the accumulated incremental history equals the rewritten full replay (including across tool loops), or accept the divergence and name its cost (a cache miss and a different prompt after each reconnect). The placement contract's frame-rewrite scenario checks continuation on a reused socket, not this equivalence.

**Retry policy (library decision).** With `gateOnPlaceholder`, the retry hook does nothing unless the session's **latest transport** (HTTP or WebSocket) was owned, leaving the host's decision untouched after a switch to an API key. OpenCode 2's retry draft carries no request, kind, credential or socket identity. The installer therefore keeps a conservative session taint: once both an owned and a foreign transport of this provider have appeared, in either order, retry emits `host-decides` and neither selects an account nor reads a limit from the retry error. This includes owned attempts still selecting or already ended. The latest-foreign early return remains silent. Mixed ownership is checked again before error attribution and immediately before publishing a decision after account selection; a reserved retry choice is released and no pending retry is stored if foreign traffic arrived during the wait. Limits already attributed before foreign traffic appeared remain noted, and response-object-attributed limits are unaffected. When that latest transport was owned and the session has never mixed credentials, the existing attempt-selection heuristic below applies. The retry hook carries no request kind, no output flag and nothing naming the call it retries, so the installer's retained attempt records supply each call's kind, observed output status and account. It judges the session's newest refused attempt not yet rerouted; else, among the session's attempts whose kind is `primary` (all of its attempts when none have that kind), the only one, or the newest that failed (error status, failed, cancelled or abandoned, or no account) and was not yet judged, or the only one still open, or the newest. With two or more open and none of these to tell them apart it judges none: it keeps the host's decision, emits `retry` with `reason: host-decides` and no account or handle, and leaves every attempt as it was, since deciding for one could reroute or end the other. When it asks the host to retry, the next attempt of the judged attempt's session and kind (the host's retry runs `model.request` again) gets that attempt's account as `previousAccountId`, and `rerouteFrom` when it rerouted; no other attempt of the session sees either. Before output, a recognised limit makes the hook call `chooseAccount` itself with `phase: 'retry'`, `previousAccountId` and `rerouteFrom` naming the refused account. Every account id it returns commits the next attempt's account. Another account returns `{retry: true, delay: 0}` whatever the host decided, including errors it deems final (`usage_limit_reached`), with `reason: reroute`. The refused account keeps the host's decision and wait (`retry-after` or backoff), with `reason: host-decides-last-account`. In either case, the next attempt of that session and kind uses the kept account without calling `chooseAccount` again. An account that becomes unavailable in that gap still serves the retry: its refusal is judged by the retry hook like any other, never turned into a `no-account` refusal. An undefined answer or a throw (logged with `warn`) keeps nothing: the host decides, reason `host-decides-last-account`, and a retry after its wait calls `chooseAccount` once with `phase: 'request'`, `previousAccountId` and no `rerouteFrom`. A kept choice that will not be used is released through `dropChoice` before any later choice for that session: the installer's computed decision is no retry, the host retries with another model or agent (which chooses afresh), the session is forgotten/deleted, the installation is disposed, or its record is evicted. The incoming host veto is not final until the installer has considered rerouting; the hook API exposes no post-pipeline callback for overrides by later plugins. After output the hook returns `{retry: false}` so the answer is not repeated; a request refused for having no account returns `{retry: false}`; anything else keeps the host's decision.

An undefined answer commits nothing to routing state: no consumed retry entry, no queued choice, and no session pin created, moved or deleted. Maintenance any request may do is allowed: refreshing a credential to check that an account is usable, and recording quota readings, since both are idempotent and the next call would do them anyway.

**Same-account hold (opt-in).** `ChooseAccountResult` adds `RetryHold`, shaped as `{ hold: { delayMs: number } }`, beside the existing account ID or `undefined`. An explicitly typed adapter opts in as `OpenCode2AuthAdapter<Q, A, ChooseAccountResult>`; the third type parameter defaults to `string | undefined`, preserving the return type seen by existing adapters' direct callers. Inline adapters passed to `installOpenCode2Auth` accept the full result without an extra annotation. Code that captures the installer's adapter parameter into a variable typed as the default `OpenCode2AuthAdapter` (including installer mocks) must widen that variable to `OpenCode2AuthAdapter<Q, A, ChooseAccountResult>`: the installer can receive hold-capable choices even when the capturing code does not use them. The object cannot be confused with an account ID and needs no duplicate account identity: it always refers to `rerouteFrom.accountId`. An adapter returning a hold commits a queued choice for that account without moving its routing pin. The installer returns `{retry: true, delay: delayMs}` with retry reason `hold`; the next attempt reuses that choice without calling `chooseAccount` again, subject to the existing model and agent checks. A hold returned in phase `request` selects no account and is treated as `undefined`.

The delay is the adapter's own Retry-After, including its per-session jitter. Finite, non-negative values are clamped (not refused) to `MAX_RETRY_HOLD_MS`, **20 minutes / 1,200,000 ms**, enough for a 15-minute reset plus up to 20 seconds of jitter. Values just below or at the cap are unchanged; larger finite values retry at the cap. Negative, NaN or infinite delays release the queued choice and keep the host's decision. `LimitSignal.retryAfterMs` remains informational: neither an ID nor `undefined` implicitly asks for a hold or replaces the host's wait.

A hold overrides the host's `{retry: false}` **only for a recognised account-level limit before output in an untainted session**. Recognition remains the adapter's responsibility through `limitFromResponse`, `inspectEvent` or `limitFromError`; the installer does not guess from an arbitrary error message or HTTP status. This lets a recoverable usage-window refusal (`usage_limit_reached`) wait even when the host misclassifies it as final. Without such a limit the adapter is not asked for a retry choice and the host's false stands. The no-account and output-started guards are unchanged, and mixed-ownership taint still leaves the host in charge without consulting the adapter. A plain `undefined` still commits nothing and leaves the host in charge.

Unused holds use the normal `dropChoice` lifecycle with the original retry input and the refused `accountId`: model/agent mismatch, record eviction, forgetting/deletion, disposal, or a revoked in-flight selection releases the choice exactly once. When the host publishes `session.status` idle (including cancellation during its retry wait), cleanup releases only pending retries recorded before that idle was observed. Retry records and idle observations receive increasing order numbers, and cleanup is serialized with that session's choice work: a retry queued after the idle survives even if cleanup was waiting for its selection to finish. Idle never revokes in-flight selections, because a delayed idle notification from an earlier turn must not refuse a healthy next turn. Account records, pins and mixed-session taint are not cleared. With no event subscription, an embedder must call `forgetSession` on cancellation. The installer never sleeps or starts a private retry loop: the host owns the wait and cancellation.

**OpenCode 2.0.32 bound.** At tag `v2.0.32`, `packages/core/src/session/runner/retry.ts:31-38` caps provider-requested Retry-After at 15 minutes **before** invoking hooks. That cap does not apply to plugin hook results: lines 88-90 accept any finite, non-negative hook delay and round it up to integer milliseconds. Thus the host does not truncate a 920,000 ms hold; the installer's independent 20-minute clamp bounds adapter input on Windows, Linux and macOS. The real-host placement suite (pinned separately to 2.0.22) also exercises a short same-account hold after a usage-limit veto.

**Host credential (library decision).** The plugin's pool is the authority; the host holds only a placeholder OAuth credential, `{access: refresh: 'common-auth-placeholder.<integrationID>', expires: now + 1 year, metadata: {commonAuthPlaceholder: true}}`, so the provider stays catalogued. `registerOpenCode2AuthMethods(ctx, {integrationID, methods: [{method, authorize(answer)}], onLogin(result, {integrationID, methodID}), label?, now?})` registers each method through `ctx.integration.transform(editor => editor.method.update(...))`. A method's `authorize` returns the host's `{url, instructions, expiresAt?, mode: 'auto' | 'code', callback}` except that `callback` resolves to the plugin's own login result; the helper awaits `onLogin` (the pool write) and only then hands the host a placeholder, so a failed pool write fails the host login and stores nothing there. Host-driven `refresh` returns a fresh placeholder and never calls the plugin. A real credential stored earlier under one of these method IDs is replaced by a placeholder at its first refresh; a plugin that wants to import such a login reads it through `ctx.integration.connection` first. The installer refuses (`host-credential-on-wire`) any HTTP request or handshake that still carries a placeholder after the account headers are applied.

**Vault activation method (0.13.0).** With `gateOnPlaceholder`, the plugin acts only on requests whose prepared credential is its placeholder, and a pool login method is the only other way to get one into the host, at the cost of a local account. A host in vault mode (`enrollmentAuthority(paths, name) === 'vault'`) must use and touch nothing local, so `registerOpenCode2AuthMethods` takes `vault?: {method, activate(context), instructions?}` (`VaultActivationMethod`; `context` is the `LoginContext` `{integrationID, methodID}` that `onLogin` also gets). The method is registered beside the pool methods under its own ID, and choosing it in the host's login picker calls `activate` and hands the host the same `placeholderCredential` under the vault method's ID. It never calls `onLogin`, so nothing is written to the pool. When `activate` throws, the host login fails with the error's message and the host stores nothing. Host-driven `refresh` renews only a placeholder of this integration stored under the vault method's ID, without calling `activate`, and refuses anything else (`This login method refreshes only its vault placeholder; choose the plugin's vault login method again.`).

OpenCode 2.0.22 has no login method that needs no user step (OAuth expects a page, a key method a typed secret, a command method a program), so the vault method is an OAuth method whose `authorize` returns `{url: '', instructions, mode: 'auto', callback}`, `callback` resolving once `activate` has. The host accepts it as is: `Attempt.url` is a plain `Schema.String` (`@opencode/schema` 2.0.22 `dist/integration.js:58-65`), and the server runs an automatic callback as soon as the attempt starts and stores its result. `opencode auth login` prints the instructions, tries to open the URL only on a terminal through an opener that refuses anything but http(s) and ignores that refusal, then polls the attempt until it completes; a failed attempt ends the command with the plugin's message. The TUI login dialog draws the link and the instructions only for a non-empty URL (an empty one shows just "Waiting for authorization…"), opens a browser only when the user presses `o` (the same opener, which refuses an empty URL), and polls the attempt the same way. The CLI path, success and refusal, runs in the placement contract; the TUI path was read from the 2.0.22 bundle and not driven.

*Vault-only host recipe.* A plugin that supports vault mode registers its vault method next to its pool methods and refuses in `activate` unless the host is in vault mode, with a fixed message that carries no credential:

```ts
await registerOpenCode2AuthMethods(ctx, {
  integrationID: 'openai',
  methods: [codexLogin], // the pool methods, unchanged
  onLogin: writeToPool,
  vault: {
    method: { id: 'openai-vault', type: 'oauth', label: 'Use vault accounts' },
    async activate() {
      if ((await enrollmentAuthority(paths, hostName)) !== 'vault')
        throw new Error('This host is not in vault mode; sign in with a local account instead.')
    },
  },
})
```

It installs the request hooks with `gateOnPlaceholder` and serves owned requests from vault accounts only. In vault mode the user signs in with the vault method once; requests carrying the resulting placeholder are then the plugin's, and its pool stays untouched. The pool methods stay registered, and refusing them in vault mode is up to the plugin's own login code. A placeholder stored by the vault method keeps renewing after the host leaves vault mode; the plugin decides what to do with the owned requests then (normally refuse with no account).

**Recipe weaknesses that remain, and what a plugin does about them.**

- *WebSocket depends on `experimental.*` hooks* (`ws.handshake` for the identity, `ws.receive` for quota, output and refusals). The `opencode2-placement` CI job fails when any of them stops firing. The job runs the host version pinned in the test (`OPENCODE_CLI_VERSION`, 2.0.22); bump that pin to adopt a new host release only once the job passes on it, and treat a red job as a release blocker. The loopback proxy is the fallback if the hooks go away.
- *A refused WebSocket handshake switches the session to HTTP for good* (host source, untested). The ungated installer never throws in the handshake in normal flow: `no-account` is raised in `model.request`, before a transport is chosen. With `gateOnPlaceholder`, no account can be chosen until the prepared credential is available, so a refused owned handshake fails locally there and may trigger this host fallback. An adapter must still refuse locally when no account can serve; it must never send the placeholder to avoid the fallback. This fallback warning is based on host-source behavior, not a placement-test assertion.
- *Some WebSocket recoveries bypass the retry hook* (`previous_response_not_found`, `websocket_connection_limit_reached` go to a full resend). With ownership gating, these recoveries are checked and selected at the transport hook; without it they still run `model.request`, so the account choice applies; they just cannot be rerouted on a limit. Nothing to do beyond keeping `chooseAccount` honest about limits recorded from `limit` events.
- *The retry hook has no kind, headers or output flag, and stops being called after 10 retries in one step.* The installer tracks refusal and output itself; a pool with more than ten refusing accounts cannot be walked within one step. Concurrent requests of the same kind in one session each get their own attempt, account and response attribution, and the retry hook judges the one that failed; when two are still open and the failing one left no trace (a dropped connection on both, say), it cannot tell which the host means and keeps the host's decision. `accountFor` names only the newest. On WebSocket, attribution stays serial per session and kind (above).
- *Every account switch on WebSocket costs a new socket and a full, non-incremental request* (measured; caching recovers on the next turn). A plugin should keep a session on one account (sticky routing) and switch only on limits.

**Differences from each plugin's current behaviour.** All three plugins own their request path on OpenCode 1 (a loader `fetch`); here the host owns it and the plugin only edits headers, URL and body at fixed points. openai-auth: credentials and `chatgpt-account-id` go in `accountHeaders`, quota comes from the `x-codex-*` headers and `codex.rate_limits` frames through `quotaFromHeaders`/`inspectEvent`, and its in-fetch 429 failover becomes the retry-hook reroute; the host's main login slot holds a placeholder instead of the main account. For openai-auth's one attempt at a time, the wire, the account choice, quota attribution and retry decisions are unchanged by concurrent attempts; what changed is that `model.request` leaves the attempt mark among its headers for the hooks after it, and that an HTTP attempt aborted before any response, which the retry hook never judged, now stays open (ending at session deletion, the record bound or dispose) instead of ending `abandoned` at the next attempt of its session and kind. openai-auth reads only `status` 401 in `onAttemptEnd`, so neither changes what it does. anthropic-auth: its URL/body rewrite and its response-stream rewrite move into `rewriteRequest`/`rewriteResponse`, and a header the host adds that must not go out (an API-key header, say) is a `null` header edit; it is HTTP only, so none of the WebSocket weaknesses apply. antigravity-auth: its endpoint and body rewrite go in `rewriteRequest`; a sender of its own that moves a request to another account reports the account that answered through `answeredBy`; whether OpenCode 2 routes its models through a driver these hooks reach is not established here.

**Placement contract.** `test/opencode2/e2e/placement.e2e.test.ts` installs `@opencode/cli` 2.0.22 with npm into a scratch directory, bundles a test plugin built on this subpath, and runs the real host in server mode with isolated `HOME`/`XDG_*` against a loopback mock with two accounts, the host credential set to the placeholder. It asserts the bearer per account on HTTP and WebSocket, a switch mid-session, quota attributed to the right account, a reroute before output (WebSocket rate limit, HTTP usage limit the host would not retry), no retry after output (both transports), an HTTP 401 ending the attempt whose receipt went out on that request with its status and value, a frame rewrite that reaches every frame while the follow-up turn stays incremental on the reused socket, every choice made in `model.request`, that every HTTP request and every handshake reached the transport hooks carrying the attempt mark of an attempt `model.request` started for the same request kind (`primary` agent loop or auxiliary `title`), that the mark never reaches the wire, and that the placeholder never reaches the wire. The pin moved from 2.0.21 to 2.0.22 with no change to the scenarios; every one of them passes on 2.0.22. A separate gated case supplies a non-placeholder API key through provider settings non-interactively and proves the real host sends it unchanged, with no account selection, receipt, attempt mark, feedback, retry or end events. The existing account-placement scenarios remain ungated to pin compatibility. Two gated vault cases leave the provider with no configured key, register the test plugin's vault method alone, and sign in with it through `opencode auth login <provider> --server … --method <vault method>` without a terminal: on success the command reports the connection, the plugin's activation ran once and its pool login never, `GET /api/credential` lists only the placeholder (active, under the vault method's ID), and the next turn's requests are owned and carry the vault account; when activation refuses, the command fails with the plugin's message and the host lists no credential for the provider. It runs only with `COMMON_AUTH_OPENCODE2_E2E=1` (`COMMON_AUTH_OPENCODE2_E2E_CLI_DIR` reuses an existing pinned install), in the `opencode2-placement` CI job; its provenance rows are in `test/opencode2/e2e/sources.md`.

## D7 compatibility limits

1. **Unlocked old writers:** exclusion holds only among cooperating live-lease holders. In openai-auth baseline e6837be, setSidebarState directly queues doWriteSidebarState without a lock, while only its merged-write path takes sidebar-write. The moved merge-recheck loop is best-effort mitigation, not exclusion against that old path.
2. **Cross-plugin preferences protocol:** antigravity-auth baseline 44eb8fa uses the same preferences lock path, newline-free payload, and marker owner.json with ownerId/pid/createdAt. Live expiresAt detection interoperates, including newline-free payload with backdated mtime, but stale eviction protocols do not. Do not claim full stale-lock compatibility.
3. **Check-to-rename expiry:** assertOwned and rename are separate operations. A holder stalled after a passing check beyond lease expiry can overwrite a successor. Commit-time fencing would be required to close this window and is outside this campaign.

Observed check-to-rename expiry demonstration: the internal acquireRefreshFileLock uses clock 100, ttlMs 1000 and renew false. A stages its file, passes assertOwned in beforeRename, advances clock to 1101, lets B acquire/write/release, then resumes its own rename. The test is `a lease expiring after the pre-rename fence can overwrite a successor`.

```text
bytes after B's write: "{\n  \"writer\": \"B\"\n}\n"
bytes after A resumes: "{\n  \"writer\": \"A\"\n}\n"
```

1. **Crash windows, per operation (since 0.3.1).** A reader after a crash at any write step sees each row either entirely as before the operation, entirely as after it, as a same-account rotation whose identity is not yet recorded, or not routable (`candidate: false`) until a later write completes it; never a credential beside another account's identity or endpoint. The `before-*` steps run before the rename, so a crash there leaves that file as it was. Rule: the state file is written first and its stamp is checked against the config (see *Credential stamps and torn rows*). Each row is pinned by `test/store/torn.test.ts` (a fresh reader, a quota reading for the row as read, a pull fired by a fresh load, and the next write) and listed in sources.md.

   | operation | writes, in order | crash after the first write (`after-<first>-write`, `before-<second>-write`) | repair |
   | --- | --- | --- | --- |
   | `add` (new row) | state (credential, stamp at epoch 1; any leftover entry for the id dropped), config (roster row, entry) | a state entry no roster row names: no reader loads it, the pool is as before | a re-run `add` adds the row (`added`); `remove` of the id drops the entry (`completed`) |
   | `add` (roster row without credential, left by another writer or by 0.3.0) | state, then config (entry) only if the row had none | the row with its credential at epoch 1: whole | none needed |
   | `add` (fingerprint already held), `rotate` with nothing to record, a refresh learning nothing | state only | — | — |
   | `replace` | state (new credential, stamp at the new epoch with the binding), config (epoch, identity, endpoint, quota dropped, duplicates disabled) | torn: shown completed, never a candidate; `recordQuota` refuses it; in-flight work for the old epoch fails attribution | the next row write (any of `add`, `replace`, `rotate`, `disable`, `enable`, `remove`, `recordIdentity`, refresh, a pull capture) writes the config from the stamp; `load()` fires the pull of an enabled OAuth row; a re-run `replace` completes it, then bumps again |
   | `rotate` learning the first identity, or materialising an entry; a refresh learning the first identity; `recordIdentity` on a bound row without an identity (since 0.4.4) | state (rotated credential, or for `recordIdentity` the unchanged credential, stamped at the row's epoch with the identity being learnt in its binding), config (identity, entry) | since 0.4.4, when an identity is learnt: shown with the stamped identity, `torn`, never a candidate; without one (a rotate materialising an entry): the rotated credential, whole | the next row write (or the pull `load()` fires) records the stamped identity; before 0.4.4 the row loaded whole without the identity and the next refresh or `recordIdentity` recorded it |
   | `remove` | config (roster row and entry dropped), state (credential dropped) | the row is gone for every reader; a state entry no roster row names is left | a re-run `remove` drops it (`completed`); an `add` of the id drops it |
   | `disable`, `enable`, `recordIdentity` (on a row already holding the identity, or whose stamp is not bound), `reorder`, `updateSettings`, `initialize`, `recordQuota`, a pull's entry materialisation | config only | — (one atomic rename) | — |

   Before 0.3.1, `replace` wrote the config first and a crash between its writes loaded as a candidate holding the new identity or endpoint beside the old credential, at the new epoch, accepting quota for the new account; an `add` crash left a credential-less row that accepted a quota reading.
2. **Older writers and torn rows.** A stamp only says something beside the credential it was written with. An older writer (0.3.0, or a plugin's legacy store) that refreshes a torn row's token in place keeps the stamp but changes the credential, and one that rebuilds state entries drops the stamp; either way the row then loads as before 0.3.1, the new credential beside the config's old identity or endpoint. A 0.3.0 `replace` sharing the files can still leave its own config-first intermediate, which loads as it did. The guarantee holds while every writer of the files is 0.3.1 or later.
1. **Crash windows, per operation.** `add` writes config then state: a crash between leaves a row with no credential (never a candidate) that a re-run `add` with the same id completes at epoch 1. `replace` writes config then state: a crash between leaves the bumped epoch beside the prior credential; in-flight work for the prior epoch fails attribution, and a re-run `replace` completes it and bumps again. `rotate` writes state then config (only when it has an identity or entry to write): a crash between leaves the rotated credential with the old identity or entry, and the next refresh or `recordIdentity` completes it; with nothing to write to the config, a crash after the state write is completion. `reorder` makes one config write: a crash leaves the whole old order or the whole new one.
2. **Durable replace intermediate.** Work issued after a crash between `replace`'s writes captures the bumped epoch with the credential `replace` meant to retire, so its reading is attributed and applies; the re-run `replace` and the next reading supersede it.
3. **Foreign writers.** A writer outside the library can replace a credential in place (id, epoch and identity unchanged), or remove a row and re-add its id; a pull in flight across either applies to the successor until the next reading supersedes it. (Since 0.8.0 a removal or re-add made through the store, by any process, does not: see *What an attribution proves, and a reused id*.) A foreign write that bumps the epoch while a refresh is in the provider call makes the refresh fail attribution and discard its rotation.
4. **Id reuse.** When a library write drops the entry of an id absent from the roster, `add` of that id is refused (`id-removed`) for the rest of the process; a fresh process accepts it.
5. **Mixed versions.** An older writer that rewrites the config keeps `commonAuthPool` as an unknown top-level key and the recorded identity in `accountId`, so every row keeps its credential. An older writer's config rewrite drops a row's credential only if the roster row lost `type` or an api row's `baseURL`; the store always writes both. `authHeader` lives in the config only; one written to the state file does not survive an older roster write. The older writers' unbidden top-level keys (`main`, `claustrum.rowHistory`) survive library writes.

The supplied reference copy can be deleted after this library extraction: no inventory requires it to exist. Keep these committed documents for provenance and adoption scope.

Quota and routing limits (declared, each pinned by a test named in sources.md):

- **routing.mode default:** an absent or unrecognised `routing.mode` routes `ordered` in roster order; legacy readers of the same config default to `main-first`. Mixed-version pools therefore route differently until the mode is set explicitly.
- **Unknown stored window length:** a limit stored without `windowMinutes` sorts last and carries no length; openai-auth assigned 300/10 080 minutes by slot.
- **Third window:** no longer a limit; the sticky primitives weigh and classify every reading (see *Sticky-balanced* under ./routing).

**Store refresh identity continuity (0.9.0).** This adds a member to the refresh result union, so a caller that narrows the result (`status === 'rotated'`, else read `reason`) stops compiling until it handles `identity-contradicted`; that is why this release is a minor version and not 0.8.1. A provider returning a different identity for a row with a known identity produces `{status: 'identity-contradicted', rowId, expectedIdentity, returnedIdentity, credential}` rather than an ordinary rotation. The single-use successor is persisted on that same row, without relabelling it or merging it into a row for the returned identity; its stamp remains bound to the config's original identity, and the row loads bound-but-disabled, never a routing candidate. The disabled reason is `identity-contradicted: ` followed by JSON containing only `expectedIdentity` and `returnedIdentity` (no credentials). The disable transition is stamped in the same state write as the successor, followed by the config write under the existing transaction and row lock; once the successor is durable, every crash point loads it rotated+disabled, never rotated+enabled, and the next store write completes any interrupted config disable forward. A crash after provider exchange but before the first state rename still loses the in-memory successor and loads the old enabled row, exactly as an ordinary refresh does today; no local recovery marker can recover a token that never reached disk. This pre-existing exchange-before-persistence window is explicitly covered by the crash tests, not claimed to be solved. Plugins must handle this distinct outcome and must not propagate its credential as the old account: `onPersisted` is deliberately not called. Ordinary enable refuses with the distinct `identity-contradicted` failure kind; a routine disable also preserves this quarantine reason. Resolution requires the provider adapter to validate a replacement credential's identity, then call the existing replace path with that explicit identity. Replacement clears the quarantine (including interrupted-replace forward recovery) but leaves the row disabled until a separate enable; replacement without an identity does not resolve quarantine. The library cannot perform provider identity validation itself. Matching identities, unknown-to-known learning and absent provider identities retain existing rotation behaviour; unlike the earlier refresh behaviour, a known-to-different identity no longer silently serves the returned account as the old one.

### Store lock contention observations (0.10.0)

`onLockEvent` now receives `{type: 'contended', name, path}` after a real file-lock attempt finds a live owner, before the store retry delay. Each refused attempt emits an event; this is not a queue-entry notification or a promise that the next attempt will fail. Stale-lock takeover and successful attempts do not emit it. Eviction-marker contention alone does not emit it either. Lock names and paths use the same values as `acquired` and `released`. Delivery is synchronous, never awaited, and synchronous callback exceptions are ignored for all three events. Returned promises and thenables are not awaited; their rejections are absorbed and ignored, rather than surfacing as unhandled rejections. Asynchronous work an observer starts without returning it remains the observer's responsibility. Lease timing, polling, jitter and lock ordering are unchanged.

This is an additive runtime event but widens `LockEvent.type`: a consumer's exhaustive switch with a `never` assertion can fail typechecking until it handles `contended`. Consumers that treated every non-`acquired` event as a release must instead check `released` explicitly; acquisition/release ordering logs should filter out `contended`. Plugins need not supply a callback. Tests can use the refusal as a causal exclusion observation while the owner is still parked, rather than treating an elapsed window as evidence of exclusion. No tag or publication accompanies this addition.

### Renewal timer lifecycle observations (0.10.0)

The `/fs` primitive accepts the optional `onRenewalTimer?: (event: 'scheduled' | 'cancelled') => void` observer. Scheduling notifies after arming and unreferencing each one-shot renewal timer; cancellation notifies after clearing a still-pending timer on detected loss or release. Delivery is synchronous, never awaited, and isolates synchronous throws and returned promise/thenable rejections exactly like `onContended`; unrelated asynchronous work remains the observer's responsibility. This option is fs-primitive only: the store does not forward it. The `onStep` union and its existing awaited semantics are unchanged, as is the store's `onLockStep` control-barrier forwarding. The timer callback drops its handle when it fires, so a fired timer is never reported or cleared as a pending one; no lease interval, retry or release/join ordering changes.

A cancellation notification identifies a cleared pending timer, not completion of an in-flight renewal and not resolution of `whenLost()` after normal release. Scheduling alone cannot guarantee the timer remains pending later; use cancellation and actual timer-call evidence when testing cancellation.

### Awaited stale-lock removal barrier (0.10.0)

`./fs` acquisition's optional `onStep` now includes `stale-lock-observed`, awaited after the first liveness check and before marker mkdir, and `stale-lock-removed`, awaited after stale removal and the post-removal marker check, before exclusive recreation. Plugins need not supply this callback; without it acquisition behavior is unchanged. A callback may pause acquisition but does not reserve the pathname. Both are new members of the awaited `onStep` union, control barriers like the existing steps, not fire-and-forget observers: an exhaustive switch over `onStep` steps fails typechecking until it handles them, and an observer must ignore steps it does not recognise rather than read them as completion. A rejected `stale-lock-observed` callback ends the acquisition before the eviction marker is taken; a rejected `stale-lock-removed` callback ends it after the stale file is removed and before recreation, with the marker released. The deterministic acquisition tests verify refusal of a fresh occupied marker and preservation of a replacement lock owner during the second liveness check, exclusive-recreation failure and delayed retry. See `research/load-probe/ACQUISITION-ORDERINGS.md`; the existing 512-round contention smoke count is unchanged.
