# Adoption inventory

This revision is publish-ready, not published, and does not adopt the library into any plugin. A later adoption into the openai-auth plugin must use a published npm range for `@cortexkit/common-auth` as a build-time devDependency, bundle/inline it, and verify its absence from the consumer's node_modules. No git, file or link dependency is permitted.

Only **moves** machinery and its covering tests are removed/replaced. A partial-file move does not authorize deleting policy in the same file. Origins in [sources.md](sources.md) are historical provenance labels, not required files or runtime imports; both inventories remain usable without the supplied reference tree.

## Adoption inputs: public exports and parameters

All ten subpaths are ESM, with `dist/<subpath>/index.js` and adjacent `index.d.ts` targets. Since 0.1.1, `/fs` also exports the try-once lock underneath `withLock`, `acquireRefreshFileLock({name, ttlMs, path, now?, renew?, renewIntervalMs?, onStep?})`, which returns a `{release, assertOwned}` handle or `null` when the lock is held, and `isLostMarkerRaceError`. It is for callers that hold a lock across several steps or poll rather than wait; openai-auth's refresh leases use it. The adopting plugin supplies its file paths, directory prefixes, registry key, preferences key, logger channels and schema/merge policy.

### ./quota

Pure functions over plain JSON; no file I/O, locks or clock reads (every time is a parameter).

**Quota map** (`QuotaMap`): `{ limits: QuotaEntry[], budget? }`. Each limit is keyed by `(scope, label)`: `scope` is `all` (`ALL_SCOPE`) or a model family, `label` names the provider's window. An entry is a reading `{ kind: 'reading', checkedAt, usedPercent, resetsAt?, windowMinutes? }`, a retirement tombstone `{ kind: 'retired', retiredAt }` or an absence record `{ kind: 'absent', checkedAt }`. A missing key is unknown; a tombstone or absence record is evidence that the key is unlimited, and admission treats both alike. The budget is a tri-state: absent (never reported), `{ kind: 'reading', checkedAt, reached, remainingPercent?, usedPercent?, resetsAt?, limit?, used?, remaining?, unit? }`, or `{ kind: 'cleared', checkedAt }`. Merge writes limits sorted by scope then label, so identical content serialises identically.

**Observation** (`QuotaObservation`): `{ checkedAt, readings?: [{ scope?, label, usedPercent, resetsAt?, windowMinutes? }], coverage?: [{ scope?, label }], budget?: { kind: 'reading', ... } | { kind: 'cleared' } }`; `scope` defaults to `all`. Coverage lists the pairs the observation speaks for with authority; every reading is implicitly covered. A header-shaped push covers only what it carries; a full poll covers every pair the source reports on. An absent `budget` says nothing about the budget.

**Merge rules** (`mergeQuotaObservation`). One freshness rule: an observation applies to a key when `checkedAt` is not older than the key's reading, retirement or absence time (equal applies, the observation applied last wins). A covered pair without a reading turns an existing reading or tombstone into a tombstone at `checkedAt`, and an empty or absent-recorded key into an absence record at `checkedAt`. Pairs outside the coverage are never touched. The budget follows the same rule against the stored budget's `checkedAt`. Unrecognised top-level keys of a stored map are carried over.

**Projection.** A family request sees only its family's keys and the `all` keys, one entry per label. A family *reading* shadows the `all` entry for its label; a family tombstone or absence record says only that no family-specific limit exists, so it does not hide an `all` entry for the same label and reaches the primitives only when there is none (library decision, pinned by `a family tombstone or absence record does not hide an all-models entry`). Limits are ordered longest stored `windowMinutes` first, unknown lengths last, then by label. Each limit carries its stored length as `windowMinutes`; an unknown stored length stays `undefined` and is never filled in by slot the way openai-auth's `getPresentQuotaWindows` fills `LEGACY_WINDOW_MINUTES` (declared divergence: a pre-dynamic-window snapshot migrated without a length sorts last and shows no length). `checkedAt` is the minimum reading time (the minimum evidence time when there is no reading), so a projection is only as fresh as its stalest reading; both the selection primitives and pending-bytes attribution see that minimum. A cleared budget projects no budget.

**Provider → (scope, window) mapping.** The library infers no labels; a plugin maps its provider's windows when it builds observations and passes the required labels per admission call. openai-auth: the wham/header primary window → `(all, primary)`, secondary → `(all, secondary)`, spend control → the budget, and a full poll covers both pairs; required labels `['primary']` (the default). anthropic-auth: `five_hour` and `seven_day` → `(all, five_hour)` and `(all, seven_day)`, a model-scoped week such as `seven_day_opus` → `(opus, seven_day)`, extra usage → the budget; it must pass its own required labels. antigravity-auth: each per-model quota → `(<model family>, <its window label>)`.

**Admission.** A marked row is excluded while `now < expiresAt` and readmitted at its roster position from the expiry on; a backed-off row likewise until its retry time. Neither reorders or re-weights any other row. openai-auth's `selectStickyCandidate` has no such inputs (its request path filtered rate-limited fallbacks before calling it), so both inputs, and their exclusion semantics in both modes, are new. Stage-1 gates in precedence: (1) API-key rows are admitted without quota; (2) no projected entry for the scope → `needs-first-reading`; (3) a required label with no entry → `unknown-window`; (4) a reading at or above 100% whose reset is missing, unparsable or not after `now` → `unknown-reset`; (5) a reading at or above 100% with a future reset → `exhausted`. Gates 4 and 5 judge every projected limit, including a third window. Gate 4 judges only exhausted-looking readings (library decision: a reading below 100% is admitted whatever its reset says), and it deliberately diverges from openai-auth, whose admission failed open on a passed window reset: the library refuses and requests a reading. Gates 2 to 4 request a pull: `requestPull(id)` is called synchronously, never awaited, once per refusal, and the refusal is returned without waiting. Every call evaluates every candidate, so a caller that fires a real pull from this callback should dedupe pulls already in flight. Stage 2: a survivor whose budget is spent (`budgetExhaustedResetAt`) is refused as `budget-spent` unless every survivor is spent, in which case all are kept with `lastPath: true`. API-key rows are survivors, a stage-1 refusal never counts as a path, and there is no last-path exception at any stage-1 gate. The budget signal ignores staleness, as openai-auth's `isQuotaExhausted` does.

**Ordered.** `routing.mode` absent or unrecognised resolves to `ordered` in roster order, where legacy readers defaulted to `main-first`; the persisted value is never rewritten. `main-first` and `fallback-first` place the row named by `formerMainId` (default `main`) first or last when that row exists. The follow-up supplies the recorded former-main id; nothing here reads `commonAuthPool`. The retry statuses have no default and are always the caller's.

**Sticky-balanced.** The primitives are openai-auth's, judged over the projection. Two limitations are declared. First, `STICKY_WINDOW_SLOTS` is 2: selection weight and the break decision use only the first two readings in projection order, so a third window per scope adds no weight and is judged by admission alone. Second, `decideStickyBreak` reports `window: { scope, label }` instead of openai-auth's `windowKey`. `routeSticky` dispatches a valid pin whose row is admitted and not killed. Otherwise it runs selection over the non-excluded rows, drops each selected row that admission refused, and re-runs until a row is admitted or none is left (`no-admissible-account`). Reserves are per window label: `reservePercent` applies to every row, and since 0.2.3 `rowReservePercent` (a map by row id, or a function of the row) replaces it for each row it returns a value for, so a plugin whose reserves are per account (openai-auth's killswitch thresholds) weighs each row by its own. Under the default `refusedPinPolicy: 'keep'` a valid pin is always `retain`: a pin whose row is refused (quota turned unknown or exhausted), excluded or killed is routed around, not deleted, and the caller's break decision governs clearing it. Under `'move-on-confirmed-exhaustion'` (since 0.2.3, openai-auth's behaviour) the pin is reassigned (`assign`) to the row this request is dispatched to when its own row was refused `exhausted` or `budget-spent`, or killed by the killswitch; a refusal for unknown quota (`needs-first-reading`, `unknown-window`, `unknown-reset`) and an exclusion keep it (`retain`) while the request is served elsewhere, and with nothing admissible a valid pin is retained under either policy. An invalid pin, meaning its row id is not among the rows passed in or both it and the row carry known identities that differ, is replaced (`assign`, carrying the row's current identity) or `clear`ed when nothing is admissible. An unknown identity on either side keeps the pin. Pins, pending bytes and assignment maps are never written to either store file by this subpath.

Admission itself is a pure function in the `/routing` subpath over rows the caller passes in; `/store` supplies the rows (`PoolRow.quota` is the codec's opaque map) and `requestReading` is how a refusal fires the pull.

**Schema.** `commonAuthPool` is one top-level key of the config file holding `schemaVersion: 1` and `rows`, a map keyed by local id. An entry holds `credentialEpoch` (an integer from 1), `needsFirstReading`, `disabledReason` and the codec's `quota` map; every other sub-key of the pool and of an entry is preserved. The recorded wire identity lives in the legacy roster row's `accountId`, which the older normaliser round-trips. Every config write emits `version: 1` and the legacy-shaped `accounts` array (id, label, type, addedAt, accountId, enabled, and baseURL/authHeader for api rows), never `mainAccountId`, and keeps every other top-level key. Credentials stay in the state file under the older field names (`access`, `refresh`, `expires`, `lastRefreshedAt`, `apiKey`); unknown state keys survive. Both files go through `writeJsonAtomic`. A missing config is an empty pool; a config with no `accounts` is an empty roster; `accounts` without `commonAuthPool` is pending migration; malformed JSON, a non-object root, a non-array `accounts`, a malformed `commonAuthPool` or `rows`, a newer `schemaVersion`, and a malformed or non-object state file (or a non-object state `accounts`) are load errors. Pending migration and load errors refuse every write, bytes unchanged. A roster row the older normaliser rejects, a second row with an already-seen id, and a malformed entry are row-level: never candidates, preserved verbatim. A pool created here carries `commonAuthPool` with no migration marker; the migration work must treat key-present/marker-absent as a pool to import into.

**Ids and dedupe.** Ids are stored verbatim; an empty id, an id with surrounding whitespace (older readers trim it) and prototype keys are refused as `invalid-input`. `disable` sets the roster row's `enabled: false` and the entry's `disabledReason`; `enable` sets `enabled: true` and drops the reason; only `remove` deletes a row. A removed id is remembered, like every id a library write drops, and `add` refuses it (`id-removed`) for the rest of the process. A crash between `remove`'s config and state writes leaves a pool from which every reader (this store and the older openai-auth reader, which ignores state entries without a roster row) has already lost the row, plus an orphaned state entry that a second `remove` of the id drops. Two enabled OAuth rows with one wire identity: the earlier in roster order stays enabled, later ones are disabled with `duplicate-identity`. The credential fingerprint (SHA-256 of the refresh token or API key) is computed on load, never persisted, and is only a dedupe key.

**Rows without an entry.** A roster row appended or stripped by an older writer loads as a candidate needing a first reading. Before a pull or refresh is issued for it, the store gives it an entry at `credentialEpoch: 1` in its own locked config write; there is no epoch-0 capture. `load()` rewrites nothing.

**Locks.** Order everywhere: row lock, provider-wide lock, extra locks (mapping order), store locks (config then state); release in reverse. The row lock is `row-<encodeURIComponent(key)>` beside the state file, where `key(row)` is the recorded identity when known, else the local id. The provider-wide lock is one `(name, path)` per provider, not keyed by identity; `add` and `replace` of an OAuth row, `recordIdentity`, `rotate` carrying an identity, and every refresh take it. `disable`, `enable` and `remove` take the row lock and extra locks but not the provider-wide lock, so a removal waits for a refresh of its row instead of landing during the provider call; a caller holding its own legacy locks around one of them passes those locks as `extraLocks` rather than holding them outside the call. `reorder` names no row and takes only its extra locks, then the store locks. Defaults (`POOL_LOCK_DEFAULTS`): ttlMs 10 000, timeoutMs 15 000, retry 50 ms plus up to 50 ms jitter, renew true; `renewIntervalMs` is optional; all overridable per store, per lock spec and for row locks. Each wait is bounded and ends in `lock-contention` wrapping `LockContentionError`. `assertOwned()` runs on every held lease after each acquisition, immediately before the provider call and immediately before each file rename; a lost lease fails `lock-ownership`, retryable. The store locks are never held across the provider call. A refresh whose row-lock key is stale at the locked re-read releases, retries once under the new key and aborts `row-key-changed` on a second change.

**Failure value.** One `PoolOperationError {operation, rowId, phase, retryable, kind, committed?}`. `operation` is `initialize`, `add`, `replace`, `rotate`, `disable`, `enable`, `remove`, `reorder`, `updateSettings`, `recordIdentity`, `refresh` or `pull` (`rowId` is absent for `initialize`, `reorder` and `updateSettings`); `phase` is `before-first-write`, `after-first-write` or `pull` (a provider failure is `before-first-write`, kind `provider`). `committed` is present only on `after-first-write` when the operation's state write had landed: a rotate or re-add failing before its config write carries the rotated credential; a replace or add failing before its state write carries none. Nothing is rolled back. `add`, `replace`, `rotate`, `disable`, `enable`, `remove`, `recordIdentity` and `refresh` take `onFailure(rowId, error)`, and `reorder` takes `onFailure(error)`, each awaited once on every non-success path with the store locks released and the outer locks still held. Pull failures (a rejecting pull, a failed attribution) go to the store-level `onPullFailure`, phase `pull`, leaving needs-first-reading set and releasing the once-per-process load guard.

**Hooks.** A refresh's `onPersisted(rowId, credential)` runs once the rotation is persisted and the store locks released, before any extra or outer lock is released; there is none when attribution or persistence failed. If it throws, the caller gets kind `after-persist-hook`, phase `after-first-write`, with the committed credential; the commit stands, the provider is not called again and `onFailure` does not fire. Inside `onPersisted` and every `onFailure`, and in every timer, promise or continuation created inside them (async context is inherited), `add`, `replace`, `rotate`, `disable`, `enable`, `remove`, `reorder`, `recordIdentity` and `refresh` reject at once with `PoolReentryError` before touching a lock. Reads and `recordQuota` are permitted. A hook that needs a row operation hands it to its caller's continuation after the operation returns. A throwing `onFailure` or `onPullFailure` is logged through `logger.warn` and swallowed.

**`refuse`.** `refuse(row) → reason | undefined | Promise<…>` is awaited before any lock, at the locked re-read and at commit time under the store locks; a reason returns `{status:'refused'}` and leaves the stored credential untouched, discarding rotated material. The row carries the stored credential including `refresh`.

**Refresh stamps.** A rotation's `lastRefreshedAt` is the injected clock at commit time, raised to one past a prior stamp that is still trusted (at most `now + 5 min`), so an older copy of the token never compares newer in the older writers' `applyNewerTokenState`; a prior stamp above the bound is ignored. When that floor would itself pass the bound (a prior stamp at exactly `now + 5 min`), the refresh refuses with `refresh-stamp-ahead`, retryable, before the provider call, and again at commit. `expires` is the provider's value verbatim.

**Attribution.** A pull or refresh captures the credential and `(id, credentialEpoch, identity)` in one read under the store locks and applies only if all three still match. `add` and the entry materialisation above start a row at epoch 1; `replace` bumps it, sets identity to the given one or clears it, clears the quota map and sets needs-first-reading; `rotate` changes none of them.

**Pulls.** `pull(request) → Promise<observation>`, where `request` is `{id, credential, credentialEpoch, identity?, reason: 'load'|'add'|'replace'|'admission'}`, is never awaited by a caller. It fires from `load()` once per process per row while needs-first-reading is set, on `add` of an enabled OAuth row, on `replace` of an OAuth row, and on `requestReading`; never for api-key, disabled, credential-less or invalid rows, and never from a refresh's re-read.

**Test and migration seams.** `now` (leases, stamps, `addedAt`); `onStep(step, {operation, rowId})` awaited at `before-config-write`, `after-config-write`, `before-state-write`, `after-state-write` (the `before-*` steps run inside `writeJsonAtomic`'s `beforeRename`, ahead of the ownership assertion); `hold(point, rowId)` awaited at `refresh-before-provider` and `pull-before-request`; `onLockEvent` (acquired/released, per lock) and `onLockStep` (the primitive's renewal steps). Crash rows exit a child process from `onStep`. For the later code that migrates a plugin's legacy store and host-slot credential into the pool: `add` with a given id and credential, `disable` with a reason, `extraLocks` taken after the provider-wide lock, and `onPersisted` after a successful refresh.

### ./cachekeep

Keeps idle prompt caches warm: one target per session holding its latest request body, replayed just before the provider's cache would expire. The manager is openai-auth's (`packages/opencode/src/core/cachekeep.ts` at b7ceb56), chosen because it is the better-tested copy: its suite tests sustain, the clock window, both idle caps, LRU and byte eviction, backoff, abort on stop and per-model TTL and warm caps, where anthropic-auth's tests scheduling, body shaping and the hybrid-mode gate. From anthropic-auth (`packages/core/src/cachekeep.ts` at 77e4c900) it takes coalesced ticks (an overlapping `tick()` returns the run in flight), an injectable `setInterval`/`clearInterval`, and a backoff that may depend on the consecutive failure count, which expresses anthropic-auth's exponential-with-jitter retry.

**The plugin supplies** `new CacheKeepManager<M>({ adapter, now, logger?, ttlMs? = 5 min, leadMs? = tick + 15 s, maxIdleWarmMs? = 1 h, maxSubagentIdleMs? = 30 min, tickIntervalMs? = 60 s, maxTargets? = 32, maxBytes? = 8 MiB, warmTimeoutMs? = 30 s, backoffMs? = 10 min or ({ sessionKey, failures }) => ms, getWindow?, getSustain?, setIntervalImpl?, clearIntervalImpl? })`. `getWindow` and `getSustain` are read on every call, so a config change applies without recreating the manager. The adapter is the provider half:

| adapter member | contract |
| --- | --- |
| `buildBody(target)` | the replay body from the captured one; a throw backs the target off |
| `send({ target, body, signal })` | resolve the account's credential and send; returns a `Response`; a throw (including no credential) or a non-2xx backs off. Provider auth-failure reporting and a 401 retry with a rotated credential live here |
| `readUsage?({ target, response, text })` | usage fields for the `cachekeep fired` log line; a throw is ignored |
| `profile?({ bodyText, isSubagent, accountId, meta })` | `{ ttlMs?, maxWarms?, maxIdleMs? }`, evaluated once at capture and kept on the target: the model-aware TTL, per-model warm cap and idle bound |
| `activeAccount?(sessionKey, target)` | the account the session routes to now, asked before every warm. A different account than the captured one drops the target without sending; `undefined` (no session binding, e.g. ordered routing) keeps the captured account; a throw backs off |

**It gets** `track({ sessionKey, bodyText, accountId?, isSubagent?, meta })` → `{ tracked: true } | { tracked: false, reason: 'body-exceeds-max-bytes' | 'outside-window' }` (arms the timer; the freshest body replaces the previous one and restarts its cache clock, idle clock and warm count), `remove(sessionKey)`, `start()`, `stop()` (aborts a warm in flight, whose result then changes nothing, and forgets every target), `tick()`, and `status()` (no bodies: per target the account, subagent flag, expiry, last real request, last warm, backoff, failures, warm count, TTL and bytes). `meta` is plugin data handed back to the adapter, such as replay headers. Also `normalizeCacheKeepWindow(value)` (a persisted `{ startHour, endHour }` block, or undefined) and `isWithinCacheKeepWindow(window, date)`.

**Bounds.** The window gates capture and warming; targets captured inside it survive outside it and warm when it reopens. A target idle past its bound (the profile's `maxIdleMs`, else `maxSubagentIdleMs` or `maxIdleWarmMs`) is pruned on every `track` and `tick`, including while it is backing off. `sustain` exempts main sessions from that idle pruning only: subagents, the window, the count and byte caps and warm caps still apply. The count and byte caps evict the target touched least recently, where a warm counts as a touch; an oversized body is refused without evicting anything. Library decision: byte caps count UTF-8 bytes.

**Differs from openai-auth.** Header capture (`buildKeepwarmCapture`), the replay body (`buildKeepwarmBody`), `ttlForModel` and the gpt-5.6 subagent policy (two warms, 75-minute idle bound), token resolution (`getMainToken`, `refreshFallback`, `onAuthFailure`), the account-id header and JSON/SSE usage parsing stay in the plugin as adapter members and a profile. `track` takes an object and reports why it skipped; `route` is gone from targets; log payloads no longer add the pid. Byte caps count UTF-8 bytes rather than string length. A tick warms in one pass in insertion order; openai-auth ran backed-off-and-expired targets first. A failed warm also counts consecutive failures. The active-account check is new; openai-auth always warmed the captured account.

**Differs from anthropic-auth.** The manager reads no storage: the plugin calls `track` only when keep-warm is enabled and the hybrid cache mode is on, and passes `getWindow` (no window is its `always`). Its 60-minute TTL and 5-minute lead are `ttlMs` and `leadMs`. A target is not dropped when its cache expires without a successful warm, nor at the end of a window period; it lives until its idle bound, and a later warm rebuilds the cache. An unbuildable body backs off instead of deleting the target (an adapter that wants deletion calls `remove` before throwing). `prewarmNow`, `trackedOAuthRoute`, `onTrackedSessionsChanged` and the per-attempt hooks are not carried: `status()` and the adapter cover them. A plugin that dumps warm requests does so from its adapter's `send`, with `./dump`.

### ./dump

Request-body dumps for cache debugging, from openai-auth's `packages/opencode/src/dump.ts` (b7ceb56) with anthropic-auth's choice of the newest earlier dump on disk as the diff baseline (`packages/core/src/dump.ts`, 77e4c900).

**The plugin supplies** `createDumper({ dir, enabled? = false, pid? = process.pid, now? = Date.now, logger?, secretKeys?, secretPatterns?, schemaKeys? = ['tools'], summarize? })`. `dir` may be a function read on every dump. `secretKeys` are key names redacted wherever they appear (compared lower-cased without `-` and `_`) on top of the common credential set (`authorization`, `x-api-key`, `cookie`, `set-cookie`, any `*apikey*`, `*secret`, `*password`, `*token`); openai-auth passes `chatgpt-account-id`. `secretPatterns` add value patterns to the common token patterns. `schemaKeys` name keys, at any depth of the body, whose values are declarations: their strings are scrubbed but their key names are never redacted, so a tool parameter named `api_key` keeps its schema. `summarize(redactedBody)` is the provider's body summary, stored as metadata `body`.

**It gets** `{ isEnabled(), setEnabled(enabled), dump(input) }` and `diffDumpBodies(previous, current)`. `dump({ session?, channel, phase?, bodyText, accountId?, url?, method?, headers?, status?, error?, meta? })` writes `<id>.body.json` (the redacted body; the original bytes when nothing was redacted), `<id>.meta.json` and `<id>.request.json` (url, method, account and headers, redacted), each 0600 and created exclusively, in a directory created or tightened to 0700, and returns `{ id, files }`, or undefined when dumps are off or the write failed (logged, never thrown). The id is `<ISO time>-<pid>-<6-digit counter>-<session>-<channel>[-<phase>]`; the pid keeps processes sharing a directory apart. A dump is diffed against the previous dump of the same session and channel; phases share the baseline. The baseline is the last body in memory, else the newest earlier dump on disk whose metadata `baselineKey` (sha256 of channel and session) matches, so it survives a restart and is cleared with the directory; it is never stored anywhere else. The diff runs on the redacted text, so its offsets index the body file.

**Differs from openai-auth.** `transport` becomes `channel`. The mask is the common `***REDACTED***`, not `[redacted]`. Bodies that are not JSON are string-scrubbed instead of written raw. The disk baseline is matched by `baselineKey`, so dumps written before adoption (which have none) are not used as baselines; it is looked up whenever the memory baseline is missing, including after eviction from the 100-key memory, instead of once per key per process. The counter has six digits. Its `bodySummary` (which reads OpenAI Responses fields), `dumpDiagnostic`, `DUMP_SESSION_HEADER` and reading the settings stay in the plugin.

**Differs from anthropic-auth.** Bodies, request headers and metadata are redacted; files are 0600 in a 0700 directory; names carry the pid. The directory sweep and size cap, response artifacts (`dumpResponseArtifact`), the relay payload file, partial-file atomic writes and the `/claude-dump` command stay in the plugin. Its `direct`/`http`/`websocket` transports and `cachekeep`/`start` tags map to channel and phase.

| `doctorAction({ checks, title?, label? })`, `runDoctorChecks(checks)`, `applyChosenRepairs(context, report)`, `formatDoctorReport(title, report)` | `DoctorCheck` is `{ id, run() → DoctorFinding[] }`; `DoctorFinding` is `{ code, message, accountId?, repair?: { label, apply() } }` | a `MenuAction`; `{findings}`; `{applied, declined, failed}`; lines |
| `runMenuLogin(login, context)`, `openBrowserForMenu(url, platform?, exec?)` | `MenuLogin` below | the login's `LoginAccount`; whether a browser opened |

**What a plugin supplies.** `AccountMenuOptions` is `{ title, store, terminal?, login?, newAccountId?, protect?, extraLocks?, pollQuota?, doctor?, custody?, status?, extraActions?, disableReason? }`. `login` is `MenuLogin { begin({headless, signal?}) → {url, instructions, completion: Promise<LoginAccount>}, openBrowser?(url) }`, where `LoginAccount` is `{ credential, identity?, label?, id? }`: the provider's browser and device-code flows, its URLs and token parsing all stay in the plugin. `protect` is the store's `remove` predicate and is passed to every removal the menu makes, delete-all included. `pollQuota(row)` returns an observation for the store's quota codec (a `/quota` `QuotaObservation` when the store was opened with `quotaCodec`). `doctor` is the plugin's checks; each repair is the plugin's own write. `custody()` says whether accounts come from a vault. Around the menu, the plugin builds its OAuth method's `authorize` with `menuAuthorize`, supplying `hasCredential` (see the rule below), `openMenu` (usually `runAccountMenu`) and its normal `login`.

**What it gets.** A full-screen menu drawn with first-party code (ported from openai-auth's `auth/ui/{ansi,select,confirm}.ts`, no prompt library): arrow keys, Enter, Escape (a lone Escape byte after 50 ms, so a split arrow sequence is not read as cancel) and Ctrl-C; raw mode and the cursor are restored on every exit. The heading shows the plugin's status lines and up to eight account lines. Local mode lists Add account and Re-authenticate (only with a `login`), Remove account, Enable or disable account, Check quotas, Auth doctor (only with checks), the plugin's extra actions, then Delete all accounts in red. Custody mode lists List accounts, Enable or disable account, Check quotas, the doctor and the extras: nothing that adds, signs in or removes, since those happen in the vault. Check quotas and the doctor stay under custody: neither changes which accounts exist or what they sign in with, so neither competes with the vault, and both still help an operator see why an account is not being used.

**Decisions.**

- *Single shot.* The menu runs one action and returns, as openai-auth's does; the operator reruns `opencode auth login` for another.
- *The failed callback.* OpenCode v1's `AuthOAuthResult` has no top-level "done, store nothing": every result ends in a callback whose success the host files as the provider's credential. After any menu action the plugin returns `menuCompletedResult()`, whose callback fails, so the host stores nothing and the operator sees `Failed to authorize` (openai-auth's capture `docs/baselines/opencode-auth-menu.v1.18.30.txt`, OpenCode 1.18.30). The library declares its own types matching the host's result shape, so it does not import `@opencode-ai/plugin`.
- *When the menu opens.* `menuAuthorize` never calls `hasCredential` on the TUI path (no `inputs`), so the TUI signs in as before. On the CLI path, the plugin's `hasCredential` must answer "a real credential exists" (the host's slot or a stored credential, `poolHasCredential` for the second half), never "the roster is non-empty": the signed-in account is usually the only one and may not be a roster row, and a roster check hid the menu from the operator adding their first extra account.
- *No TTY.* `runMenu` prints the title, status and actions as a plain list, says nothing was changed, and returns `not-interactive` without reading a key. `confirm` answers no without a TTY, so nothing destructive runs unconfirmed. openai-auth's selector threw instead; antigravity-auth's CLI fell back to a readline prompt.
- *Destructive actions.* A `destructive` action is drawn red and runs only after an explicit yes ("No" is listed first). Remove confirms by account name after the account is picked. Delete all removes row by row through `store.remove` with the plugin's `protect`, reporting what was deleted and what was kept and why; a protected id stays with its files untouched.
- *Re-authenticate.* Replaces the chosen row's credential through `store.replace`, keeping the row's identity when the login reports none, and refuses (writing nothing) when the login reports a different identity from the row's: replacing would silently turn the row into another account.
- *Check quotas.* Polls each valid row with a credential once, in roster order, records each observation through `store.recordQuota` with the row's epoch and identity (so a reading cannot land on a credential replaced meanwhile), then prints every row's windows from the stored map through `projectQuota`. A failed poll is printed beside the row; the others still run.
- *Doctor.* Checks only read; findings are printed, then each available repair is asked about in turn and only the ones answered yes are applied. A check that throws becomes a `doctor-check-failed` finding instead of hiding the rest. openai-auth's separate Auth doctor and Apply repairs entries become this one entry.
- *Single-item lists are shown.* openai-auth's selector returned a one-item list's value without drawing it; this one draws it, so a menu or account picker with one entry still asks.
- *Errors.* An action that throws is printed (`<label> failed: <message>`) and reported as `failed`; the menu never throws past the plugin's `authorize`, which still owes the host its result.

**Differences from each plugin's current behaviour.**

- *openai-auth* (`packages/opencode/src/auth/{methods,doctor}.ts`, `auth/ui/*`): its six entries (Add account, Auth current, Check quotas, Auth doctor, Apply repairs, Delete all accounts) become the list above. Auth current (writing OpenCode's main slot) has no library action: the slot becomes a placeholder under the agreed design; a plugin that still needs it passes it in `extraActions`. Its legacy (non-pool) branches, its three repairs (copy the stored main credential back into the host slot, drop state-file ids missing from the roster, clear an armed refresh backoff) and its usage-endpoint quota poll stay in the plugin, passed in as doctor checks and `pollQuota`. Its delete-all keeps `main` by name; with the library, `main` stays because the plugin's `protect` names it. Its quota check printed `quota refreshed`; the library prints each window.
- *antigravity-auth* (`packages/opencode/src/plugin/ui/auth-menu.ts`, `cli.ts`): its account rows with a per-account detail menu, Switch to this account, Verify account(s), Restore fingerprint, Configure models and Repair auth are provider extras for `extraActions`; its readline non-TTY fallback is replaced by the plain list; its quota bars and badges are not reproduced (the library prints remaining percent and reset per window).
- *anthropic-auth*: has no auth-login menu; its `authorize('max'\|'console')` methods keep their flows and may adopt `menuAuthorize` to gain one.

**Tests not carried.** From openai-auth `packages/opencode/src/tests/auth-menu.test.ts`: `keeps the three auth entries and their rendered login results byte-identical`, `renders exactly the six approved actions`, `Auth current changes only the OpenCode main credential`, `Check quotas bypasses an armed backoff and performs one fetch per account`, `Check quotas serves a custody fallback through the injected vault resolver`, `Auth doctor leaves both store files byte-unchanged` and `Apply repairs performs only the three declared mutations` test openai-auth's own entries, host slot and repairs, so they remain in openai-auth; `the recorded auth-login capture still says every action reports a failed login` reads a capture file kept in openai-auth and stays there. All of `auth-doctor.test.ts` tests openai-auth's own doctor checks and remains in openai-auth. antigravity-auth's `auth-menu.test.ts` and `auth-menu.actions.test.ts` test its formatters and detail menu, which stay in that plugin.
### ./commands

One slash command per plugin (`/openai`, `/claude`, `/antigravity`) opening one menu, drawn by OpenCode's TUI from a payload sent over the loopback RPC and by Pi with its extension UI. The per-feature commands (`/openai-account`, `/openai-quota`, `/openai-routing`, `/openai-killswitch`, `/openai-cachekeep`, `/openai-dump`, `/openai-logging`, `/openai-reset`; `/claude-account`, `/claude-quota`, `/claude-routing`, `/claude-killswitch`, `/claude-cache`, `/claude-cachekeep`, `/claude-dump`, `/claude-logging`, `/claude-fast`, `/claude-prime`, `/claude-start`; `/antigravity-account`, `/antigravity-quota`, `/antigravity-routing`, `/antigravity-killswitch`, `/antigravity-dump`, `/antigravity-logging`, `/gemini-dump`) are removed at adoption, not kept as aliases; what they did becomes a section or an action of the one menu.

Runtime exports: `createCommandMenu(options)`, `runPiCommandMenu(menu, ui, {sessionId?}?)`, `parseApplyRequest(value)`, `SECTION_SLOTS`, `DEFAULT_IRREVERSIBLE_CONFIRMATION`, `MENU_DISABLED_REASON`. Type exports: the menu model (`CommandMenuModel`, `MenuSection`, `MenuItem`, `MenuAction`, `MenuKnob`, `MenuChoice`, `MenuConfirmation`, `MenuAccount`, `KnobValue`, `KnobValues`, `SectionSlot`), the wire types (`CommandDialogPayload`, `CommandApplyRequest`, `CommandApplyResult`), the definitions a plugin writes (`PluginSection`, `PluginExtraSection`, `SectionContent`, `ItemDefinition`, `ActionDefinition`, `ActionInput`, `ActionOutcome`), the per-section options (`AccountsSectionOptions`, `QuotaSectionOptions`, `RoutingSectionOptions`, `LimitsSectionOptions`, `LoginOutcome`), `CommandMenu`, `CommandMenuOptions`, `CommandInvocation`, `NotifyKind`, `PiMenuUi`, `PiMenuOptions`, `SeamLogger`.

**Model.** Sections, in one fixed order everywhere: Accounts, Quota, Routing, Limits (built in), then Cache and Diagnostics (plugin slots, shown only when supplied), then provider extras in the order given. A section has read-only `lines`, `items` and section-level `actions`; an item has a `label`, an optional `detail`, the projected `account` (built-in sections only) and `actions`. An action has an `id`, a `label`, typed inputs (`choice`, `toggle`, `number`, `text`; `number` and `text` may be left empty, which the action receives as `null`) and an optional confirmation `{message, irreversible}`. An irreversible action always carries one: the `ActionDefinition` type requires `confirm` with `irreversible: true`, and a definition that names none (plain JS) gets `DEFAULT_IRREVERSIBLE_CONFIRMATION`. `apply` refuses an action that carries a confirmation unless the request says `confirmed: true` (`{ok:false, needsConfirmation:true}`), so both renderers confirm before applying; Pi confirms with `ui.confirm`.

**What a plugin supplies.** `createCommandMenu({command, title, store, extraLocks?, accounts?, quota?, routing?, limits?, cache?, diagnostics?, extras?, logger?, now?})`:

- `store`: its `PoolStore`; `extraLocks`: its legacy locks, passed to every store write the menu makes.
- `accounts.login {label?, knobs?, run(values, invocation) → LoginOutcome}`: `{status:'ready', account}` adds now; `{status:'pending', message, completion}` shows `message` (the login URL or device code) and adds the account when `completion` resolves, reporting through the invocation that asked; `{status:'cancelled', message?}`. Without it, Accounts has no add action. `accounts.protect` is passed to `store.remove` (the plugin's reserved ids and pending-operation records). `accounts.describeIdentity(row)` chooses what is shown as the identity (defaults to the recorded identity).
- `quota.check(ids, invocation)`: the plugin's "check now" poll; without it the menu calls `store.requestReading` for each id and awaits `store.pullsSettled()`. `quota.scope` picks the projection scope (default `all`).
- `routing.orderedVariants`: further `routing.mode` values offered between `ordered` and `sticky-balanced` (openai-auth: `main-first`, `fallback-first`); `routing.formerMainId` for the "tried in order" line.
- `limits.labels`: the window labels floors can be set for (defaults to the labels in the pool's quota readings, else `primary`).
- `cache`, `diagnostics`: `{title, build(invocation) → SectionContent}`; `extras`: the same with an `id` (not one of the fixed ids). A section whose `build` throws shows "This section could not be loaded." and the rest of the menu still opens.
- `logger`: receives the seam's warnings and failed actions (defaults to the library logger's `commands` channel).

**What it gets.** Accounts: the roster in order with type, enabled state (and disabled reason), identity and a quota summary; add (through the plugin's login), remove (irreversible, `store.remove` with `protect`), enable, disable (reason `MENU_DISABLED_REASON`), and move to a position (`store.reorder`). Quota: per-account windows (`primary 42% used, resets in 1h 30m`) and the credit budget from the `/quota` projection, and "check now" for one or all candidate accounts. Routing: the mode as a choice over `ordered`, the plugin's variants and `sticky-balanced`, written to `routing.mode`; and the roster order as an editable list (`store.reorder`). Limits: the killswitch on/off (`killswitch.enabled`) and per-account floors, minimum % left per window label, under `killswitch.accounts.<id>.<label>` (an empty input clears a floor; an account left with no floors loses its entry). Every settings write goes through `store.updateSettings` with the plugin's `extraLocks`.

**Wiring.** OpenCode: on the slash command, `menu.open({sessionId, notify})` and send the `CommandDialogPayload` to the TUI; on the TUI's apply RPC, `parseApplyRequest(body)` and `menu.apply(request, {sessionId: request.sessionId, notify})`, and send back the `CommandApplyResult` (its `menu` is the refreshed model, so the drawer redraws from it). The drawer is plugin code; the payload carries everything a generic drawer needs (titles, lines, items, typed inputs with current values, confirmations), so it no longer needs per-command dialogs. Pi: `runPiCommandMenu(menu, ctx.ui, {sessionId})` from the command handler.

**The seam.** `open` and `apply` are the only producers of payloads, and both go through one function: every part is projected field by field (an account is `{id, label, enabled, type, identity}` and nothing else), then the whole payload is scrubbed of credential-shaped property names (case, `-` and `_` ignored: names ending in `token`, `key` or `secret`, and `access`, `refresh`, `apiKey`, `password`, `authHeader`, `credential`, `credentials`), and each drop is warned with the field paths, never the values. The section and action bodies stay in the process. A plugin's `facts` (free name/value display pairs on a section or item) are the one place plugin data passes through unprojected, so they are where the scrub matters.

**Per-invocation context.** `open` and `apply` copy the `{sessionId, notify}` they are given before their first await, and work an invocation leaves running (a pending login) reports through that copy. A host can therefore reuse one context object across sessions without one session's feedback reaching another; the menu keeps no state between invocations.

Differences from each plugin's current behaviour:

- openai-auth: one dialog instead of eight; `/openai-reset` becomes a provider extra, `/openai-cachekeep` the Cache section, `/openai-dump` and `/openai-logging` the Diagnostics section, all supplied by the plugin. The payload is the generic model, not `{command, text, knobs}`, so `command-dialogs.tsx` is replaced by one generic drawer. `routing.mode` gains `ordered` (written explicitly when chosen; openai-auth's legacy readers do not know the value and route `main-first` for it, as they do for an absent mode; see the `routing.mode default` limit below). The killswitch's `main` thresholds have no menu entry: the main account is a pool row like any other under `killswitch.accounts`. `buildDialogPayload`'s scrub is kept and widened from `*token` to `*token`, `*key` and `*secret`.
- anthropic-auth: the same sections replace eleven OpenCode commands and nine Pi commands; `/claude-cache`, `/claude-fast`, `/claude-prime` and `/claude-start` become Cache or provider-extra entries. On Pi the menu is now interactive (`select`, `confirm`, `input`) where the commands took arguments and answered with `notify`.
- antigravity-auth: the same sections replace its seven OpenCode commands; `/gemini-dump` is not kept. Its Pi package registers no command today; adopting gives it the one command.

**Pool integration.** A vault credential becomes a `RoutingRow { id: routeId, kind: 'oauth' \| 'api-key', quota? }` through `routingRows()`; the plugin concatenates them with its local rows (from `/store`) and passes the lot to `admit`, `routeOrdered` or `routeSticky` unchanged. Only enabled rows in state `active` route; declined or cold rows stay in `snapshot()` for the menu. Quota for a vault row lives in the roster file and is merged with `/quota`'s `mergeQuotaObservation` by `recordQuota`, which requires the receipt the reading was taken with. The fence is mandatory and exact: the receipt's credential must still be the row's representative or alias, and its account must equal the row's (a known account on one side never matches an absent one; the only absent-absent match is a row that has never had a known account, reached by a receipt issued for it in that state). While the row is `unclaimed` only an `asserted` or `parsed` identity is accepted, never the roster's own expectation. An observation for a replaced account is dropped, and the authorizing account is never inferred by reading the roster after the request. An admission refusal's `requestPull(id)` for a vault id is the plugin's cue to fetch a reading through `send(id, …, { site: 'quota' })`. Nothing in `/store`, `/routing` or `/quota` changed: the store never holds a vault row, and a vault row never holds a token, so there is no local refresh. The roster file (`rosterPath`) is the plugin's, separate from the store's files, secret-free, written 0600 through `writeJsonAtomic` under a `withLock` write lock.

**Token acquisition.** Every physical send costs one local vault call (`get_scoped`): there is no credential cache and no single-flight of credential reads, and each call to `dispatch` gets its own receipt. This is deliberate (anthropic-auth's reviewed design): a revoked enrollment or a changed record takes effect on the next send. It is the token-acquisition step the hot-path rule allows to block. Metadata is coalesced: one connection, one discovery in flight. OAuth reads demand `minTtlMs` 300 000 and refuse a served token with less validity; API keys are served without a TTL demand and may have no expiry. A 401 is retried once, only when re-authorization (a fresh `get_scoped`) serves a new record version of the same credential and account; the final 401 is reported by `credential_id` with the exact record version the failing send used, signed with the enrollment token that authorized it, and only for a receipt this custody issued. 429, 402 and 5xx are never reported. After a reported 401 the consumer refreshes the roster in the background, so an account the vault now holds cold leaves routing before the next poll.

**Enrollment.** Propose and poll run only in `ClaustrumEnrollmentManager.reconcile()`, which setup calls; `ClaustrumConsumer` never enrolls, and a missing token fails a send with `not-enrolled`. The request secret is written (0600, under the `ceremony` lock beside the state file) before the propose call, so a restart between propose and poll resumes the poll, and a crash before the request id is saved re-proposes with the same secret (the vault returns the same request id). The token is written before the pending state (and its secret) is replaced. Terminal codes `invalid_params`, `pending_exists`, `not_found`, `already_consumed`, `superseded`, `stale_generation` block the ceremony and scrub the secret whatever action the client reports; `pending_queue_full` is always retried; other codes follow the client's action. The token and state directory is created 0700 and an existing one with group or other bits is tightened to 0700; files must be owner-only regular files (no symlinks) under no group- or world-writable non-sticky ancestor.

**Discovery and the view cursor.** `list_scoped` returns `view`, a digest over this consumer's visible credentials, grants, state and identity, not over `record_version`. `onRoster` fires once per view change (the first roster included); a token refresh never fires it. An absent `account_id` is no claim, not a failure. A record the consumer cannot use (empty id, duplicate id, blank identity, empty state) is skipped with a `logger.warn('skipped malformed vault record', { credentialId, reason })` (a safe id, omitted when the id itself was unusable, and one of four fixed reasons) and the rest of the list is used. Such a reply is incomplete: the roster records `complete: false` and `rejected` (the same id and reason pairs), and no previous member the reply does not account for is removed. A member is unaccounted for when its record was rejected, or when any rejected record has no usable id (it could be any of them). An unaccounted member of a live account stays one of its aliases; an account with no member listed stays as its last good projection marked `stale`. A credential the same reply lists under a live account is taken out of every stale row (the next remaining member becomes the stale row's credential), so one credential is never authorized or quota-recorded under two account bindings; a stale row left with no member is dropped rather than kept as unavailable (the primary hook reads the inventory, not stale rows, so it is unaffected). A valid newcomer is added either way, and only a complete reply removes an account. The client's own decoder still refuses a whole reply whose rows are wire-malformed (a non-string id, a non-array field); that fails safe (the last committed roster keeps serving) and is declared below. Several records logged into the same provider account collapse into one row (active first, then the existing binding, then by id), listing the rest as `aliases`. There is no main: the record named `oauth:<provider>` is an ordinary pool account. The discovery lease (`claustrum-roster`, 30 s, renewed) covers the list call and the commit; a run that lost it is refused at commit, a peer holding it means the last committed roster is served, and a failed list or custody switching off mid-run writes nothing.

**Route ids.** `<routePrefix><credentialId>` plus `~<10 hex of sha256(identity)>` when the account is known; a reserved local id gets a numeric suffix. A route keeps its id and quota while its credential keeps the same account (an identity learned for the first time counts as the same account); a credential that now logs into a different known account gets a new id and no quota. A record listed without an identity keeps the last account it was known to log into (as representative or alias), and the row is marked `unclaimed`: the omission is neither proof of continuity nor of replacement. When the account comes back the route continues; when a different known account appears, it is a replacement and inherits no route id, quota or decline. A record that claims the account is preferred as representative over one only remembered as belonging to it.

**Receipt identity.** A receipt's `accountIdentity` is what it is bound to: the vault's assertion, else the plugin's parse of the token, else the roster's expectation, and `accountIdentitySource` says which (`asserted`, `parsed`, `expected`, `none`). `assertedCredentialId` and `assertedAccountIdentity` hold only what the served reply itself said and are never filled from the roster or a parse; `expectedAccountIdentity` is the roster's account at request time. With `requireAssertion` a receipt is refused (`identity-unasserted`) unless the reply asserts the credential id and the expected account and the roster's account is known; a different asserted account is `identity-changed`. Receipt validation (safe-integer record version, serving margin), the fresh `get_scoped` per physical attempt, the one bounded 401 replay on a different version of the same credential and account, and reporting against the failing send's own receipt are unchanged by this.

**Primary hook.** The library has no main. A plugin that keeps a host-owned main calls `resolveVaultPrimary` with its filtered inventory, whether it is complete, the previous verified binding, the request's expected account (on the request path) and the record id that holds the role. Main follows the account that record claims; another credential of that same account may serve it when the record is not active, and no credential of another account is ever promoted. A complete inventory without the record is `absent` (`authorize('main')` should fail; ordinary fallback routing is unaffected but must not be renamed main). A rejected primary record (`malformed`), a record without an identity claim (`unclaimed`), or a reply with a rejected record of unknown id or `complete: false` (`incomplete`) is `unavailable`, never absent, and hands back the last verified binding untouched; continuing to serve it still needs a fresh receipt that matches it (`requireAssertion`). A known different account is `ready` with `replaced` set to the previous binding: the plugin drops quota, profile, backoff and cache affinity owned by that account and fences outstanding observations, while the logical route and the host slot or device identity stay. A request whose expected account is no longer main's is `unavailable` (`identity-changed`).

**Declined-account interlock.** The consumer keeps declines in the roster file, keyed by account (or credential id while the account is unknown), never by record version. A decline follows the provider account: an entry made while the account was known matches every credential id and alias that logs into that account, so relabelling, a new alias, or removal and return keep it declined. A credential id that now logs into a different known account does not match; that account has its own policy, and the declined account's entry is kept (entries are never pruned). While the account is unknown on either side the entry matches by credential id. `accept` lifts every entry that declines the accepted route's account and credential ids, and leaves a different account's entries alone.

**Host slot.** In custody mode the host slot holds `custodyPlaceholder(provider)` (an OAuth-shaped value with an empty access token). `assertHostSlotMatchesMode` fails closed on a real login in the slot under custody (anthropic-auth's behaviour, and the answer to openai-auth #173: serving either the host login or the vault would silently pick one of two accounts the user may not mean, so the plugin refuses until the user leaves custody or removes the login) and refuses the placeholder in local mode; `assertNotCustodyPlaceholder` guards a local refresh.

**What a plugin supplies** (`OpenCode2AuthAdapter<Q, A>`, `Q` being the plugin's own quota reading and `A` its per-attempt value; the library never looks inside either):

| member | role |
| --- | --- |
| `providerID` | every hook is registered with `{providerID}`; other providers never reach the adapter |
| `chooseAccount({providerID, modelID, sessionID, agent, kind, previousAccountId?, rerouteFrom?})` | the account for one model request, or `undefined` (the request is refused, kind `no-account`); called again on every retry. The plugin admits and routes its `/store` pool rows with `/routing` here; `rerouteFrom.accountId` was just refused before any output, so it should not be picked again unless nothing else is admissible |
| `accountHeaders({…scope, accountId})` | the credential and per-account headers as `HeaderEdits` (a string sets every spelling of the name, `null` removes it), or `{headers, attempt}` where `attempt` is the plugin's per-attempt value (a served credential receipt, say); called once per attempt, applied in `model.request`, `http.request` and `experimental.ws.handshake` |
| `rewriteRequest?`, `rewriteResponse?`, `rewriteHandshakeURL?` | optional URL/body rewrite before the account headers, body-stream/status rewrite after detection, WebSocket URL rewrite; each also gets `attempt` |
| `rewriteWebSocketFrame?({…scope, attempt, frame})` | optional rewrite of every outgoing WebSocket frame of the provider, from `experimental.ws.send` (registered only when this is supplied); returns the frame to send or `undefined`. It must be a deterministic function of the frame, stable per session; it may add `input` items or settings fields but must never alter, drop or reorder the items the host put in `input`, nor touch `previous_response_id` (see below); `attempt` is `undefined` for a frame no attempt can be tied to, and the rewrite still runs |
| `quotaFromHeaders?(headers, status, attempt)` | quota in HTTP response headers |
| `limitFromResponse?({status, headers, body(), attempt})` | an account-level refusal from an HTTP response before streaming; `body()` reads a copy |
| `inspectEvent?({transport, data, event?, attempt})` | one SSE event's `data` or one WebSocket frame → `{outputStarted?, quota?, limit?, done?, error?}`; `done` (last event of the response) or `error` (the response failed) ends the attempt |
| `limitFromError?(error, attempt)` | a refusal recognised only from the error the retry hook receives |
| `onAttemptEnd?(attempt, {status?, outputStarted, limit?, error?})` | called once per attempt when it ends (rules below); `error.reason` is `failed`, `cancelled` or `abandoned`, absent when the response completed whatever its status. The retry hook waits for it to settle |

Options: `hostCredentials` (values that must never reach the wire; default `[placeholderSecret(providerID)]`), `maxRecords`, `logger` (`{warn}`).

**What it gets.** `installOpenCode2Auth` registers `model.request`, `http.request`, `http.response`, `experimental.ws.handshake`, `experimental.ws.receive` and `retry`, keeps a `sessionID:kind → attempt` record (bounded, oldest dropped first, cleared on the host's `session.deleted` event or `forgetSession`), and returns `{on, accountFor, forgetSession, size, dispose}`. Every event that belongs to an attempt carries it as `handle` (`retry` already uses `attempt` for the host's retry count). Events: `select` (with the hook that picked), `quota` (attributed through the record, since neither headers nor frames name the account), `limit` (`via: http | ws | error`, with `outputStarted`), `retry` (`reason: reroute | output-started | no-account | host-decides`, host and final decisions). Listener errors are logged and swallowed. The retry hook awaits every `limit` listener before asking for the retry, so a plugin that records the rate-limit mark there has it in place when `chooseAccount` runs again.

**Attempts (library decision).** An attempt is one physical send: `{attemptId, providerID, modelID, sessionID, agent, kind, accountId, transport, data}`, created when the account is chosen, in `model.request`, or in `http.request`/`experimental.ws.handshake` when no fresh attempt is waiting (the host skipped `model.request`, or a second send followed without one). `transport` is `undefined` until a transport hook has carried the attempt. `data` is what `accountHeaders` returned as `attempt`. The attempt is handed back on everything that belongs to it, and attribution follows fixed rules, so an event that cannot be tied to an attempt reaches no adapter callback and no listener rather than a wrong one:

- an HTTP response belongs to the attempt whose `http.request` produced its request; if the host hands back another request object, it belongs to the newest attempt of its session and kind only while that attempt went out over HTTP and has no response yet; its body events belong to the same attempt;
- a WebSocket frame belongs to the newest attempt of its session and kind only while that attempt went out over WebSocket (its handshake ran) and has not ended. The host runs one exchange at a time per session socket, so frames between one handshake and the next belong to the earlier attempt; a frame after a newer `model.request` but before its handshake goes nowhere;
- the retry hook names only the session, so it judges the record chosen as described under the retry policy, and hands that attempt to `limitFromError` and the `retry` event.

An attempt ends once: an HTTP body read to the end, errored (`failed`) or cancelled by the host (`cancelled`, with `outputStarted` as observed); an HTTP response with an error status or no body, at once, with its status, so the end does not depend on whether the host reads an error body (2.0.21 does read it); an event verdict with `done` or `error`; a transport hook that throws (`failed`); or `abandoned`, when it was still open as a newer attempt of its session and kind began, its session was forgotten, its record was dropped for space, or the installation was disposed. The host has no hook for a WebSocket closing or a turn being cancelled on WebSocket, so such an attempt ends `abandoned` at the next of those points; a plugin should flag `done` on the provider's terminal events so a WebSocket attempt ends when its response does. Per-attempt values belong in `data`, not in headers: the host keys a session's WebSocket on its handshake headers, so a header that changes per attempt opens a new socket every turn and loses incremental continuation: on 2.0.21, with a per-attempt header on the handshake, the second turn of the placement test's frame-rewrite scenario went out on a new socket with no `previous_response_id` and the full input.

**WebSocket frame rewrite (library decision).** The host chains turns by diffing its own request as it was before `experimental.ws.send` ran (`research/opencode2-thin/REPORT.md` §4), so a rewrite applied uniformly to every frame keeps `previous_response_id` continuation incremental; a rewrite that alters, drops or reorders the host's `input` items, changes `previous_response_id`, or is applied to some frames and not others, leaves the server's view out of step. Items the rewrite adds become part of the server's history, which the host never re-reads on an incremental turn, so adding (for example a settings update just before a new user message) keeps the follow-up turn incremental. The hook therefore rewrites every frame of the provider, attributed or not.

**Retry policy (library decision).** The retry hook carries no request kind and no output flag, so the record supplies both: it judges the session's latest refused attempt, else its primary attempt, else its latest. Before output, a recognised limit returns `{retry: true, delay: 0}` whatever the host decided, including errors the host deems final (`usage_limit_reached`); after output it returns `{retry: false}` so the answer is not repeated; a request refused for having no account returns `{retry: false}`; anything else keeps the host's decision.

**Host credential (library decision).** The plugin's pool is the authority; the host holds only a placeholder OAuth credential, `{access: refresh: 'common-auth-placeholder.<integrationID>', expires: now + 1 year, metadata: {commonAuthPlaceholder: true}}`, so the provider stays catalogued. `registerOpenCode2AuthMethods(ctx, {integrationID, methods: [{method, authorize(answer)}], onLogin(result, {integrationID, methodID}), label?, now?})` registers each method through `ctx.integration.transform(editor => editor.method.update(...))`. A method's `authorize` returns the host's `{url, instructions, expiresAt?, mode: 'auto' | 'code', callback}` except that `callback` resolves to the plugin's own login result; the helper awaits `onLogin` (the pool write) and only then hands the host a placeholder, so a failed pool write fails the host login and stores nothing there. Host-driven `refresh` returns a fresh placeholder and never calls the plugin. A real credential stored earlier under one of these method IDs is replaced by a placeholder at its first refresh; a plugin that wants to import such a login reads it through `ctx.integration.connection` first. The installer refuses (`host-credential-on-wire`) any HTTP request or handshake that still carries a placeholder after the account headers are applied.

**Recipe weaknesses that remain, and what a plugin does about them.**

- *WebSocket depends on `experimental.*` hooks* (`ws.handshake` for the identity, `ws.receive` for quota, output and refusals). The `opencode2-placement` CI job fails when any of them stops firing. The job runs the host version pinned in the test (`OPENCODE_CLI_VERSION`, 2.0.21); bump that pin to adopt a new host release only once the job passes on it, and treat a red job as a release blocker. The loopback proxy is the fallback if the hooks go away.
- *A refused WebSocket handshake switches the session to HTTP for good* (host source, untested). The installer never throws in the handshake in normal flow: `no-account` is raised in `model.request`, before a transport is chosen. A plugin should keep `accountHeaders` from throwing and should not refuse at the handshake; HTTP still carries every account.
- *Some WebSocket recoveries bypass the retry hook* (`previous_response_not_found`, `websocket_connection_limit_reached` go to a full resend). They still run `model.request`, so the account choice applies; they just cannot be rerouted on a limit. Nothing to do beyond keeping `chooseAccount` honest about limits recorded from `limit` events.
- *The retry hook has no kind, headers or output flag, and stops being called after 10 retries in one step.* The installer tracks refusal and output itself; a pool with more than ten refusing accounts cannot be walked within one step. Concurrent requests of the same kind in one session each get an attempt and HTTP responses are tied to their own request, but the retry hook and `accountFor` see only the newest (not observed on WebSocket, which serialises a session's exchanges).
- *Every account switch on WebSocket costs a new socket and a full, non-incremental request* (measured; caching recovers on the next turn). A plugin should keep a session on one account (sticky routing) and switch only on limits.

**Differences from each plugin's current behaviour.** All three plugins own their request path on OpenCode 1 (a loader `fetch`); here the host owns it and the plugin only edits headers, URL and body at fixed points. openai-auth: credentials and `chatgpt-account-id` go in `accountHeaders`, quota comes from the `x-codex-*` headers and `codex.rate_limits` frames through `quotaFromHeaders`/`inspectEvent`, and its in-fetch 429 failover becomes the retry-hook reroute; the host's main login slot holds a placeholder instead of the main account. anthropic-auth: its URL/body rewrite and its response-stream rewrite move into `rewriteRequest`/`rewriteResponse`, and a header the host adds that must not go out (an API-key header, say) is a `null` header edit; it is HTTP only, so none of the WebSocket weaknesses apply. antigravity-auth: its endpoint and body rewrite go in `rewriteRequest`; whether OpenCode 2 routes its models through a driver these hooks reach is not established here.

**Placement contract.** `test/opencode2/e2e/placement.e2e.test.ts` installs `@opencode/cli` 2.0.21 with npm into a scratch directory, bundles a test plugin built on this subpath, and runs the real host in server mode with isolated `HOME`/`XDG_*` against a loopback mock with two accounts, the host credential set to the placeholder. It asserts the bearer per account on HTTP and WebSocket, a switch mid-session, quota attributed to the right account, a reroute before output (WebSocket rate limit, HTTP usage limit the host would not retry), no retry after output (both transports), an HTTP 401 ending the attempt whose receipt went out on that request with its status and value, a frame rewrite that reaches every frame while the follow-up turn stays incremental on the reused socket, every choice made in `model.request`, and that the placeholder never reaches the wire. It runs only with `COMMON_AUTH_OPENCODE2_E2E=1` (`COMMON_AUTH_OPENCODE2_E2E_CLI_DIR` reuses an existing pinned install), in the `opencode2-placement` CI job; its provenance rows are in `test/opencode2/e2e/sources.md`.

### /store declared boundaries

1. **Crash windows, per operation.** `add` writes config then state: a crash between leaves a row with no credential (never a candidate) that a re-run `add` with the same id completes at epoch 1. `replace` writes config then state: a crash between leaves the bumped epoch beside the prior credential; in-flight work for the prior epoch fails attribution, and a re-run `replace` completes it and bumps again. `rotate` writes state then config (only when it has an identity or entry to write): a crash between leaves the rotated credential with the old identity or entry, and the next refresh or `recordIdentity` completes it; with nothing to write to the config, a crash after the state write is completion. `reorder` makes one config write: a crash leaves the whole old order or the whole new one.
2. **Durable replace intermediate.** Work issued after a crash between `replace`'s writes captures the bumped epoch with the credential `replace` meant to retire, so its reading is attributed and applies; the re-run `replace` and the next reading supersede it.
3. **Foreign writers.** A writer outside the library can replace a credential in place (id, epoch and identity unchanged), or remove a row and re-add its id; a pull in flight across either applies to the successor until the next reading supersedes it. A foreign write that bumps the epoch while a refresh is in the provider call makes the refresh fail attribution and discard its rotation.
4. **Id reuse.** When a library write drops the entry of an id absent from the roster, `add` of that id is refused (`id-removed`) for the rest of the process; a fresh process accepts it.
5. **Mixed versions.** An older writer that rewrites the config keeps `commonAuthPool` as an unknown top-level key and the recorded identity in `accountId`, so every row keeps its credential. An older writer's config rewrite drops a row's credential only if the roster row lost `type` or an api row's `baseURL`; the store always writes both. `authHeader` lives in the config only; one written to the state file does not survive an older roster write. The older writers' unbidden top-level keys (`main`, `claustrum.rowHistory`) survive library writes.

- **Unknown stored window length:** a limit stored without `windowMinutes` sorts last and carries no length; openai-auth assigned 300/10 080 minutes by slot.
- **Third window:** the sticky primitives weigh at most two readings per projection; further windows are judged by admission only.
